# 微信内置浏览器安全弹窗恢复访问验证处方

> 来源：2026-06-23，处理秒哒站点在微信内置浏览器访问时出现“无法确认该网页的安全性，请谨慎访问”的恢复访问验证失败问题。
> 本文记录通用方法论，不保存某一次申诉生成的具体 txt 文件名和验证码内容。

## 适用场景

| 场景 | 是否适用 |
|---|---|
| 微信内置浏览器打开网站时出现“无法确认该网页的安全性，请谨慎访问” | 适用 |
| 页面底部有“申请恢复访问”，进入后要求在网站根目录部署 txt 验证文件 | 适用 |
| 已经把 txt 文件放到项目 `public/` 或根目录，但微信仍提示“校验失败” | 适用 |
| 普通 SEO、备案、微信 JS-SDK 域名校验 | 不完全适用，思路可参考 |

## 核心判断

微信要求的不是“代码仓库里有这个 txt 文件”，而是腾讯/微信的校验服务器可以从公网直接访问：

```text
https://your-domain.com/<wechat-generated-file-name>.txt
```

并且响应正文必须严格等于微信页面给出的验证码内容。

最重要的验收标准：

- HTTP 状态码应为 `200`。
- 最终响应正文只能是那一行验证码内容，不应返回 HTML 首页。
- 文件名、扩展名、大小写必须完全一致。
- 文件内容不能多字、少字、带引号、带空格、带富文本，也不要带 BOM。
- 不要把文件部署成 `/public/<file>.txt`，公网路径必须是 `/<file>.txt`。

## 标准操作流程

1. 在微信拦截页点击“申请恢复访问”。
2. 选择“部署验证文件并提交证明材料”。
3. 复制微信生成的 txt 文件名和文件内容。
4. 在网站根目录部署该 txt 文件。
5. 用公网方式验证，不要只看项目文件树：

   ```bash
   curl -i https://your-domain.com/<file>.txt
   ```

6. 只在 `curl` 结果确认正确后，再回到微信页面点击“已部署，开始验证”。

## 必须用公网验收

推荐验收命令：

```bash
curl -i --max-time 20 https://your-domain.com/<file>.txt
```

正确结果应该类似：

```text
HTTP/2 200
content-type: text/plain

<wechat-generated-content>
```

如果返回的是下面这种情况，微信一定会校验失败：

```text
HTTP/2 200
content-type: text/html

<!doctype html>
<html>...
```

状态码是 `200` 也不代表成功。很多 React/Vite SPA 或无代码平台会把所有未知路径都回退到 `index.html`，于是 `/<file>.txt` 表面是 200，实际内容却是首页 HTML。

## 常见失败原因

| 表现 | 根因 | 修复方向 |
|---|---|---|
| `/<file>.txt` 返回首页 HTML | SPA fallback 抢先命中，静态文件没有被单独发布 | 让静态文件优先于 fallback；或用平台支持的根目录静态文件机制 |
| `/<file>.txt` 返回 404 | 文件没有进入最终发布产物，或目录放错 | 确认构建产物根目录有该文件 |
| `/<file>.txt` 返回 301/302 后到首页 | 跳转规则把 txt 路径重写了 | 给验证文件加例外规则 |
| 本地能打开，线上不行 | 只改了源码，没重新发布/缓存未刷新 | 重新部署并清 CDN 缓存 |
| 内容看着一致但仍失败 | 多了空格、换行、BOM、中文标点、引号 | 用纯文本单行保存，重新上传 |
| HTTP 能访问，HTTPS 不行 | 证书、域名绑定或 HTTPS 回源异常 | 修 HTTPS，优先让 HTTPS 路径直接返回验证码 |

## 秒哒/React SPA 特别注意

在 React/Vite 项目里，理论上放到 `public/<file>.txt` 后，构建产物根目录会出现 `/<file>.txt`。但秒哒这类平台可能有自己的发布层、域名层或运行时注入逻辑，不一定按普通 Vite 静态托管规则暴露。

因此不能只相信秒哒 Summary 里说“已在 public 目录创建文件”。必须立刻用公网请求验证实际返回内容。

如果发现返回首页 HTML，说明要修的是“静态文件发布/路由回退规则”，不是继续反复创建同名 txt。

## 给秒哒的修复提示词

```text
当前网站需要通过微信/腾讯安全恢复访问验证。微信要求在网站根目录直接访问一个 txt 文件。

请不要只在源码里创建文件后就结束，必须确保线上公网路径：
https://当前域名/<微信生成的文件名>.txt
直接返回微信给出的验证码内容。

红线：
- 不允许让该 txt 路径走 React Router / SPA fallback / index.html。
- 不允许返回 HTML 页面。
- 不允许把文件路径变成 /public/<文件名>.txt。
- 不允许改动现有页面业务逻辑。

请你检查并修复静态资源发布规则，让验证文件优先于所有路由 fallback。
完成后请用线上公网 URL 验证，并回报：
1. 请求的完整 URL
2. HTTP 状态码
3. Content-Type
4. 响应正文是否严格等于微信验证码内容
5. 是否存在跳转
```

## 如果平台做不到

如果秒哒或当前托管平台无法为根目录 txt 文件配置静态直出，需要改用外层能力兜底：

- 用自己的 Nginx/CDN/边缘规则为 `/<file>.txt` 单独返回纯文本。
- 或把域名解析到可控托管服务，先确保验证文件可直出，再代理/跳转应用主体。
- 或联系平台支持，要求增加“根目录静态验证文件”发布能力。

Nginx 兜底示例：

```nginx
location = /<file>.txt {
    default_type text/plain;
    return 200 "<wechat-generated-content>";
}

location / {
    try_files $uri $uri/ /index.html;
}
```

关键是验证文件规则必须写在 SPA fallback 前面。

## 本次实战复盘

本次站点的 txt 验证文件路径公网访问返回了：

- 状态码：`200`
- `Content-Type`：`text/html;charset=UTF-8`
- 正文：站点首页 HTML

因此微信校验失败的根因不是“微信参数填错”，而是验证文件没有被线上静态资源系统命中，访问 `/<file>.txt` 时被应用的首页回退规则接管了。

结论：以后遇到微信恢复访问验证失败，第一步不是继续让 AI “重新创建文件”，而是直接 `curl -i https://域名/文件名.txt` 看腾讯校验服务器实际会抓到什么。

## 2026-06-23 复测后的边界结论

这次对 `moumou.shiyichuang.com` 做二次复测后，边界进一步明确：

| 检查对象 | 实测结果 | 结论 |
|---|---|---|
| 秒哒构建后的 BOS/CDN 源文件 | HTTP 200，`Content-Type: text/plain`，`Content-Length: 40`，正文与微信验证码匹配 | 源文件和构建产物本身是正确的 |
| 绑定后的正式域名根路径 txt | HTTP 200，但 `Content-Type: text/html;charset=UTF-8`，正文仍是站点首页 HTML | 正式域名服务层仍把 txt 路径回退到了首页 |
| `index.html` 中加入 `document.write` 输出验证码 | HTML 中确实出现了这段前端脚本 | 对微信服务器校验无效，因为服务器只看 HTTP 响应正文，不执行浏览器 JS |

当前真实结论：

- 在“继续使用秒哒当前绑定域名/BLB/云服务分发链路”的前提下，秒哒应用代码层暂时无法独立解决这个问题。
- 问题不在 React 代码、`public/` 文件、验证码内容，也不在本地构建产物。
- 问题位于秒哒域名服务层或平台发布层：它把根路径 txt、`robots.txt`、`sitemap.xml` 等静态文件请求统一 rewrite 到 `index.html`。
- 继续让秒哒在应用代码里“修复”大概率只会得到前端脚本兜底，但微信校验不会执行前端脚本。

在不迁移托管架构的前提下，可行路径只剩两类：

1. **找秒哒官方/平台支持处理**：要求在 `moumou.shiyichuang.com` 的部署配置中，把微信生成的 `/<file>.txt` 路径排除在 SPA fallback 之外，并在服务端直接返回对应纯文本。
2. **走微信“仅提交证明材料”兜底**：在无法让平台开放根目录 txt 直出的情况下，通过域名所有权、DNS 解析、备案/主体等材料进行人工证明。

另一个技术可行但不属于“秒哒独立解决”的方案，是把域名迁移到可控托管/CDN/Nginx 层，自己配置 `/<file>.txt` 优先于 SPA fallback 返回纯文本。
