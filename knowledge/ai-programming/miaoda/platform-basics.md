# 秒哒平台基础认知

> 实战角度对秒哒（百度 MIAODA）平台架构的理解。这部分认知能让你在与秒哒 AI 协作时，准确判断"这件事归哪个层做"。

## 一、四套独立运行时

秒哒生态里有 4 个不同的"地方能跑代码"，**它们的环境变量、密钥、运行语言、生命周期都互相独立**。混淆它们是新人最大的踩坑源。

| 运行时 | 跑什么 | 语言 | 环境变量从哪里来 | 何时执行 |
|---|---|---|---|---|
| 应用前端 | 用户浏览器里的页面 | TypeScript/React | 不能放密钥 | 用户访问页面时 |
| 应用后端（Edge Function） | Supabase 风格的 Deno 函数 | TypeScript/Deno | Supabase Functions Secrets | API 被前端调用、或外部 webhook 触发 |
| 应用数据库 | Supabase Postgres | SQL | DB 连接信息 | Edge Function 访问时 |
| 自定义技能（Skill） | 上传的 .zip 包内的 scripts/ | Python / Shell | 技能控制台「环境变量」面板 | AI 在"生成代码 / 执行任务"时主动调用 |

### 关键含义

- **支付密钥这种敏感凭证**：放"自定义技能的环境变量"或"Edge Function Secrets"都可以，**永远不要**放前端。
- **如果你把密钥填到了"技能环境变量"，Edge Function 里读不到**，反之亦然——这两套是完全隔离的。
- **写在 SKILL.md / scripts 里的脚本，最终是在秒哒服务器上跑的**，不是在用户浏览器、也不是在你的电脑上。

## 二、"自定义技能"与"自定义插件"的演变

| 时间 | 名称 | 接入方式 |
|---|---|---|
| 2026-02 之前 | 自定义插件 | 在输入框粘贴 API 文档文本 → AI 解析自动配置 |
| 2026-05-10 起 | 自定义技能 | 上传 `.zip` 技能包，根目录含 `SKILL.md`，AI 解析后注册 |
| 2026-07-16 — V3.5 | 自定义技能扩展 | 首页“技能创建”、项目内对话创建/修改、`.zip` / `SKILL.md` 导入，以及 API 文档链接或 API 说明创建 |

2026-05-10 版文档曾明确写过“暂时下架 API 文档链接或 API 说明创建自定义插件”，当时只有 `.zip` 上传这一条路。**该限制已被 V3.5 官方发布文章取代**：2026-07-16 起，秒哒重新支持粘贴 API 文档链接或 API 说明创建技能，也支持直接导入 `SKILL.md`。

因此，旧教程是否可用要按日期判断：2026-05-10 至 V3.5 前，优先走 `.zip`；V3.5 起可按技能复杂度选择对话创建、导入或 API 文档创建。涉及签名、支付、大文件上传等高风险场景，仍优先使用经过本地校验的 `.zip` 技能包，不要只依赖对话生成。

## 三、应用底座是 Supabase 风格

秒哒生成的应用底座有以下确凿迹象：
- 后端用 `Deno.env.get(...)` 读环境变量
- 数据库是 Postgres（通过 `@supabase/supabase-js` 访问）
- API 用 `supabase/functions/<name>/index.ts` 形态
- 异步通知接收端是 Edge Function

**实战意义**：写给秒哒应用后端的参考代码必须是 Deno + Supabase 形态，写 Flask/FastAPI/Express 都会被秒哒"翻译"，翻译过程中很容易引入 bug。

## 四、应用预览域名 ≠ 自定义域名

- 秒哒生成应用后默认给的域名形如 `app-bd0ygtaa9zwh.appmiaoda.com`
- 通过「应用发布 > 自定义域名发布」可以绑到自己的域名
- **YunGouOS / 微信支付的"支付授权目录"配置时，必须填实际访问支付页的那个域名**——绑域名前后是两个不同的值，不能写错

## 五、秒哒 AI 的协作模式

| 特性 | 含义 | 应对 |
|---|---|---|
| 指令式执行 | 发指令后秒哒直接修改代码，没有"先讨论再做"的对话能力 | 提示词必须一次写到位，事后修补成本高 |
| 自由发挥 | 即使你提供了技能/参考代码，它仍可能"自己另写一遍" | 必须在提示词里明确"禁止重写 X"，并指明使用哪个文件 |
| @ 技能调用 | 在输入框 `@技能名 + 自然语言` 是让秒哒明确使用某个技能的标准方式 | 涉及技能的提示词开头必须有 `@<技能名>` |
| 容易丢失上下文 | 改完一处可能忘了另一处保持不变 | 强约束写在提示词最前面（"红线"），不要藏在中段 |

## 六、文档与实现的差异（必记）

秒哒官方文档（2026-05-10 版）描述自定义技能 SKILL.md 时**没有提到 YAML frontmatter 是强制的**，但实际上传时校验会拒绝没有 frontmatter 的 SKILL.md，报错信息是：

> ❌ SKILL.md 格式校验失败：SKILL.md 的内容必须以 "---" 开头

类似的"文档未明说但实际强制"的细节可能还有更多。**永远以实际报错为准，不要相信文档完备**。这也是为什么这套实战经验库存在的价值——补齐文档没写的部分。

## 七、秒哒「后端服务」面板：你能看到的"数据库"

秒哒应用底层确实是 Supabase 风格（Postgres + Edge Functions + Auth），但 **用户没有 Supabase 控制台的访问权**——你拿不到 Project URL、anon key、service_role key、SQL Editor、Logs 这些原生 Supabase 工具。

替代方案是秒哒在应用编辑器侧栏内置的「**后端服务**」面板。它就是用户能看到数据库/后端的**唯一**入口，里面有 4 个 Tab：

| Tab | 作用 | 能做什么 / 不能做什么 |
|---|---|---|
| 数据表管理 | 查看/编辑应用的 Postgres 表 | ✅ 看表结构、看行数据、改字段值、加行；❌ 看不到 SQL Editor、看不到关系图、看不到索引/约束细节 |
| 用户管理 | 应用的用户体系（Supabase Auth） | ✅ 看用户列表、改角色；❌ 看不到 JWT/Session 详情 |
| 后端函数 | Edge Functions 列表 | ✅ 看函数名/源码（有时只读）；❌ **不能直接看到每个函数当前生效的 Secrets**——这是后面坑 #11 的关键 |
| 密钥管理 | 全局 Secrets 配置 | ✅ 增删改全局密钥；❌ 不能查看密钥的当前值（写入后只显示 `••••`） |

### 实战意义

1. **想"对比"是不是新建了字段、有没有遗漏字段、外键有没有连对**——只能通过秒哒「后端服务 > 数据表管理」一张张点开看，没有 schema 总览图。表多以后这是个体力活。
2. **想确认"某个 Edge Function 实际读到的环境变量名"**——后端服务面板**看不到**！只能让秒哒在 Function 里加 `console.log(Object.keys(Deno.env.toObject()))` 打印出来才知道。
3. **想直接执行 SQL 修复脏数据**——做不到。只能让秒哒帮你写一个一次性 Edge Function 跑完即弃，或在「数据表管理」里手工逐行改。
4. **没有 Logs 中心化查看**——前端 console 日志要靠"管理员可见的日志按钮"（见 `prompt-patterns.md` 片段 7），后端 Edge Function 的 console 输出要在秒哒应用编辑器的"调试"按钮里看。

### 给 AI 协作者的实操建议

- 让秒哒做"加字段 / 加表"操作时，**必须明确要求它执行后回贴**当前 schema 字段列表（按表分组），否则你看不到改动结果
- 让秒哒做"修脏数据"操作时，**必须明确要求它先 SELECT 给你看影响范围**（行数 + 样例 5 条），再 UPDATE
- 涉及 Secrets 的事故（环境变量为空、变量名拼错），**别浪费时间猜**——直接让 Edge Function 打印 `Object.keys(Deno.env.toObject())` 一查就清楚（见 [pitfalls.md](./pitfalls.md) #11、#12）

## 八、首轮生成时的三个前置决策

这三件事不要等应用做完后再补救：**应用形态**、**后端存储**和**后端环境模式**。它们看起来像一句提示词里的小词，但实际会决定底层技术栈、数据落点和迭代风险。

### 1. 应用形态：Web / 小程序 / APP 不能后期强转

秒哒首轮生成时要明确选择形态：

| 形态 | 底层技术栈 | 关键后果 |
|---|---|---|
| Web 应用 | React + Vite | 适合网站、后台、工具页，可绑定域名 |
| 微信小程序 | React + Vite + Taro | 走微信小程序发布链路，上传、登录、支付都要按小程序规范 |
| APP | 原生 | 走原生 APP 调试和打包链路 |

**实战判断**：这不是发布时勾选一下渠道的问题，而是生成时的架构选择。Web 项目后期强行改小程序、网站改 APP、小程序改 PC 后台，都容易出现编译产出为空、无法发布到目标渠道、运行能力不匹配等问题。需要小程序就首轮写清楚“做微信小程序”，最好直接使用秒哒界面的「做小程序」入口。

### 2. 后端存储：不明说就可能只是浏览器缓存

秒哒能生成后端数据库，但**不等于每个应用默认都有真正后端存储**。如果需求里没有明确“后端存储 / 数据库 / 数据表 / 云端保存”，模型可能用浏览器缓存或本地状态实现，看起来能保存，换浏览器、无痕模式或换设备后数据就丢。

验证方法：

1. 在应用里录入一条测试数据。
2. 关闭当前浏览器，改用无痕窗口或另一台设备登录。
3. 还能看到数据，才说明后端存储真正生成；看不到就是本地缓存。

首轮提示词建议直接写：

```text
本应用需要真实后端数据库存储，不允许只用浏览器缓存或 localStorage。
请生成必要的数据表，并提供数据的增删改查能力。
同时生成管理员可用的数据查看维护页面，方便后续导出和人工维护。
```

如果应用已经生成但发现没有数据库，可以二次补救：

```text
请基于当前应用补充真实后端数据库存储功能，并把现有浏览器缓存/本地状态保存的数据逻辑迁移为后端数据库读写。
请补充数据的增删改查操作，并基于现有表结构生成管理员可用的数据查看维护页面。
完成后请按表回贴字段列表，并说明我应该如何用无痕窗口验证数据持久化。
```

### 3. 后端环境：单环境 / 多环境要在创建时选清楚

秒哒 V3.5 支持在创建应用时选择单环境或多环境：

| 模式 | 数据库与后端 | 适用场景 |
|---|---|---|
| 单环境 | 开发与线上共用同一套数据库和后端资源，开发改动会直接影响线上 | Demo、原型验证、个人轻量工具 |
| 多环境 | 开发环境和线上环境隔离，通过发布流程把数据结构变更合入线上 | 正式上线项目、团队协作、持续迭代、企业管理系统 |

多环境下，发布合入遇到 Migration 冲突、SQL 报错或存储不兼容时，V3.5 提供免费的 AI 修复入口；版本变更还会记录 Schema 与数据快照，用于回滚。文章只确认了“多环境可切回单环境”，没有确认单环境能否无损切换为多环境，因此不要对既有单环境正式项目擅自承诺可原地升级。

## 九、多应用共享后端（2026.07.16 — V3.5）

> 来源：[秒哒 3.5 官方发布文章](https://mp.weixin.qq.com/s/y2_ip4MYlJQPpTJ2a_O26A?scene=1)。

同一个业务需要 Web、APP、小程序、用户端、商家后台等多个入口时，V3.5 支持这些应用复用同一套数据库、接口和存储。各端的前端页面可以独立设计和迭代，数据则统一管理。

实操边界：

- 这是“多个应用共用一套后端”，不是把一个 Web 项目强行转换成小程序或 APP；各终端仍应按各自应用形态创建
- 创建新终端时，应明确选择已有项目作为共享后端，并要求秒哒回贴复用的数据库、接口、存储范围
- 共享后端会扩大变更影响范围。改表、改鉴权、改接口前，要列出受影响的全部终端，并优先在多环境的开发库验证
- 对于支付、登录、设备权限等渠道差异很大的能力，仍按各终端独立实现，不要因为共享后端就复用前端逻辑

## 十、后端资源分级（2026.07.16 — V3.5）

> 来源：[秒哒 3.5 官方发布文章](https://mp.weixin.qq.com/s/y2_ip4MYlJQPpTJ2a_O26A?scene=1)。

V3.5 提供基础版、小容量、中容量、大容量、超大容量等后端资源规格，涉及并发、数据库存储和文件存储；支持随业务增长升级，并提供使用量可视化与临近上限提醒。

2026-07-15 后端能力与计费调整公告补充了基础版额度：

| 套餐 | 并发 | 数据库存储 | 对象存储 |
|---|---:|---:|---:|
| 基础版（免费） | 10 | 1GB | 200MB |

公告没有披露其他档位的完整额度和价格。建委 2026-07-19 在当前产品界面观察到最高对象存储档位为 10GB；该数字属于当前界面信息，后续做预算仍要以购买页实时显示为准。

同一公告还写明“取消应用内 50MB 文件上传上限限制，支持更大的文件处理能力”。这只证明旧的 50MB 产品限制已被取消，**不能直接推出 200MB 文件一定能单请求上传成功**。新的单文件上限、请求体上限、CORS、Edge Function 内存/时长和网关 413 状态均未公布。新项目应先用 200MB 测试文件验证，再决定上传架构；旧的永久分片 + Range 代理方案已降级为兼容兜底，见 [patterns/large-video-upload.md](./patterns/large-video-upload.md)。

选型时先按并发、数据量、文件量和可接受成本做预估，不要因为能弹性扩容就忽略容量监控。

## 十一、快速 / 深度模式计费（2026.07.15 调整）

> 来源：建委 2026-07-19 提供的“秒哒产品能力升级及计费规则调整公告”截图。

| 模式 / 操作 | 秒点 | 适用场景 |
|---|---:|---|
| 快速模式 | 10 秒点/次 | 查询、轻量生成 |
| 深度模式 | 40 秒点/次 | 调用更多模型资源和 Tokens，复杂分析与推理 |
| 源码下载（2026-07-16 凌晨起，以实际更新时间为准） | 深度模式 30 秒点/次 | 项目代码整理、依赖处理、资源打包、文件生成；原为 40 秒点/次 |

公告只给出单次秒点消耗，没有给出秒点对应的现金价格。核算实际人民币成本时，应同时查看会员套餐、秒点购买价和是否存在赠送额度。

## 十二、定时任务能力（2026.07.08 更新速报）

> 来源：建委 2026-07-09 提供的"秒哒 7.8 更新速报"。截至 2026-07-09，官方 26 年更新日志尚未收录本节点，底层实现细节待官方文档确认。

2026.07.08 速报显示，秒哒生成应用已支持为已有应用增加定时任务。用户可以用自然语言描述固定时间或周期任务（每日 / 每周 / 每月 / 每小时等），例如定时同步数据、发送通知、每小时统计社区热门帖子并更新热榜。

实操判断：

- 这是**应用层能力**，不是自定义技能本身的定时执行；后续遇到"定时同步 / 定时统计 / 定时发送 / 周期更新"类需求，应优先考虑让秒哒在应用内生成定时任务
- 提示词里要写清：任务名称、触发频率、处理对象、写入位置、运行记录查看方式、失败后的预期处理
- 在官方文档补齐前，不要臆测底层是不是 cron、队列、Edge Function 调度或某个固定 API；只写产品层需求和验收标准
- 验收时应要求秒哒说明可视化面板入口，并提供最近一次运行记录 / 状态 / 错误信息的查看路径

示例提示词：

```text
请在当前内容社区应用中新增一个定时任务：每小时统计一次热门帖子，并更新热榜。
统计规则：优先按过去 24 小时内的评论数、点赞数和浏览量综合排序。
请同时生成一个管理员可查看的任务运行记录面板，至少展示任务名称、最近运行时间、运行状态、处理帖子数量和错误信息。
完成后请回贴定时任务的触发频率、更新的数据表/字段，以及我应该在哪里查看运行记录。
```
