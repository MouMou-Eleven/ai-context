# 用读者真正关心的问题组织宣传内容

状态：建委明确认可并要求复用；确认日期：2026-09-13。主归属：自媒体与个人IP经营／营销文案。已验证的是本次介绍页的清晰度与建委认可，尚无咨询量、报名率或跨项目效果数据。

## 何时调用

写产品介绍、会员社群宣传、报名详情页，或需要解释产品与回应购买顾虑的推广文章、口播和直播话术时，先读本方法，再按渠道调整篇幅。用户无需指定本文件名；相关任务从[自媒体入口](../README.md)或[营销入口](./README.md)进入即可。

纯教学课件、知识科普、个人随笔、内部复盘不默认使用招生问答。提到课程不代表正在授课；宣传的接收者是考虑报名的人，课堂资料的接收者是正在学习的人。讲师要拿着讲，也不能把宣传成品写成给讲师看的操作说明。

## 核心方法

先确定读者做决定前真正需要知道什么，再用问题组织内容。问号只是形式；每一问要有实际关切，每一答要补齐判断依据。不能把内部框架名称改成疑问句，就称为读者视角。

制作前按[执行与验收](../../../../system/repository/execution-checks.md)在任务工作区保存一张简表：`读者问题 → 为什么现在会问 → 答案与事实来源 → 在成品中的位置`。这是AI内部检查材料，不放进宣传正文，不要求建委先替AI列问题。

1. **从真实关切找问题。** 优先用建委明确反馈、用户咨询、既有认可稿。没有咨询记录的候选问题要标明推断，不编造“学员普遍反馈”。判断它是否影响读者理解产品、判断适合度、决定投入或完成报名。
2. **按理解顺序组织。** 先讲能获得什么、整体包含什么；再展开当前具体内容；随后回答替代方案、支持、可信度、价格权益与个人顾虑，最后给出报名方式。根据产品和渠道调整，不机械套八段或强行制造焦虑。
3. **让下一问承接上一答。** 总览已提到AI编程，下一问自然是“具体包括什么”；答案要进一步展开，不能再复述总览。FAQ补充剩余顾虑，不重复正文。
4. **答案直接回应问题。** 开头先给明确答案，再解释组成、实际用途、案例和必要条件。读者看完这一段应能说出获得了什么信息，不能只有“赋能、体系、价值”等抽象判断。
5. **用困难解释框架。** 如需介绍四类内容，分别说明它解决哪个阶段的问题。名称可保留，但不能让读者自己猜“这块有什么用”。
6. **保留事实状态。** 已发布、部分可看、后续计划分开；价格、会员期限、答疑范围等回对应项目的当前事实核对。不从一份旧样稿照搬权益，不把“适合零基础”变成保证学会、保证收入。
7. **适配渠道。** 完整详情页可以系统展开；短文章、朋友圈或口播只选择本条最需要回答的问题，详情以链接承接。线下讲解也沿问题解释，不输出“此处停顿、讲师引导购买”等内部指令。

8. **自然表达，按内容区别处理。** 解释要能直接说出口，零基础问题用具体动作和直观例子回答，不用“工具环境、协作方法”等目录语言。讲师区用姓名、专业头衔和可核实背书，不能为了口语化改成“我平时主要做……”的闲聊。需要严谨的服务条件仍写准确。
9. **局部改稿先对齐整篇人称。** 改写某一问或某一节之前，先读取相邻章节，确认正文是在直接对读者说话，还是在第三人称介绍受众。已有介绍页以“你”为主时，新段落继续用“你”；需要同时面向多人时可以用“大家”，不能突然改成“成员”或“学员”。“成员／学员”适合内部规则、受众分类或第三人称事实描述，不应混入直接对读者说话的连续正文。这里要求的是上下文一致，不是让所有项目机械使用同一代称。

内部保持承诺与证据检查；宣传正文不主动增加“学完能赚钱吗”及整段免责FAQ。建委已明确否定本次无关声明。用户确实询问结果、产品本身涉及该承诺，或有必要说明实际交易条件时如实回答，不能以删除声明为理由制造收益保证。

## 认可稿怎样把内容讲清楚

本次[会员社群最终介绍页](https://hv21wf9uao9.feishu.cn/wiki/R9Gsw9KVuiLEppklfqHc1DuMnMg)于2026-09-13读取 revision 228。下表是对结构的分析；只用于学习组织方法，产品现状以[社群README](../../../projects/paid-community-course/README.md)为准。

| 读者问题与顺序 | 该段实际承担的解释 |
|---|---|
| 加入能获得什么 | 先建立与自己的工作、项目和能力扩展的关系 |
| 社群具体包含哪些内容 | 区分整个社群与当前AI编程内容，区分现有与后续 |
| 现阶段AI编程具体包括什么 | 展开系统课、场景实战、内部资料、工具专题 |
| 有免费教程为什么还加入 | 解释学习衔接、实际项目经验和持续答疑，不笼统贬低免费内容 |
| 已经能问AI，为什么还需要答疑 | 回应不会定位问题、不会提问、无法判断方案的实际困难 |
| 谁来讲、价格与权益是什么 | 用可核实经历和明确服务范围支持判断 |
| 零基础／已有基础／赶不上直播怎么办 | 分别回答适合度、已有内容与补学方式 |
| 如何报名 | 说明实际购买和入群路径，不以空泛口号结束 |

第二层没有只堆四个内容名称，而是将它们放回读者的学习处境：

| 处境 | 对应内容 | 回答必须讲清 |
|---|---|---|
| 没有基础，不知从哪里开始 | 系统课程 | 起点、要完成什么、基本过程 |
| 学过知识，不会用在具体需求 | 场景实战 | 一个需求中工具怎样配合、操作怎样衔接 |
| 能做了，但反复试错、效率低 | 内部资料 | 哪类经验可以直接参考，解决什么困难 |
| 工具更新快，不知道怎样跟进 | 工具专题 | 哪些新能力值得学，适用于什么任务 |

这些分类属于本次产品说明，不要求其他产品也分四类。

## 真实改稿中为什么前几版仍失败

已读取建委补充的Codex对话 `01a09629-6cfb-7f91-a95c-cd89a7378e26` 的全部7轮用户反馈及各轮交付说明，并核对最终飞书正文。

| 已观察的偏差 | 建委的纠正 | 后续执行约束 |
|---|---|---|
| 在原有四阶段、逐课拆解上继续整理 | 宣传要讲课程最终能做什么，详细逐课目录另看 | 不因旧稿已有结构就沿用；把本轮新目标落实到信息顺序 |
| 以剪辑工作流和游戏开发代表全部实战范围 | 两者只是帮助理解的例子 | 案例说明用途，不将举例变成产品范围限制 |
| 按模块逐个说明，仍像知识库或课程手册 | 说清每类内容为何存在、解决什么问题 | 模块名称与用户困难、实际用途一一对应 |
| 改成问答后，开头问“你想做的事，能不能不再卡在‘我不会’这一步？” | 改为“加入社群，你能够获得什么？”，随后讲整体内容与当前编程内容 | 不能用情绪化提问替代读者要了解的产品信息 |
| 讲师区泛讲平时做什么 | 姓名、头衔、实际获奖与背书直接呈现 | 专业证明与自然解释分工，不把所有段落口水化 |

上述旧开头可在原任务 `output/community-benefits-rebuild.xml` 核对；最后的问题顺序在 `output/community-user-question-order.xml` 及最终页核对。旧稿只用于失败对照，不再作为当前写作模板。用户曾先要求保留标红与加粗，后明确授权重组这些内容：这是该次编辑的授权变化，不能推为以后可任意覆盖用户编辑。

## 写完怎样判断真的遵循了

逐段回读实际正文，不能只检查标题是否有问号：

| 检查 | 不合格信号 | 修改动作 |
|---|---|---|
| 读者是否真需要这一问 | 只问内部如何构建体系，却未解释买到什么 | 回到读者的获得、顾虑和决定，删除无实际作用的问题 |
| 答案是否回答标题 | 问包含什么，答“持续赋能成长” | 写清具体内容、服务及可核实状态 |
| 顺序是否自然 | 还没介绍社群，就开始列工具参数 | 先总览，再展开当前部分，再回应顾虑 |
| 框架是否讲透 | 只有四个栏目名称，没有用途 | 将每类内容对应到真实困难和使用场景 |
| 受众是否走偏 | 写“讲师此时解释”“先引导用户认识价值” | 改成直接给读者的解释；内部安排留工作区 |
| 人称是否与上下文一致 | 相邻段落一直称“你”，局部改稿突然称“成员／学员” | 沿用正文的“你”；需要群体指代时用“大家”，内部分类名称留在内部记录 |
| 事实是否可靠 | 将“后续逐步补充”写成已可学习 | 按当前项目来源恢复已发布／部分／计划边界 |
| 是否只是凑FAQ | 删除某问完全不影响理解或决策 | 删除、合并，或补真正缺失的关切 |

例如，候选“我们的四维赋能体系如何构建？”和回答“形成完整成长闭环”，即使没有禁词脚本命中，也没有讲明读者能得到什么，应退回。改为“现阶段的AI编程内容具体包括什么？”，再解释各类内容、用途和实际状态，才是遵循。本例为复核示例，并非原对话逐字引述。

对零基础的回答要解释从哪里开始、如何操作和得到什么支持，不用一句“都能学会”替代。对已会AI的人说明可参考的项目经验与专题，不能承诺对所有人都有同等价值。
