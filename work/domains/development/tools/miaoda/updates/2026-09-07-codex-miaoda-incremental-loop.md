# 2026-09-07：Codex × 秒哒版本化增量迭代闭环

## 背景

建委确认“秒哒开发 → Codex查看和审查 → 生成带版本号增量包 → 上传执行 → 线上反馈 → 下一轮修复”是长期项目的高效协作方式，需要沉淀为 AI 编程板块中的通用经验。

## 本次修订

新增 [`../experience/patterns/codex-miaoda-iterative-increment-workflow.md`](../experience/patterns/codex-miaoda-iterative-increment-workflow.md)，统一记录：

- 版本号、包名、manifest、字节数和 SHA-256 规则；
- Codex、用户和秒哒的职责边界；
- 本地源码修复、构建、增量打包、秒哒校验、部署和反馈回传流程；
- 数据库迁移、前后端字段矩阵、权限和预览一致性要求；
- 视频、图片、附件和静态资源的线上验收；
- 正式域名 release manifest、`data-release`、CDN URL 和真实浏览器 DOM 验证；
- 对抗式审查、回滚、失败状态和可直接复用的秒哒提示词模板。

## 这次暴露的不足

此前资料分别记录了云端分批提示词和本地源码分包，但没有把两条路径统一到“版本基线 → 包校验 → 可回滚合并 → 构建 → 正式域名验收 → 反馈闭环”。R6/R7/R8 的核验尤其表明，秒哒执行或构建回执不代表正式域名已经切换到新资源。因此今后的“完成”必须区分：已生成、已上传、已合并、已构建、已部署、已通过正式域名验收。

## 长期口径

1. 每个交付物都有唯一版本，不能使用“最终包”这类不可追踪名称。
2. 没有 manifest、哈希、迁移说明和回滚方案的增量包不视为可交付。
3. 不能只信秒哒摘要，必须核对正式域名的版本标记、资源 URL、真实 DOM、网络和权限行为。
4. 发现未切换、缓存、迁移或资源闭包问题时，先分类根因，再进入下一轮；不得覆盖历史状态。
5. 这一流程适用于百度秒哒，不得与飞书妙搭的发布链路混用。
