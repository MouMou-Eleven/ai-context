# AI × 秒哒协作方法

建委做秒哒项目的核心方法：**AI（Codex、Claude Code 等，不限哪个）在本地开发、测试、打包；包上传给秒哒（建委手动上传，或建委明确要求时由 AI 用 Ego 浏览器自动上传）；秒哒负责云端存储、数据库、构建；点“发布”后线上才更新；再按线上结果验收，有问题就描述、改、出下一个增量包，循环到没问题为止。** 本页是这套方法的唯一正文，按阶段组织。遇到具体问题（上传、登录、支付、SEO、排错）时，再查 [topics/](./topics/README.md) 里对应的专题。

> 来源：混世魔牛游戏（2026-08）、建委个人网站 R6~R8（2026-09）、言剪 AI B1~B8（2026-09）、德锦周锦网站整改（2026-06）等实战。当前限额见[事实表](./facts.md)。

## 先选路径

| 当前状态 | 走哪条 | 从哪个阶段开始 |
|---|---|---|
| 新项目，准备在本地用 AI 开发 | **A. 首次全量交付** | 第 1 阶段 |
| 已经有本地源码基线，继续迭代或修问题 | **B. 增量迭代** | 第 5 阶段 |
| 项目是在秒哒里原生生成的，建委下载了源码交给 AI 检查 | **B. 增量迭代**（以下载的源码为基线） | 第 5 阶段，先做下方"把下载的源码变成基线" |
| 项目只在秒哒云端，建委只发截图或报错，要 AI 写提示词 | **C. 纯提示词协作** | 见本页末尾"路径 C" |

**把下载的源码变成基线**：下载源码要高级版及以上，每次 300 秒点（见[事实表](./facts.md)），所以只下载一次，之后靠增量包和回执维护本地源码。拿到 ZIP 后记录它的 SHA-256、下载时的秒哒版本号，写进 manifest 的 `baseSource`；先在本地装依赖、构建跑通，再开始改。下载的源码不一定包含线上真实的表结构，涉及数据库的改动先按[数据库专题](./topics/backend-storage.md#四增量包里的数据库迁移路径-b)把字段列表要回来。

**默认**：有本地源码的项目，一律在本地改好、按约定格式打成 ZIP 包上传给秒哒部署（路径 A 或 B），不改成只给秒哒发提示词、让它自己改代码（路径 C）。暂时拿不到云端最新改动时，先把缺的那几个文件或哈希要回来，其他不冲突的工作继续做。为什么：秒哒自由改代码会和本地源码分叉，下一次打包就会把它的改动覆盖掉，或者被它覆盖。

## 一轮迭代长什么样（默认）

1. **首次：本地开发完整版 → 打全量包上传。** 本地开发到差不多，按[第 4 阶段](#第-4-阶段分包上传先校验再创作路径-a)打包：每个包不超过 20MB（建议小于 19,000,000 字节），总量大就拆成几个（例如 40MB 拆两个），按上传顺序编号；一条对话消息最多 5 个包，超过就分几条发。
2. **之后每一轮：描述问题 → AI 本地修改 → 出增量包 → 上传到秒哒对话框并附执行提示词 → 秒哒修改 → 点“发布” → 线上测试。** 有问题就描述新问题，进入下一轮；没问题这一版就结束。

谁来上传、发布、验收，看建委这次的说法：

| 建委这次怎么说 | 走哪种 | AI 交出什么、做到哪一步 |
|---|---|---|
| 没提浏览器，只说改问题、出包（默认） | **手动** | 增量包、要粘贴给秒哒的执行提示词、验收清单（见[第 7 阶段](#第-7-阶段打增量包路径-b)）。建委上传、发送、点发布、测试，再把新问题描述给 AI |
| 明确说用 Ego 浏览器自动上传、验收、发布、迭代 | **自动闭环** | AI 自己跑完下面的循环，每轮结束给建委一段简报 |

**自动闭环怎么跑**（建委明确要求时才用）：

1. 浏览器只用 Ego，接管建委已登录的“秒哒登录”空间，从中选目标项目（见[本机浏览器调用约定](../../../../../system/environment/computers/desktop-1/README.md#浏览器调用约定2026-11-05建委明确要求)）。
2. 本地改好、测完、干净复建通过后，先看包里有没有删列、删表、改名、清数据的迁移：有就停下找建委（单环境应用一执行迁移就改到线上库，等回执再停已经晚了）。没有就在秒哒对话框上传增量包，粘贴执行提示词并发送；等秒哒这一轮结束（回执出现终态）再动，不在它执行中追加命令。
3. 读回执：秒哒报云端版本和基线不一致、或云端有别人改过的文件，停下找建委，不整文件覆盖；校验、构建、迁移任何一步失败，回到本地修，不点发布（迁移失败时说明可能已部分写进线上库）。
4. 回执正常就点“发布”，等发布完成。
5. 按验收清单在线上逐项实测（[第 9 阶段](#第-9-阶段线上真实验收路径-b)：版本标记、真实页面、手机宽度、游客和管理员），截图留证。
6. 有问题：记进同一张问题清单（原编号不换），回到本地修，出下一个增量包，回到第 2 步；全部通过就停。
7. 每轮结束给建委一段简报：这轮改了什么、包名、秒哒版本、发布结果、验收通过和没通过的项；没实测的写“未验”，不写“已通过”。

**自动闭环里遇到这些，停下来找建委，不自己往下做**：数据库迁移要删列、删表、改名、清数据（见[第 7 阶段](#第-7-阶段打增量包路径-b)）；要真实付款、真实短信或实名；要花秒哒点数的操作（如下载源码，见[事实表](./facts.md)）；登录失效要重新扫码；Ego 连接断开或建委接管浏览器（按 Ego 技能的停止与恢复流程）；同一个问题修了两轮还在（按[修到第二次停下来换路](../../experience/delivery-and-testing.md#同一类问题修到第二次还冒新的停下来换路默认)先换思路，跟建委说一声）。

为什么分两种：自动闭环把建委从“上传、点发布、验收、描述问题”里解放出来，但它会改线上网站，所以只在建委明确说了的时候用；没说就按手动，把包交给建委。

## 三方分工

| 角色 | 负责 | 不负责 |
|---|---|---|
| 建委 | 描述问题；手动方式下上传包、点发布、在线上页面验收、回传截图和秒哒回执 | 不用自己设计技术方案；自动闭环时只看每轮简报和需要他决定的事 |
| AI | 读仓库经验、改本地源码、测试、打包、写秒哒提示词和验收清单、审查回执；自动闭环时还用 Ego 上传、点发布、线上验收 | 不假装能直接访问秒哒云端源码或数据库 |
| 秒哒 | 接收校验、合并代码、执行数据库迁移、构建、部署、回报结果 | 不负责跨轮记忆和版本管理；它说"构建成功"不等于线上已经对了 |

## 第 1 阶段：开工前定三件事（路径 A）

这三件事秒哒生成后很难改，第一次就要说清楚。详见[平台基础 · 首轮决策](./basics/platform-basics.md)。

1. **应用形态**：Web、小程序还是 APP。后期强转容易出空产物。
2. **后端存储**：明确要真实数据库，不说就可能只存在浏览器缓存里。
3. **环境**：单环境还是多环境。单环境下编辑器里改库就是改线上；要正式上线、长期迭代的，创建时就开多环境（需要高级版及以上，之后也能切换）。区别见[数据库专题](./topics/backend-storage.md)。

## 第 2 阶段：本地开发和验收（路径 A）

AI 交付前至少做到：

1. 读项目 README、现有测试、素材清单。
2. 不删建委没授权删的源码、素材、功能。
3. 跑现有测试和生产构建。本地构建按项目锁文件执行，不要重新解析依赖。上传给秒哒的包要另外满足秒哒发布时的构建方式（`pnpm install && npx vite build`，见[踩坑 #27](./pitfalls.md#27-上传源码与秒哒云端构建环境不一致--本地能构建发布时装依赖或构建失败)）：不写 `packageManager`、带空插件的 `postcss.config.js`；平台模板自带的构建文件不要求删除。
4. 用真实浏览器看桌面和手机：控制台、网络请求、布局、点击、触控、声音。
5. 游戏、3D、视频项目另查帧率、纹理内存、预加载、页面隐藏时是否暂停。

## 第 3 阶段：统一技术栈，做运行时闭包（路径 A）

**默认**：秒哒 Web 应用是 **React + Vite**，产物是 `dist/`。不能用 Next.js、SSR、Next API Routes，也不能用必须常驻 Node 服务才能打开的方案。Vercel、Cloudflare 的专用配置不带过去。

只交付运行时真正用到的文件：

- 保留：源码、锁文件、运行时引用的素材、必要的配置样例（`.env.example`）
- 排除：`node_modules`、`dist`、日志、截图、缓存、密钥、原始母版、没引用的素材、本机部署配置

不要把整个工作目录直接压缩。

## 第 4 阶段：分包、上传、先校验再创作（路径 A）

**分包**：对话附件一次最多 5 个、每个 20MB（见[事实表](./facts.md)），单包建议小于 19,000,000 字节。**包内文件名只用英文、数字、短横线**（默认）：2026-10-22 秒哒解压时把 3 个中文文件名解成乱码，虽然它自己重解成功，但会多一轮核对；中文文档改成 `architecture.md` 这类名字，中文标题写在文件里。每个包编号（01、02……），附一份清单：每个文件的路径、字节数、SHA-256。给建委的上传文件夹按上传顺序编号，每个文件夹最多放 5 个包，对应一条对话消息。超过 5 个包就分几条消息发，前面每条都只接收不创作，全部收齐后再发创作提示词。

**附件说“没收到”时先拆小包**（默认）：秒哒回复“压缩包未落盘、请重新上传”，而界面上附件明明显示已附加时，先看包的大小。2026-11-28 言剪 B28 的单包 552,870 字节连传三次都没落盘（消息里有附件路径、沙箱里没有文件），之前 39 万字节以内的包都能一次或重传一次就成功；拆成服务端包（374KB）和前端包（182KB）两个分包、每个都带同一份清单、提示词写明“两个分包解压到同一目录正好是清单里的全部文件”，一次就收到。这和上面的 20MB 上限不矛盾：20MB 是平台写的上限，实际在约 500KB 以上就可能失败，原因不明。所以同一个包重传一次仍没收到时，不要再原样重传，直接拆成每个 40 万字节以内的分包。

**打完包自己先复建一次**：在另一个干净目录把所有包解压，重新安装、测试、构建。通过了才交付。

**上传分两步，不要一步到位：**

1. **只接收**：第一条提示词要求秒哒只解压、核对文件数和哈希，缺文件或哈希不对就停下报告，**不准开始生成页面，不准用占位图补缺失素材**。
2. **确认齐全后再创作**：再发一条提示词，重新声明技术栈、禁止修改的范围、素材映射、测试和构建要求。

首次全量交付的最后一句**必须**是：

```text
严格依照上传的源码，然后给我生成网页应用，给我生成产品需求文档，并立即开始创作。
```

只说"生成网页应用"时，秒哒可能跳过产品需求文档（PRD）。

**多个应用共享一个后端**（如用户端 + 管理后台）：把后端（表、函数、迁移）只放在第一个应用的包里，第二个应用的包只有前端；先完整部署、发布第一个，再在首页点「共享后端」创建第二个。第二个应用上传自定义源码时连接配置没注入的问题和提示词写法见[踩坑 #31](./pitfalls.md#31-共享后端的第二个应用上传的自定义源码没拿到后端连接配置)，完整实例见[本命音律案例](./topics/case-benming-shared-backend.md)。

**素材进对象存储**：压缩包不是线上地址。图片、音频、视频、模型要解压进秒哒对象存储，并让秒哒回报"原路径 → 对象键 → HTTPS 地址 → SHA-256"的映射。视频要支持 Range（能拖动），不要用 Base64 或临时 Blob 地址。

**数据库**：只存需要查询、权限、跨设备保存的业务数据（用户、订单、存档、后台内容），不把图片视频塞进表里。要求秒哒回报表结构和权限规则，并用无痕窗口或另一台设备验证数据确实存在云端。不需要登录和存档的项目，不要为了显得完整硬加数据库。建库提示词和验收见[数据库专题](./topics/backend-storage.md)。

完整的首次交付提示词模板见 [prompt-templates.md](./prompt-templates.md#首次全量交付)。

## 第 5 阶段：每轮开始先读执行卡（路径 B）

每个项目在自己的 README 或状态记录里维护一张执行卡。每轮开始、长任务恢复、交付前都先读它，不要只盯着最后一条报错继续做。**默认**：同时确认唯一项目根目录及当前可编辑源码树；增量包、隔离复建、测试和临时文件都在该根目录内分类存放，不能因换了 AI 对话就在新 cwd 另建完整项目。原平台本地版、当前秒哒版和历史恢复包分别标注，版本号不能从文件夹的“最新”二字推断。

| 执行卡字段 | 用途 |
|---|---|
| 本轮目标、验收标准、明确不做的 | 确认还是建委的最新要求 |
| 应用、环境、基线版本、本批版本 | 不把预览当生产，不拿旧包覆盖云端改动 |
| 当前阶段和上一轮结果 | 执行中不发下一条命令；取消了不自动重发 |
| 未解决的问题、需要的证据、谁来提供 | 每个问题保留编号，直到验收通过 |
| 已验证和未验证的 | 本地测试、秒哒回执、线上实测分开写 |

进入技术细节前，先判断它是否阻塞本轮验收；不阻塞的记进问题清单，不顺手扩大改动。同一个错误重复出现、又没有新证据时，停止重试，先去拿缺的日志、源码或环境信息。

### 云端改过代码，先对齐基线再制包（默认）

触发条件：继续上一轮秒哒增量、换对话接手、云端热修或新增过能力、预检报差异，或者上轮只拿到“构建成功”的文字回执。先核对下面的事实，再修改本轮代码：

1. **分开记录三种版本。** 执行卡分别填前端发布标识、工作区源码清单、实际后端部署输入。页面显示上一轮版本，只说明前端标识；编辑器源码与已部署 Edge 无法逐字核实时，明确保留这个缺口，并安排部署后成功路径验收。
2. **先比较原字节，再决定要不要取源码。** 用上一轮保存的实际文件路径、字节数和完整 SHA-256 对照本地基线，逐项填“相同／已回收合并／明确原地保留／待回收”。发生未知差异的被覆盖文件、部署依赖或数据库函数，不得进入可执行交付包；其他不冲突的实现可以继续。
3. **要回的是可合并材料。** 差异文件必须有完整原始源码和相对导入的传递依赖；数据库要有实际函数定义、签名、所有者、权限、安全属性、易变性、search_path及相关表结构。哈希只用于核对，不能还原代码。优先让秒哒只读导出这个有限范围，不默认让用户付费下载全量源码。导出器先逐类小样查询，核对退出码、错误正文和机器可读结果，再批量运行；语法错误先修查询，明确限流才退避重试，失败不能被解析成“对象不存在”或空文件。交接清单须在排除辅助文件之后生成，与 ZIP 实际成员集合、字节数和哈希逐项一致；缺文件要分清是运行依赖、数据库定义还是导出辅助工具，不照抄总数宣布齐全。
4. **用三份材料合并。** 共同旧基线、云端现行源码、本轮修改分别冻结，逐段判断变化来源，保留云端已经提供的功能、权限和资源约定，再叠加新需求。不能只改 manifest 的基线哈希让预检放行，也不能用“官方干净版”整文件覆盖带有真实业务改动的版本。
5. **测试也要换基线。** 从回收材料生成本轮夹具和依赖清单，比较合并前后的工具、路由、管理目标和上传通道，原能力无授权删除时不能减少。至少走通一条保留能力的成功流程，以及权限拒绝、失败重试和重复请求；涉及数据库时实际执行该基线的函数与迁移。只在原本地夹具上把新功能测通，发现不了云端能力被删。

例如：预约应用在秒哒增加了附件直传，本地只知道旧表单。下一包要改消息提醒时，应先回收附件接口及存储依赖，把附件上传、回读和权限列为保留项，再合并提醒功能；前端版本相同、旧表单测试通过，都不能代替这条验证。反例与本单来源见本页末尾。

## 第 6 阶段：在本地修改和测试（路径 B）

**默认**：先确认实际运行入口与构建链，记录源码目录、构建脚本/配置、产物目录、托管目录与根 HTML 引用。根类型检查必须核对覆盖范围，覆盖不到本轮改动就追加对应检查；根 build 为提示脚本或嵌套 build 为 Next 时，不能替代秒哒实际 Vite 构建。相关检查串行执行，保留完整退出码，失败不继续发布。详情见[构建与入口诊断](./topics/runtime-diagnostics.md#源码改了但页面没变先核对构建和入口)。

加功能、改功能、加一种类型或页面时，开工前先找同级参照、列影响面清单，交付前按清单用同一条记录走一遍，见[加功能、改功能](../../experience/delivery-and-testing.md#加功能改功能先列影响面新界面沿用同级的旧样式默认)。

前后端不一致（后台能录、前台不显示）也按同一节的字段逐段对照查。

**默认**：接入新的开源工具或音视频能力，先按[平台基础的执行位置检查](./basics/platform-basics.md#引入-ffmpeg浏览器渲染器或-github-项目前怎么选)拆清浏览器、Edge 和独立 Worker。安装依赖和构建成功不能替代生产运行验证。公开页面的 403 先按[来源校验与业务权限](./topics/runtime-diagnostics.md#预览域名请求被拒绝时先分清来源校验和业务权限)排查；不要用放宽登录或数据库权限修复域名遗漏。

每个涉及登录、存储、支付或外部接口的增量包，另外检查：

1. 从前端源码列出所有 `import.meta.env.VITE_*`，和 `.env.example`、秒哒构建脚本逐项对照，漏一个就停。
2. 分别测 200、空返回、非 JSON 错误、超时、配置缺失。配置缺失不能被笼统报成"网络异常"。
3. 传给数据库的值用数据库同样的规则（正则、枚举、长度）做断言，至少有一项测试真实执行 SQL，而不是用替身假装成功。
4. 项目使用浏览器持久登录时，除新鲜会话外，验证临近过期、慢刷新、同源多标签页和后台恢复；监听未处理异常并检查加载态恢复。遇到锁抢占按[认证锁竞争专题](./topics/authentication.md#会话刷新与浏览器锁竞争)核对实际SDK与调用链，不用关闭锁或全局吞错通过验收。

来源：[踩坑 #29](./pitfalls.md#29-增量包修复了业务代码却漏掉云端构建变量且跨层假数据掩盖格式错误)。

## 第 7 阶段：打增量包（路径 B）

**命名**：`<项目>-JW-YYYYMMDD-R<序号>-<主题>-v<格式版本>.zip`，例如 `jianwei-JW-20260906-R8-dynamic-types-increment-v4.zip`。序号只增不减，不用"最新版""最终包"这种名字。

**包里放**：本轮改动的文件（相对路径）、`MIAODA-PACKAGE-MANIFEST-<版本>.json`、变更说明和禁止修改的范围、数据库迁移脚本或"无需迁移"、秒哒执行提示词、回滚说明。

manifest 记录每个文件的路径、字节数、SHA-256，以及基线：

```json
{
  "version": "JW-20260906-R8",
  "baseVersion": "JW-20260906-R7",
  "baseSource": {"kind": "git-commit-or-full-archive", "reference": "<commit或存档路径>", "sha256": "<存档哈希>"},
  "package": "jianwei-JW-20260906-R8-dynamic-types-increment-v4.zip",
  "files": [{"path": "src/pages/Admin/Works.tsx", "bytes": 12345, "sha256": "..."}],
  "databaseMigration": "required|not-required|manual-review",
  "createdAt": "2026-09-07"
}
```

**基线哈希用原始字节，打包统一 LF**（默认）：manifest 里记录的被覆盖文件原哈希，必须是云端文件原样字节的 SHA-256，按换行归一后再算会让秒哒预检误判"云端已被改过"。2026-10-22 本命音律下载的源码里有 16 个 CRLF 文件，核对后全部来自我们首次上传的包（Windows 本地文件没统一换行），秒哒改写过的文件都是 LF。所以首次全量包和增量包都要把文本文件统一成 LF 再打包。

**交付前的干净复建（默认）**：增量包不能单独解压构建。在干净目录先还原 `baseVersion` 的全量源码，校验增量的路径和哈希后覆盖上去，再校验一次，然后按锁文件安装、测试、构建。任何一步失败就不交付。当前开发目录跑通不能代替这一步。

**数据库迁移（红线）**：迁移只做加法、可以重复执行；删列、改名、改类型单独成包，先备份、等建委确认。单环境应用里秒哒一执行迁移就改到线上库，而前端要等发布才切换，所以新字段必须让线上旧前端也能跑。规则和示例见[数据库专题](./topics/backend-storage.md#四增量包里的数据库迁移路径-b)。

**依赖文件**：业务改动、运行依赖、仅本地验证用的依赖分开统计。同名但内容不同的文件，核对差异后再决定，不要一律覆盖。

**收件校验与作者复建分开（默认）**：供秒哒先运行的校验脚本，只依赖独立解压目录中已列明的文件和约定运行时；不能导入作者电脑上的历轮打包脚本、历史 ZIP、outputs 或临时夹具。交付前单独解压到没有项目源码与历史包的新目录，运行收件校验并检查完整退出码；测试缺文件、改字节和额外未列明文件均被拒绝。作者侧的累计基线复建脚本只用于本地验收，不能冒充收件方入口。

测试环境合同要写明外部程序、浏览器、包路径、夹具来源和时长。云端没有编码器时，使用随包已核验的样片，或明确将逐帧核验留在作者侧；不能临时换掉测试含义后仍沿用原证明结论。播放观测窗口必须短于实际样片剩余时长。平台环境不支持的用例标为未验或修好夹具，不能因为失败集中在登录态就直接定性为非产品回归。

**Edge 部署输入闭包（默认）**：按当前平台实际使用的部署接口，列出真正发送的入口文件和全部相对导入的传递依赖，并记录部署输入哈希。项目工作区里存在共享模块、ZIP清单有该文件，不证明部署器会把父目录或兄弟目录一起上传。部署文件集合需单独放入空目录，脱离完整项目做模块加载和必要启动检查；缺任一依赖时必须在部署前失败。接口支持多文件时显式提交完整路径映射；只接收单个入口、或共享目录行为未核实时，生成无本地相对导入的独立入口，保留可维护源码与生成关系，不手工复制后各自改逻辑。只有编译通过或部署门禁通过，不能替代这一检查。

**同一批可以多个包一起交**：标明批次号、依赖顺序、每个文件属于哪个包，建委一次上传，秒哒按顺序应用。功能阶段（R8、R9、R10）、ZIP 编号、上传次数是三回事，不必每个阶段单独上传一次。不要先让建委上传一个纯说明包、等秒哒勘察完再开始本来本地就能做的实现。

**每包必交一份单独打开的验收清单**（建委 2026-09-16 要求），不能只藏在压缩包里：

```text
编号 | 截图/原问题 | 改后行为 | 入口与操作 | 预期结果 | 已做验证/待验证 | 建委验收
```

新问题追加进同一张清单，前轮已交付的列为回归项。"代码已改""本地已验证""等待云端部署""建委验收通过"分开标。

**需要云端数据时随包带取证要求**：下一包需要云端的某些文件、表结构、哈希时，随本包带一份 `EVIDENCE-REQUEST-<版本>.md`，写清要什么、为了验证哪个问题、改前还是改后采集。只要需要的那几项，不要求导出全库；不索取密钥、密码和用户原始数据。

**不要默认要求全量导出源码**：导出一次 300 秒点（见[事实表](./facts.md)）。已知的完整源码加上历次交付的包，就是本地重建基线。只有实际要改的文件出现无法解释的差异时，才要那几个文件或哈希。

**默认：取回源码快照仍须核对完整性范围。** 记录资源所属应用、消息事件、编辑/发布版本、原 ZIP 哈希与实际展开清单；逐项确认构建脚本、配置、锁文件和发布入口是否都在快照里。版本一致、ZIP CRC 通过，只证明该资源完整取回，不证明平台工作环境全部导出。快照缺构建脚本等关键文件时，先记录缺口并补齐构建合同，不能用局部回执 diff 臆造完整脚本，也不能宣布已具备可复现构建；之后从别处补回的文件，要对照实际源码核查、记录来源和行尾处理，并独立复建一次。平台拒绝的底层核验不反复换话术重试。例：见[言剪 v75 快照缺构建脚本](../../../../projects/yancut-ai/README.md#本机源码与交接入口)。

## 第 8 阶段：秒哒校验、合并、构建（路径 B）

秒哒执行提示词必须要求它按顺序：

1. 确认当前云端版本等于 `baseVersion`，不一致就停。
2. 校验增量包的路径、字节数、SHA-256，失败就停。
3. 建立可回滚版本，在完整基线上叠加增量，再校验一次。备份仅记录变更前目标与清单，记录容量和保留策略；不能每轮复制整个静态素材目录并无限积累。
4. 执行约定的数据库迁移，按锁安装依赖，检查实际改动覆盖范围并测试；按已核对的实际构建链生成产物，核对入口及资源后部署。涉及懒加载时，新资源先就绪再切入口，并按兼容窗口保留旧 hash 资源，见[发布兼容诊断](./topics/runtime-diagnostics.md#发布后动态导入失败核对新旧资源兼容)。
5. 部署有后端变更的批次后，先对真实部署地址运行本批的最小成功请求，再进入前端发布收尾。核对响应状态、响应结构、版本标识及直接依赖的下一跳；例如媒体服务要验证授权成功后实际 Range 返回正确字节，而不只检查 OPTIONS。启动失败、缺模块、关键成功请求失败时停止宣告完成，回读错误正文与日志并修复；返回鉴权拒绝也只能证明拒绝分支，不能证明成功分支。记录部署前后请求证据，输出时去掉签名、JWT和密钥。
6. 按验收清单逐项回报实际结果，区分本地、云端、待建委手动验收。真实部署成功路径未通过时，明确保持未完成；完成后停止。

**已有应用不要重复 generate-app**，也不用每轮重写 PRD；只有需求变了才更新相关文档。这一点和首次交付不同。

完整的增量提示词模板见 [prompt-templates.md](./prompt-templates.md#增量包执行)。

**回执必须回流到下一轮基线**：保存实际修改文件和部署输入的完整哈希；秒哒自行热修或调整依赖时，同时回收源码。按[基线对齐](#云端改过代码先对齐基线再制包默认)逐项更新执行卡、本地累计基线和测试夹具，再开始下一包。未知差异停止时，执行提示词只让秒哒导出缺少的证据并停止，不让用户在“覆盖丢功能”和“现场自由重写”之间猜选；原包冻结，合并后另出修订包。

## 第 9 阶段：线上真实验收（路径 B）

秒哒改完、构建成功后，要点“发布”线上才会换成新版；只在秒哒的预览里看对了，不等于线上对了。发布完成后再按下面验收。

"执行成功""构建成功""发布完成"都不能证明正式域名已经切换。要检查：

- `/jianwei-release.json` 或项目约定的版本文件
- 页面 HTML 的 `data-release` 版本标记
- 实际加载的 JS/CSS 地址是不是这一轮的，懒加载工作台等路由的 chunk 是否可达；同时测试发布前已打开页面和发布后新会话
- 真实浏览器里新字段、新交互在不在
- 控制台、网络状态码、缓存、权限
- 未登录、普通用户、管理员、手机、无痕窗口

版本文件更新了但页面还引用旧资源，判为"回执成功但线上未切换"。强刷后成功不关闭旧会话失败项；核对 HTML 缓存响应头、旧 chunk 保留和受限恢复行为，避免刷新循环或丢失未保存内容。来源：[言剪恢复后复盘](../../../../projects/yancut-ai/case-miaoda-source-migration.md#官方恢复后的静态发布复盘)。

预览必须和正式发布用同一套数据读取、组件、权限和媒体地址。数据库迁移只创建了文件、没在秒哒环境执行，不算完成。

## 第 10 阶段：反馈、归因、下一轮（路径 B）

建委反馈问题后，先归因：没上传、没合并、没迁移、没构建、没切换、缓存、权限、数据映射，还是视觉回归。原问题编号保留，修复后复验；不能换个编号掩盖失败，也不能一句"全部已修复"关掉没验收的项。

批次是否完成，看建委能不能走通主要成功路径，不看包号、测试数量或秒哒的总结。

**经验怎么回写仓库**（建委 2026-09-27 确认）：反馈用来校正认识，不是每轮都要入库。缺的补、错的改、已有的不重复，没有新价值就不写。改本页或对应专题的原文，不追加流水账。只跟这个项目有关的进度，写在项目自己的记录里。建委对成品的纠正或认可，先记进[观察记录](../../../../../system/repository/observations.md)，要不要写成通用规则按[进化机制](../../../../../system/repository/evolution.md)判断。

## 路径 C：纯提示词协作（项目只在云端）

适用于：项目只在秒哒云端，没有本地源码，建委接受 AI 写提示词、自己贴给秒哒的方式。拿到源码后可以转成路径 B。

**流程**：AI 先判断问题类型（内容、前端、数据展示、后端、交易链路） → 查对应[专题](./topics/README.md)和[踩坑](./pitfalls.md) → 收集当前证据（截图、报错、秒哒回执） → 划清边界、拆成小批 → 建委**一批一批**贴给秒哒 → 每批执行完先在预览里检查，正常再发下一批 → 出问题把秒哒输出发回给 AI，AI 写修复批。

"一批一批发"只适用于路径 C：秒哒在自由改代码，一次给太多容易漏改、误改。路径 B 的多个增量包是 AI 已经写好、测过的代码，可以同批上传、按顺序应用。两者不冲突。

**每批提示词要能独立执行**：写清本批只改什么、严禁改什么、具体改成什么、完成后回报什么、然后停止。不要写"先分析一下再告诉我怎么做"，也不要写"第 0 批先做检查"，除非这次目标就是诊断。

**AI 交付给建委的**：执行顺序、每批一个代码块的提示词、验收清单、需要建委人工确认的事项（身份、密钥、支付参数不能让 AI 编）、失败时要回传什么。

提示词骨架和正反例见 [prompt-templates.md](./prompt-templates.md#纯提示词协作)。

## 交付前自查

- [ ] 是百度秒哒，不是飞书妙搭
- [ ] 应用形态、技术栈（React + Vite）确认过
- [ ] 测试、生产构建、真实浏览器都过了
- [ ] 包里没有依赖目录、日志、密钥、母版
- [ ] 每个包小于限额、每个文件有 SHA-256
- [ ] 在干净目录复建过（增量包：基线 + 增量）
- [ ] 秒哒先校验再执行
- [ ] 素材在对象存储、有 URL 映射；数据库跨设备验证过
- [ ] 加功能、改功能：影响面清单逐行走过，新界面与同级参照并排对比过
- [ ] 线上版本标记、真实资源、手机端都验过
- [ ] 验收清单单独交付，每项状态如实
- [ ] 已填基线对照表；原能力清单无遗漏，回收源码与实际部署的未核验项已列明

## 基线对齐的来源与边界

2026-11-28，建委个人作品网站 R85 首包通过 ZIP 完整性检查，却在覆盖前预检命中 4 个 content-mcp 文件差异。云端已有大型 Skill ZIP 上传、安装包管理及中文路径校验，本地累计基线未回收这些变化；直接覆盖会丢能力。预检按约定停止，报告称未应用、未迁移、未部署，网站保持 R84。错误属于读过“云端修改要回收”却未在制包前做到：本地测试和干净复建使用同一旧基线，因而相互印证却未覆盖现行能力。建委要求把避免方式写回秒哒板块。

随后只读取回有限源码与数据库定义，实际清单列 53 项、ZIP 有 48 项正文，缺的 5 项是导出辅助脚本，运行依赖和数据库材料都在；这也说明清单生成必须在排除辅助文件之后执行。现行工作区的 33 个 MCP 工具成为保留对照，修订实现增加 2 个规范工具；已部署 Edge 原字节无法只读回收，仍保留未核验状态。这是本次基线与合并的证据，不是正式站已部署或所有功能已验收的声明。
