# Codex × 秒哒协作方法

建委做秒哒项目的核心方法：**Codex 在本地开发、测试、打包，建委上传给秒哒，秒哒负责云端存储、数据库、构建、部署，Codex 再根据秒哒回执和线上结果验收。** 本页是这套方法的唯一正文，按阶段组织。遇到具体问题（上传、登录、支付、SEO、排错）时，再查 [topics/](./topics/README.md) 里对应的专题。

> 来源：混世魔牛游戏（2026-08）、建委个人网站 R6~R8（2026-09）、言剪 AI B1~B8（2026-09）、德锦周锦网站整改（2026-06）等实战。当前限额见[事实表](./facts.md)。

## 先选路径

| 当前状态 | 走哪条 | 从哪个阶段开始 |
|---|---|---|
| 新项目，准备在本地用 Codex 开发 | **A. 首次全量交付** | 第 1 阶段 |
| 已经有本地源码基线，继续迭代或修问题 | **B. 增量迭代** | 第 5 阶段 |
| 项目只在秒哒云端，没有本地源码，建委接受用提示词修改 | **C. 纯提示词协作** | 见本页末尾"路径 C" |

**红线**：已经有本地基线的项目，即使暂时拿不到云端最新改动，也不要退回路径 C 让秒哒自由重写。先把缺的那几个文件或哈希要回来，其他不冲突的工作继续做。

## 三方分工

| 角色 | 负责 | 不负责 |
|---|---|---|
| 建委 | 描述问题、上传包、在线上页面操作验收、回传截图和秒哒回执 | 不用自己设计技术方案 |
| Codex | 读仓库经验、改本地源码、测试、打包、写秒哒提示词和验收清单、审查回执 | 不假装能直接访问秒哒云端源码或数据库 |
| 秒哒 | 接收校验、合并代码、执行数据库迁移、构建、部署、回报结果 | 不负责跨轮记忆和版本管理；它说"构建成功"不等于线上已经对了 |

---

## 第 1 阶段：开工前定三件事（路径 A）

这三件事秒哒生成后很难改，第一次就要说清楚。详见[平台基础 · 首轮决策](./basics/platform-basics.md)。

1. **应用形态**：Web、小程序还是 APP。后期强转容易出空产物。
2. **后端存储**：明确要真实数据库，不说就可能只存在浏览器缓存里。
3. **环境**：单环境还是开发、生产双环境，要在生成前选。

## 第 2 阶段：本地开发和验收（路径 A）

Codex 交付前至少做到：

1. 读项目 README、现有测试、素材清单。
2. 不删建委没授权删的源码、素材、功能。
3. 跑现有测试和生产构建。**构建命令按项目 `packageManager` 字段和锁文件执行**，不要一律改成 npm，也不要重新解析依赖。
4. 用真实浏览器看桌面和手机：控制台、网络请求、布局、点击、触控、声音。
5. 游戏、3D、视频项目另查帧率、纹理内存、预加载、页面隐藏时是否暂停。

## 第 3 阶段：统一技术栈，做运行时闭包（路径 A）

**红线**：秒哒 Web 应用是 **React + Vite**，产物是 `dist/`。不能用 Next.js、SSR、Next API Routes，也不能用必须常驻 Node 服务才能打开的方案。Vercel、Cloudflare 的专用配置不带过去。

只交付运行时真正用到的文件：

- 保留：源码、锁文件、运行时引用的素材、必要的配置样例（`.env.example`）
- 排除：`node_modules`、`dist`、日志、截图、缓存、密钥、原始母版、没引用的素材、本机部署配置

不要把整个工作目录直接压缩。

## 第 4 阶段：分包、上传、先校验再创作（路径 A）

**分包**：对话附件一次最多 5 个、每个 20MB（见[事实表](./facts.md)），单包建议小于 19,000,000 字节。每个包编号（01、02……），附一份清单：每个文件的路径、字节数、SHA-256。

**打完包自己先复建一次**：在另一个干净目录把所有包解压，重新安装、测试、构建。通过了才交付。

**上传分两步，不要一步到位：**

1. **只接收**：第一条提示词要求秒哒只解压、核对文件数和哈希，缺文件或哈希不对就停下报告，**不准开始生成页面，不准用占位图补缺失素材**。
2. **确认齐全后再创作**：再发一条提示词，重新声明技术栈、禁止修改的范围、素材映射、测试和构建要求。

首次全量交付的最后一句**必须**是：

```text
严格依照上传的源码，然后给我生成网页应用，给我生成产品需求文档，并立即开始创作。
```

只说"生成网页应用"时，秒哒可能跳过产品需求文档（PRD）。

**素材进对象存储**：压缩包不是线上地址。图片、音频、视频、模型要解压进秒哒对象存储，并让秒哒回报"原路径 → 对象键 → HTTPS 地址 → SHA-256"的映射。视频要支持 Range（能拖动），不要用 Base64 或临时 Blob 地址。

**数据库**：只存需要查询、权限、跨设备保存的业务数据（用户、订单、存档、后台内容），不把图片视频塞进表里。要求秒哒回报表结构和权限规则，并用无痕窗口或另一台设备验证数据确实存在云端。不需要登录和存档的项目，不要为了显得完整硬加数据库。

完整的首次交付提示词模板见 [prompt-templates.md](./prompt-templates.md#首次全量交付)。

## 第 5 阶段：每轮开始先读执行卡（路径 B）

每个项目在自己的 README 或状态记录里维护一张执行卡。每轮开始、长任务恢复、交付前都先读它，不要只盯着最后一条报错继续做。

| 执行卡字段 | 用途 |
|---|---|
| 本轮目标、验收标准、明确不做的 | 确认还是建委的最新要求 |
| 应用、环境、基线版本、本批版本 | 不把预览当生产，不拿旧包覆盖云端改动 |
| 当前阶段和上一轮结果 | 执行中不发下一条命令；取消了不自动重发 |
| 未解决的问题、需要的证据、谁来提供 | 每个问题保留编号，直到验收通过 |
| 已验证和未验证的 | 本地测试、秒哒回执、线上实测分开写 |

进入技术细节前，先判断它是否阻塞本轮验收；不阻塞的记进问题清单，不顺手扩大改动。同一个错误重复出现、又没有新证据时，停止重试，先去拿缺的日志、源码或环境信息。

## 第 6 阶段：在本地修改和测试（路径 B）

前后端一致的问题要顺着"录入 → 保存 → 查询 → 渲染 → 预览/发布"查一遍。字段多的，列一张字段矩阵：后台字段、数据库列、接口、列表、详情、预览、空值，逐列对上。

每个涉及登录、存储、支付或外部接口的增量包，另外检查：

1. 从前端源码列出所有 `import.meta.env.VITE_*`，和 `.env.example`、秒哒构建脚本逐项对照，漏一个就停。
2. 分别测 200、空返回、非 JSON 错误、超时、配置缺失。配置缺失不能被笼统报成"网络异常"。
3. 传给数据库的值用数据库同样的规则（正则、枚举、长度）做断言，至少有一项测试真实执行 SQL，而不是用替身假装成功。

来源：[踩坑 #29](./pitfalls.md#29-增量包修复了业务代码却漏掉云端构建变量且跨层假数据掩盖格式错误)。

## 第 7 阶段：打增量包（路径 B）

**命名**：`<项目>-JW-YYYYMMDD-R<序号>-<主题>-v<格式版本>.zip`，例如 `jianwei-JW-20260906-R8-dynamic-types-increment-v4.zip`。序号只增不减，不用"最新版""最终包"这种名字。

**包里放**：本轮改动的文件（相对路径）、`MIAODA-PACKAGE-MANIFEST-<版本>.json`、变更说明和禁止修改的范围、数据库迁移脚本或"无需迁移"、秒哒执行提示词、回滚说明。

manifest 记录每个文件的路径、字节数、SHA-256，以及基线：

```json
{
  "version": "JW-20260906-R8",
  "baseVersion": "JW-20260906-R7",
  "baseSource": {"kind": "git-commit-or-full-archive", "reference": "<commit或存档路径>", "sha256": "<存档哈希>"},
  "package": "jianwei-JW-20260906-R8-dynamic-types-increment-v4.zip",
  "files": [{"path": "src/pages/Admin/Works.tsx", "bytes": 12345, "sha256": "..."}],
  "databaseMigration": "required|not-required|manual-review",
  "createdAt": "2026-09-07"
}
```

**交付前的干净复建（红线）**：增量包不能单独解压构建。在干净目录先还原 `baseVersion` 的全量源码，校验增量的路径和哈希后覆盖上去，再校验一次，然后按锁文件安装、测试、构建。任何一步失败就不交付。当前开发目录跑通不能代替这一步。

**依赖文件**：业务改动、运行依赖、仅本地验证用的依赖分开统计。同名但内容不同的文件，核对差异后再决定，不要一律覆盖。

**同一批可以多个包一起交**：标明批次号、依赖顺序、每个文件属于哪个包，建委一次上传，秒哒按顺序应用。功能阶段（R8、R9、R10）、ZIP 编号、上传次数是三回事，不必每个阶段单独上传一次。不要先让建委上传一个纯说明包、等秒哒勘察完再开始本来本地就能做的实现。

**每包必交一份单独打开的验收清单**（建委 2026-09-16 要求），不能只藏在压缩包里：

```text
编号 | 截图/原问题 | 改后行为 | 入口与操作 | 预期结果 | 已做验证/待验证 | 建委验收
```

新问题追加进同一张清单，前轮已交付的列为回归项。"代码已改""本地已验证""等待云端部署""建委验收通过"分开标。

**需要云端数据时随包带取证要求**：下一包需要云端的某些文件、表结构、哈希时，随本包带一份 `EVIDENCE-REQUEST-<版本>.md`，写清要什么、为了验证哪个问题、改前还是改后采集。只要需要的那几项，不要求导出全库；不索取密钥、密码和用户原始数据。

**不要默认要求全量导出源码**：导出一次 300 秒点（见[事实表](./facts.md)）。已知的完整源码加上历次交付的包，就是本地重建基线。只有实际要改的文件出现无法解释的差异时，才要那几个文件或哈希。

## 第 8 阶段：秒哒校验、合并、构建（路径 B）

秒哒执行提示词必须要求它按顺序：

1. 确认当前云端版本等于 `baseVersion`，不一致就停。
2. 校验增量包的路径、字节数、SHA-256，失败就停。
3. 建立可回滚版本，在完整基线上叠加增量，再校验一次。
4. 执行约定的数据库迁移，安装依赖，测试，构建，部署。
5. 按验收清单逐项回报实际结果，区分本地、云端、待建委手动验收。完成后停止。

**已有应用不要重复 generate-app**，也不用每轮重写 PRD；只有需求变了才更新相关文档。这一点和首次交付不同。

完整的增量提示词模板见 [prompt-templates.md](./prompt-templates.md#增量包执行)。

**秒哒云端自己改过的代码**（比如建委直接在秒哒对话里让它热修）：视为新的基线差异。先把那些文件或哈希要回来合进本地源码，或者在下一包里写明保留它们，不能整文件覆盖。

## 第 9 阶段：线上真实验收（路径 B）

"执行成功""构建成功""发布完成"都不能证明正式域名已经切换。要检查：

- `/jianwei-release.json` 或项目约定的版本文件
- 页面 HTML 的 `data-release` 版本标记
- 实际加载的 JS/CSS 地址是不是这一轮的
- 真实浏览器里新字段、新交互在不在
- 控制台、网络状态码、缓存、权限
- 未登录、普通用户、管理员、手机、无痕窗口

版本文件更新了但页面还引用旧资源，判为"回执成功但线上未切换"。

预览必须和正式发布用同一套数据读取、组件、权限和媒体地址。数据库迁移只创建了文件、没在秒哒环境执行，不算完成。

## 第 10 阶段：反馈、归因、下一轮（路径 B）

建委反馈问题后，先归因：没上传、没合并、没迁移、没构建、没切换、缓存、权限、数据映射，还是视觉回归。原问题编号保留，修复后复验；不能换个编号掩盖失败，也不能一句"全部已修复"关掉没验收的项。

批次是否完成，看建委能不能走通主要成功路径，不看包号、测试数量或秒哒的总结。

**经验怎么回写仓库**（建委 2026-09-27 确认）：反馈用来校正认识，不是每轮都要入库。缺的补、错的改、已有的不重复，没有新价值就不写。改本页或对应专题的原文，不追加流水账。只跟这个项目有关的进度，写在项目自己的记录里。

## 路径 C：纯提示词协作（项目只在云端）

适用于：项目只在秒哒云端，没有本地源码，建委接受 Codex 写提示词、自己贴给秒哒的方式。拿到源码后可以转成路径 B。

**流程**：Codex 先判断问题类型（内容、前端、数据展示、后端、交易链路） → 查对应[专题](./topics/README.md)和[踩坑](./pitfalls.md) → 收集当前证据（截图、报错、秒哒回执） → 划清边界、拆成小批 → 建委**一批一批**贴给秒哒 → 每批执行完先在预览里检查，正常再发下一批 → 出问题把秒哒输出发回给 Codex，Codex 写修复批。

"一批一批发"只适用于路径 C：秒哒在自由改代码，一次给太多容易漏改、误改。路径 B 的多个增量包是 Codex 已经写好、测过的代码，可以同批上传、按顺序应用。两者不冲突。

**每批提示词要能独立执行**：写清本批只改什么、严禁改什么、具体改成什么、完成后回报什么、然后停止。不要写"先分析一下再告诉我怎么做"，也不要写"第 0 批先做检查"，除非这次目标就是诊断。

**Codex 交付给建委的**：执行顺序、每批一个代码块的提示词、验收清单、需要建委人工确认的事项（身份、密钥、支付参数不能让 AI 编）、失败时要回传什么。

提示词骨架和正反例见 [prompt-templates.md](./prompt-templates.md#纯提示词协作)。

## 交付前自查

- [ ] 是百度秒哒，不是飞书妙搭
- [ ] 应用形态、技术栈（React + Vite）确认过
- [ ] 测试、生产构建、真实浏览器都过了
- [ ] 包里没有依赖目录、日志、密钥、母版
- [ ] 每个包小于限额、每个文件有 SHA-256
- [ ] 在干净目录复建过（增量包：基线 + 增量）
- [ ] 秒哒先校验再执行
- [ ] 素材在对象存储、有 URL 映射；数据库跨设备验证过
- [ ] 线上版本标记、真实资源、手机端都验过
- [ ] 验收清单单独交付，每项状态如实
- [ ] 秒哒云端改过的代码已合回本地源码
