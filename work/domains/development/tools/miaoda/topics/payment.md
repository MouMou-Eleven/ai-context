## 付了钱订单还是“未支付”：异步回调怎么排查（默认）

用户付款成功后，支付平台会另外向你填的 `notify_url` 发一次请求（异步通知），订单状态靠它改。页面跳回“支付成功”不算数，订单表没改就是回调没走通。按顺序查，查到哪步断了就修哪步：

1. **通知地址能不能从公网访问。** 下单时传的 `notify_url` 必须是公网 HTTPS 地址，指向真正处理通知的后端函数（秒哒里是 Edge Function），不能是前端页面路由、预览域名或本机地址。用 `curl -i -X POST <notify_url>` 试一下：返回首页 HTML 说明被单页应用的路由接管了（同类问题见[踩坑 #21](../pitfalls.md#21-微信恢复访问-txt-验证文件被-spa-fallback-吃掉--校验失败)）。
2. **函数有没有收到请求。** 看后端函数的运行日志里有没有这次通知；没有，回到第 1 步。有，看它读到的参数和环境变量名（密钥名拼错是常见原因，见[踩坑 #12](../pitfalls.md#12-秒哒新建-edge-function-时把环境变量名拼错--读出-undefined-当作配置不完整)）。
3. **验签过没过。** 只用通知里规定的字段算签名（YunGouOS 支付通知是 `code`、`orderNo`、`outTradeNo`、`payNo`、`money`、`mchId`，见[完整案例](payment-case-yungouos-jsapi.md)），可选字段不参与；不能用 Web Crypto 算 MD5（见片段 4）；按支付渠道取对应的密钥。验签失败就拒绝，不改订单。
4. **业务处理对不对。** 先看支付结果码（YunGouOS 是 `code == 1` 才算成功），再核对金额和本地订单一致，然后按商户订单号更新订单。要**幂等**：同一笔通知来第二次，订单已经是已支付就直接返回成功，不重复加积分、不重复发货。
5. **最后有没有正确应答。** 处理完要按平台规定返回，YunGouOS 是输出纯文本 `SUCCESS`，表示“不用再通知了”（官方回调示例的写法）；不要返回 JSON 或页面。没正确应答时平台怎样重发，官方示例没写，以官方文档为准。
6. **还是没收到时别直接判定没付钱。** 订单状态不明时，先查支付平台后台或它提供的订单查询方式（YunGouOS 有没有、怎么调，先查官方文档）核对实际状态，再补改订单。

验收：用最小金额真实付一笔（让建委手动付，自动化测试不重复消费），看后端日志收到通知、验签通过、订单变为已支付、返回 `SUCCESS`；再把同一条通知手动重放一次，订单和积分不变。退款通知（`refund-notify`）也按地址、日志、验签、幂等的顺序查，但验签字段不同（见完整案例），应答方式先查官方文档再定。

为什么：回调失败时用户看到的只是“付了钱订单没变”，问题却可能在地址、日志、签名、幂等、应答任何一环；不按顺序查，容易在签名上反复改却漏掉地址根本没通。

## 提示词片段

### 片段 1：设备识别（让秒哒原样实现，不要自由发挥）

```javascript
function getPayMethod() {
  const ua = navigator.userAgent || "";
  const isWeChat = /MicroMessenger/i.test(ua);
  const isMobile = /Mobile|Android|iPhone|iPad|iPod/i.test(ua);
  if (isWeChat && isMobile) return "jsapi";
  return "native";
}
```

适用场景：要让秒哒在多种条件下做不同分支时，给一段确定函数比口头描述要稳得多。

### 片段 2：强制使用技能而非自己写

```
所有 X 接口调用必须通过 @<技能名> 这个技能内的脚本完成：
- scripts/foo.py 做 A
- scripts/bar.py 做 B
禁止在 Edge Function 或前端代码里自行实现签名 / MD5 / 加密相关逻辑。
之前你这么做过，结果有 bug，已经验证翻车。
```

适用场景：已有案例出现过重写已验证实现的情况，应明确复用路径和原因。

### 片段 3：强制使用参考实现而非另写

```
异步通知接收端请直接使用技能包内的 references/edge_function_notify.ts，
原样部署到 supabase/functions/wxpay-notify/index.ts，**不要重写**。
该文件已经包含 X / Y / Z 功能，并已在测试环境验证。
```

适用场景：技能包里附带了完整可用代码，但秒哒倾向"重新生成一份"。

### 片段 4：禁止 MD5 + Web Crypto 死路

```
禁止调用 crypto.subtle.digest("MD5", ...)，
Deno/浏览器 Web Crypto 拒绝 MD5，必抛 NotSupportedError，
之前你这么做翻车过。
如需 MD5，使用 references/edge_function_notify.ts 里的纯 JS MD5 实现，
或调用技能内的 Python 脚本（用 hashlib.md5）。
```

适用场景：任何涉及微信支付、YunGouOS 等需要 MD5 签名的场景。

### 片段 5：保护密钥

```
<密钥名> 严禁出现在任何源码、配置文件、前端、注释、日志里。
它只通过 <某面板> 的环境变量 X 注入。
如果你的代码里需要密钥，正确做法是调用技能脚本而不是自己读密钥。
```

## 反面教材：失败的提示词

```
❌ 帮我加上手机端支付，最好兼容微信
❌ 把支付改一下，让它在手机上能用
❌ 接入一个支付插件
```

为什么失败：没有 @ 技能、没有红线、没有约束 AI 行为、没有指明分工。这类提示缺少可核验边界，案例中曾导致实现偏差。

## 来源与状态

提示词片段来自德锦周锦官网 YunGouOS 支付接入（见完整案例）。本页只适用于已采用对应支付技能、回调和运行时的项目。`getPayMethod` 是那个案例的设备分支，不是所有支付平台的通用协议；密钥读取、签名与部署方式以当前集成为准。回调排查六步：通知字段和 `code == 1` 判成功、验签失败拒绝、处理完输出 `SUCCESS` 停止重发，2026-11-27 对照 YunGouOS 官方 SDK 回调示例（GitHub YunGouOS-PAY-SDK 的 PHP demo/notify.php）核实；重发次数和间隔官方示例未写明，这里不写具体数字；地址、日志、幂等、主动查询是支付回调的通用做法。
