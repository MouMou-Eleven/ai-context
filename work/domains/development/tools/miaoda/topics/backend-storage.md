# 数据库与后端存储

秒哒应用的数据怎么存、库表怎么建和改、改了会影响谁，都以本页为准。会员档位对应的容量、备份天数、哪些功能要高级版，只写在[事实表](../facts.md#后端数据库)。

秒哒应用的数据库是 Supabase（底层 PostgreSQL），秒哒结合自己的多 Agent 架构和百度智能云资源做了改造。所以写给秒哒的后端代码按 Supabase 形态写：表在 Postgres，接口是 `supabase/functions/<name>/index.ts` 的 Deno 函数，登录用 Supabase Auth，文件进 Storage。四套运行时的区别见[平台基础](../basics/platform-basics.md#一四套独立运行时)。

## 一、动数据库之前，先判断应用处在哪种状态（红线）

同一句"给报名表加个字段"，在不同状态下后果完全不同。先在编辑器左侧「后端服务」里看清楚，再写提示词或打增量包。

| 状态 | 怎么认 | 改数据库的后果 |
|---|---|---|
| 没有后端 | 「数据库维护页」提示当前应用无数据库 | 数据只在浏览器里，换设备就丢。用下文"二轮补数据库"加上 |
| 单环境 | 创建时没开多环境（创建时开多环境需要高级版及以上） | **编辑器里的数据库就是线上数据库。** 对话改表结构、在数据库维护页改数据、增量包里的迁移，执行那一刻就作用到已发布应用；前端改动却要手动发布才生效 |
| 多环境 | 后端服务里有开发环境、线上环境之分（高级版及以上可开） | 改动先落在开发环境，发布时才把表结构同步到线上；首次发布同步全部数据，之后的发布**只同步结构和配置，不同步业务数据** |
| 2025-09-17 前创建的旧应用 | 创建时间早于秒哒 V1.5 | 用的是旧数据库，不能切换到新库，也享受不到对话改库等能力。还要长期迭代的，建议重新创建应用再迁数据 |

**单环境的危险窗口**：数据库改动已经上线，新前端还没发布，线上用户用的还是旧前端。所以单环境下的结构变更必须让新旧前端都能跑：

- 正例：报名表原来只有姓名、手机号，新加"地区""场次"两列，允许为空或给默认值。旧前端不写这两列也不报错，新前端发布后开始写。
- 反例：把 `phone` 列改名为 `mobile`。改名那一刻，线上旧前端的读写全部报错，直到新前端发布。

已发布、有真实用户的应用，没特别理由就开多环境（单环境可以随时升级为多环境，开启时会把线上库同步一份到开发库）。单环境只适合 Demo、原型、活动报名页、个人小工具。

## 二、哪些改动是破坏性的（红线）

| 改动 | 能不能撤回 | 怎么做 |
|---|---|---|
| 新增表、新增字段 | 版本回退可以恢复到历史字段状态 | 可以直接做；单环境下新字段允许为空或带默认值 |
| 删字段、删表、字段改名、改类型、清空数据 | **版本回退恢复不了已删除的字段** | 先备份，再让秒哒列出影响范围，建委确认后才执行 |
| 在数据库维护页手工改、删数据 | 不能撤回 | 改之前导出该表 CSV |

破坏性改动的固定顺序：

1. **先备份。** 高级版及以上在「后端服务 → 数据库备份」手动打一个备份点（每次扣 100 秒点），恢复是原地覆盖、不可撤销。标准版和免费版只有每日自动备份，自己不能恢复，所以要先在数据库维护页把受影响的表全量导出 CSV。
2. **先查影响。** 让秒哒先 SELECT：受影响的表、行数、样例 5 条、哪些页面和函数还在用这个字段。
3. **先改代码，后删字段。** 前端和函数不再读写这个字段、并且新前端已发布，再删字段。不要在同一轮里既改前端又删字段。
4. 建委明确说"可以删"之后再执行。

"应用回收站"只能恢复被删除的应用，不是数据库备份。

## 三、让秒哒建库、改库的提示词

### 首轮：按业务描述，不按表结构描述

秒哒自己会从业务语义里识别订单、用户、商品这些对象并建表。描述"谁产生数据、谁查看、能不能改、要不要登录"，比直接写字段清单效果好。

- 推荐：用户可以发布旅行计划，其他用户可以评论，作者可以删除自己的计划。
- 不推荐：创建一个包含 title、content 字段的数据表。

单一数据（记事本只存笔记）一句话就够。复合数据（电商独立站有用户、商品、订单、物料）要把每类对象和它们的关系说全，并写明是否需要登录、用什么方式登录，因为登录会决定数据归属和权限。

```text
我现在要做一个 <Web 应用 / 微信小程序 / APP>，请从首轮就按这个应用形态生成，不要生成成其他类型。

红线：
- 需要真实后端数据库存储，不允许只用浏览器缓存、localStorage 或前端状态保存业务数据。
- 需要用户登录：<是/否>，登录方式：<手机号+验证码 / 账号密码 / 微信登录>。

业务对象和流程：
1. <谁> 可以 <新增/提交/修改/查看> <什么数据>
2. <谁> 可以 <……>
3. 管理员需要 <查看/导出/审核> <哪些数据>

完成后请说明：
1. 生成了哪些数据表，每张表有哪些字段，表之间怎么关联。
2. 哪些页面或操作会写入数据库，每张表的读写权限规则。
3. 我如何用无痕窗口或另一台设备验证数据已经保存在云端。
```

### 二轮：给没有后端的应用补数据库

适用：第一轮做的是静态页，现在要加报名表单；或者发现数据只存在浏览器里。

```text
请为当前应用增加后端数据库存储能力，不要重建应用，不要删除现有页面和功能，不要重构无关模块。

需要保存的数据：<例如：活动报名表，字段为姓名、手机号、地区、场次>
<如果原来用 localStorage 存过业务数据：把这些读写全部改为读写后端数据库。>

完成后请只输出：
1. 新增了哪些表和字段。
2. 哪些页面已改为读写后端数据库。
3. 是否还有业务数据保存在 localStorage 或浏览器缓存；有的话列出位置和原因。
4. 我如何用无痕窗口验证。
```

### 改字段（加法）

```text
本次只修改数据库结构，不改页面布局。
当前应用是 <单环境 / 多环境>。

在 <表名> 表新增字段：<地区（文本，可为空）>、<场次（文本，可为空）>。
同步修改：<报名表单> 增加这两个输入项，<后台列表> 增加这两列。
不要删除、改名或修改已有字段的类型，不要清空已有数据。

完成后按表回贴当前全部字段列表，并说明已有记录的新字段是什么值。
```

### 删字段、改名（破坏性）

先按第二节备份。然后分两轮发：

```text
第一轮：本次不执行任何删除。
我准备删除 <表名>.<字段名>。请只做检查并回报：
1. 这张表现在有多少行，这个字段有值的有多少行，给 5 条样例。
2. 哪些页面、组件、后端函数、RPC 还在读写这个字段。
完成后停止，等我确认。
```

```text
第二轮（已备份、已确认，且新前端已发布不再使用该字段）：
请删除 <表名>.<字段名>，只删这一个字段，不要动其他表和字段。
完成后回贴该表当前字段列表。
```

## 四、增量包里的数据库迁移（路径 B）

本地开发、打增量包给秒哒的项目（流程见 [workflow.md](../workflow.md)），迁移脚本按这些规则写：

1. **manifest 写清环境和迁移类型。** `databaseMigration` 填 `required`、`not-required` 或 `manual-review`，同时写明应用是单环境还是多环境。单环境下秒哒执行迁移就等于改线上库。
2. **迁移只做加法，并且可以重复执行。** 例如 `alter table signups add column if not exists region text;`。新字段允许为空或带默认值，保证线上旧前端还能跑。
3. **破坏性迁移单独成包。** 删列、改名、改类型不和前端改动放在同一个包；包里写明前置条件（已备份、新前端已发布）、影响范围和回滚说明，秒哒执行前必须停下等建委确认。
4. **不知道线上真实表结构时，先要。** 秒哒原生生成的项目、或建委在秒哒对话里改过库的项目，本地源码里的迁移文件不一定等于线上结构。写迁移前先让秒哒按表回贴当前字段列表，或随包带取证要求，不要凭源码猜。
5. **对话里改过的库是新的基线差异。** 建委直接在秒哒对话里加过字段，下一包先把字段列表要回来合进本地迁移，再打包。

## 五、验收

- 在应用里录一条测试数据，换无痕窗口或另一台设备还能看到，才算存进了云端。
- 在「数据库维护页」核对数据确实写入、字段和预期一致。维护页能增删改查、筛选、CSV 导入导出，但在这里改数据会直接影响线上（单环境）。
- 改库后让秒哒按表回贴字段列表；修数据前先让它 SELECT 影响范围（行数和样例）。
- 正式上线的应用开启「后端保活」，不然连续一段时间没人访问，数据库会自动暂停，用户打开就报错（天数和哪些档位能开见[事实表](../facts.md#后端数据库)）。
