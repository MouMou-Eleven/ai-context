# 案例：本地源码上传 + 多应用共享后端（本命音律，2026-10-22）

一个后端被两个秒哒 Web 应用共享：用户端（带后端）+ 管理后台（只有前端）。全部代码在本地写好、测好后打包上传，秒哒负责校验、建表、部署函数、构建发布。最终两个应用都已发布，后台能读到用户端写入的数据。本页记录整套做法和中途出的问题，下一个"多端共享后端"项目照此执行。

方法正文在 [workflow.md 第 4 阶段](../workflow.md#第-4-阶段分包上传先校验再创作路径-a)；平台坑在[踩坑 #27](../pitfalls.md#27-上传源码与秒哒云端构建环境不一致--本地能构建发布时装依赖或构建失败)、[#31](../pitfalls.md#31-共享后端的第二个应用上传的自定义源码没拿到后端连接配置)。项目事实在[六十甲子项目](../../../../../projects/ai-sixty-jiazi-music-ip/README.md)。

## 一、本地怎么准备（这部分一次就成功了）

| 做法 | 为什么 |
|---|---|
| 后端写成 Supabase Edge Function 形态，并**在本地打包成单文件** `supabase/functions/<name>/index.ts`（esbuild，`platform: neutral`，只把 `npm:@supabase/supabase-js@2` 留作外部依赖），提示词要求"原样部署，禁止改写" | 秒哒没有改写函数，一次部署成功；避免了"秒哒把后端翻译一遍引入 bug" |
| 后端代码只用 Web 标准 API（`crypto.subtle`、`TextEncoder`、`btoa`），不用 `node:crypto`、`Buffer`、`node:fs`；环境变量用 `Deno.env` 优先、`process.env` 兜底的小函数读取 | 同一份代码既能在本地 Node / Vercel 跑，也能在秒哒 Deno 跑，本地测试即线上行为 |
| 所有业务数据放一张表，迁移只建表、开 RLS、不建策略，函数用平台自带的 `SUPABASE_SERVICE_ROLE_KEY` 读写 | 迁移一次执行成功；浏览器拿 anon key 碰不到表 |
| 业务身份放自定义请求头（`X-Device-Id`、`X-Session-Token`、`X-Admin-Token`），`Authorization` 和 `apikey` 留给平台网关放 anon key；函数自己处理 CORS 预检并放行这些头 | 不和网关的 JWT 校验冲突；管理后台在另一个域名也能调 |
| 前端只读两个公开变量 `VITE_SUPABASE_URL`、`VITE_SUPABASE_ANON_KEY`；缺一个时页面直接提示"后端未配置完整" | 秒哒回报注入情况时有明确核对对象 |
| 本地装真实 Deno 跑打包后的函数（内存存储），跑 23 项接口；再把两个前端按秒哒模式构建，放在两个不同端口，同连这个 Deno 后端做浏览器联调 | 上线前就验证了 CORS、跨域名共享、数据互通 |
| 两个包各自解压到新目录：逐文件核对 SHA-256 → `npm ci` → 构建 → 测试 → 敏感信息扫描 → 用包内源码重新打包函数、比对哈希 | 秒哒 127 / 14 个文件一次核对通过 |
| 密钥值不进压缩包；扫描时把测试脚本里写着真实密码的地方也查出来改掉了 | 包里没有任何密码。**但**密钥值写在上传步骤说明里，而这份说明被当作附件一起发给了秒哒，等于密钥进了秒哒对话记录。以后密钥单独放一个文件，文件名标明"不要上传"，不和上传说明、提示词放在同一个文件夹 |

## 二、上传顺序

1. 用户端：首页「网页」，**不选**共享后端。第一条消息只校验，第二条才创作（建表、部署函数、注入变量、构建）。
2. 密钥：秒哒回执显示它按"先读我"里的值把 3 个密钥配到了函数上（因为这份说明随附件上传了）。正确做法是建委在「后端服务 → 密钥管理」手填，密钥不出现在任何上传给秒哒的文件里。函数能否读到密钥，用**行为**验证：`/config` 返回的 `needPayCode`、`storage`，后台登录正确密码 200、错误密码 401。红线禁止改写函数时，秒哒就没法按提示词插入 `console.log(Object.keys(Deno.env.toObject()))`，行为验证是可行的替代。
3. 发布用户端，记下网址。
4. 管理后台：首页「网页」→ 点「共享后端」选用户端项目 → 上传 → 校验 → 创作。

## 三、中途出的问题

| 问题 | 发生在 | 怎么解决的 | 下次在打包时就解决 |
|---|---|---|---|
| 3 个中文文件名解压成乱码 | 用户端校验 | 秒哒自己用正确编码重解，核对通过 | 包内文件名只用英文 |
| 秒哒按我们的红线删掉了平台模板文件（`pnpm-workspace.yaml`、Tailwind、shadcn 组件），并替换了 `vite.config.ts` | 两个应用生成阶段 | 删除本身没报错；发布修复时又改回了部分模板文件 | 红线不再写"与清单完全一致、删除注入文件"，改为保留平台模板构建文件，见 #27 |
| 发布报 `ERR_PNPM_UNKNOWN: This project is configured to use npm` | 两个应用发布 | 删 `package.json` 的 `packageManager` 字段 | 不写这个字段 |
| 管理后台修发布错误时，秒哒另外补了 `vite-plugin-svgr` 依赖、恢复了 `pnpm-workspace.yaml` | 管理后台发布 | 一并修好，发布成功 | 用户端没做这两步也发布成功了，所以不能证明它们必需；真正已证实的原因只有 `packageManager` |
| 共享后端识别三次 `Sandbox creation timeout`，工作区没有后端 URL / anon key | 管理后台校验 | 秒哒从已发布用户端 JS 取 anon key、探测到在用的后端后注入 | 提示词要求秒哒自己从共享后端读取连接配置并回报注入结果，读不到先重试，不需要用户提供地址，见 #31 |
| 中途用到一个已暂停的旧后端地址（`offline-projects`） | 管理后台 | 秒哒探测后改用在用的 `backend.miaoda.online/projects/...` | 提示词写明不使用 offline-projects 地址 |
| PRD 保存状态 failed | 管理后台 | 秒哒重试后保存成功 | 无需处理 |

全部问题都在当天通过对话修复，没有回滚。

## 四、上线后在秒哒里直接改的

建委随后在用户端对话里调用秒哒的「登录」「短信验证码」技能，把邮箱 + 密码改成**手机号 + 密码 + 短信验证码注册、手机号 + 密码登录、短信找回密码**（Supabase Auth 原生手机号流程，百度智能云短信）。秒哒新增了"把 Supabase 会话换成应用自己的会话令牌"的接口，并顺带修了一个网关路径 404。回执提示两个应用都受影响（共享后端），后台用户列表改为显示手机号。

随后又做了一轮注册登录对抗式审查，修了 8 个问题，清单已收进[登录专题](./authentication.md#原生手机号--密码--短信注册登录找回密码的一次性检查清单)。

两次改动让本地源码和云端出现了较大差异（认证相关文件、依赖、`vite.config.ts`、两个迁移）。转入增量包前，建委下载了一次云端源码（205 个文件，含 git 历史和平台 `.rules/` 构建规则）作为新基线。

## 五、可以照搬的结论

- 多端共享后端：后端只放第一个应用的包；第二个应用的包只有前端，提示词写死"不建表、不建函数、不改密钥"，并要求秒哒自己读取共享后端的连接配置、回报注入结果。
- 本地预打包函数 + 原样部署，比让秒哒按说明写后端稳。
- 上传包按秒哒发布合同准备：无 `packageManager`、精确版本、空插件 PostCSS、文件名英文、提示词要求发布前用 pnpm 验一次。
- 验收共享是否成功，看第二个应用能否读到第一个应用写入的数据。
