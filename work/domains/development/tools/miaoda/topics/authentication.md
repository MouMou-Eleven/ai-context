# 登录与手机号身份一致性

> 查看模板不代表已授权收费、部署或外部发送。

> 仅在当前项目已经采用Supabase Auth或对应秒哒用户体系、并复现所述故障时使用；“中国手机号”规范化只覆盖本案例业务范围，不据此改全球号码规则或自动合并旧账户。

## 身份签发与业务会话分工

Supabase Auth 负责验证码、密码验证与平台凭据签发；应用的 Edge Function 可以验证该凭据、绑定业务用户并建立业务会话。不能把“不要自写验证码或签发平台凭据”误读为删除所有业务认证桥。言剪当前使用原生手机号认证及服务端 sub 绑定，不适用下方旧手机号拼邮箱方案；具体登录合同回项目 README 核对。

## 登录：优先使用 Supabase Auth，不自建验证码签发器

**适用场景**：短信验证码登录报 `Edge Function returned a non-2xx status code`，或登录注册流程被秒哒自己包了一层后端函数。

```text
当前短信验证码登录失败。先确认失败层，不自建验证码校验或平台凭据签发器，不删除必要业务认证桥。

红线：
- 登录、注册、验证码、会话管理优先使用 Supabase Auth / 秒哒内置用户体系。
- 不要自己重新实现平台验证码校验、平台session签发、平台身份写入；既有业务会话与身份映射按已验证合同保留。
- 不要破坏现有用户表、权限字段和管理员判断逻辑。

任务：
1. 检查当前登录流程是否绕过了 Supabase Auth。
2. 若自写函数代替了平台验证码校验或凭据签发，先确认依赖再替换该职责；保留必要的服务端凭据验证、业务会话、sub绑定和权限检查，不因存在Edge函数就删除。
3. 改为 Supabase Auth / 秒哒内置用户体系支持的登录注册方式。
4. 完成后检查登录后用户身份、管理员权限、历史数据读取是否正常。

完成后请说明：
1. 前端现在调用的 Auth 方法或登录入口。
2. 保留的Edge认证桥分别负责什么，如何验证平台凭据及业务归属。
3. 如何测试登录、退出、重新登录和权限识别。
```

## 原生手机号 + 密码 + 短信：注册、登录、找回密码的一次性检查清单

**默认，适用场景**：秒哒项目用 Supabase Auth 原生手机号流程（`signUp({ phone, password })` 发短信 → `verifyOtp` 激活；`signInWithPassword` 登录；找回密码 `signInWithOtp` → `verifyOtp` → `updateUser`），或秒哒「登录」「短信验证码」技能生成的同类流程。新做或改登录时，**按下表一次性全部检查、全部修完**再上线，不要等用户撞到一个修一个。不适用于手机号拼邮箱的旧方案（见本页末"历史兼容"）。

第 1~8 行是本命音律 2026-10-22 对抗式审查一次查出的 8 个问题，第 9~14 行是同批界面问题。它们都是秒哒生成登录时常见的默认缺陷。

| # | 问题 | 怎么出现 | 正确做法 | 怎么验 |
|---|---|---|---|---|
| 1 | 手机号格式分裂账号 | `+86`、`86`、`0086` 前缀，或粘贴带空格、横线，被当成不同号码，同一人注册出两个账号 | 前端、服务端、数据库三层用**同一个**归一化规则：去掉非数字 → 去 `0086` / `86` 前缀 → 必须是 `^1[3-9]\d{9}$`；调 Auth 时统一拼成 `+86` + 11 位 | 用 `13800138000` 注册，再用 `+86 138-0013-8000`、`8613800138000` 登录，命中同一个用户 ID |
| 2 | 找回密码变成注册后门 | 对没注册的号走"忘记密码"，`signInWithOtp` 默认会**静默创建新用户**，绕过协议勾选 | 找回密码的 OTP 请求加 `options: { shouldCreateUser: false }`，没注册直接提示"该手机号尚未注册，请先注册" | 未注册号点找回密码 → 被拒绝（Supabase 返回 422），数据库没有新增用户 |
| 3 | 注册后密码和登录密码不一致 | 已注册的号再走一遍注册，`signUp` 静默复用旧账号、忽略新密码，用户之后用"注册时填的密码"登录报"密码不正确" | `verifyOtp` 成功后**再调一次** `updateUser({ password })`，保证注册时填的密码就是登录密码；这一步失败时要提示用户，不能静默吞掉（本命音律 v6 用 try/catch 忽略了失败，留有风险） | 已注册号用新密码再注册一遍，然后用新密码登录成功 |
| 4 | 输入框截断粘贴的号码 | `maxLength={11}` 时粘贴 `+8613800138000` 被截成 `86138001380`，用户看不出来 | 输入框不按 11 位截断（放宽到 16 左右）；输入时能归一成 11 位就直接替换显示 | 粘贴带 `+86`、空格的号码，框内显示正确的 11 位 |
| 5 | 登录漏校验密码长度 | 只在注册校验 ≥6 位，登录时直接提交，拿到难懂的报错 | 登录、注册、重置三处提交前统一校验 | 登录输 3 位密码 → 中文提示"密码至少 6 位"，没有发出请求 |
| 6 | 验证码按钮连点，重复发短信 | 网络慢时倒计时还没开始，连点发出多条，费钱且触发频控 | 请求中禁用按钮 + 同步锁（`useRef`，防同一帧两次点击）+ 成功后 60 秒倒计时 | 网络调成慢速后连点 5 次，只发出 1 条 |
| 7 | 手机号展示混乱 | 账号页、后台显示 `+8613800138000`，脱敏成 `+86****8000` | 展示一律用归一化后的 11 位；脱敏规则 `138****8000` 只对 11 位做 | 账号页、后台用户列表、"验证码已发送至…"三处格式一致 |
| 8 | 数据库存原始格式 | 触发器把 `auth.users.phone`（`8613800…`）原样写进业务表，唯一约束挡不住格式不同的重复行 | 数据库建 `norm_phone()` 函数，新用户触发器和历史数据都过一遍；业务表只存 11 位 | 查业务表 `phone` 列，没有带 `86` 前缀的值 |
| 9 | 英文原始报错直接给用户 | `Invalid login credentials`、`Token has expired` 原样显示 | 集中做一个错误映射：密码错误、已注册、未注册、手机号格式、验证码错误或过期、发送过于频繁，各有中文提示；未知错误给通用中文提示 | 逐个制造这几种错误，看提示是不是中文 |
| 10 | 协议勾选形同虚设 | 只拦"注册"不拦"获取验证码"；协议文字不是链接，或点开是空页面 | 注册时"获取验证码"和"注册"**都**要求先勾选；《用户协议》《隐私政策》是能打开的真实正文 | 不勾选点获取验证码 → 被拦下；两个链接都能打开正文 |
| 11 | 默认停在注册页 | 老用户每次都要先切 Tab | 默认显示**登录**，Tab 顺序登录在前、注册在后；登录页下方"还没有账号？立即注册"，注册页下方"已有账号？去登录" | 打开登录框，默认是登录 |
| 12 | 看不到自己输的密码 | 输错了不知道错在哪 | 每个密码框右侧放显示 / 隐藏切换（小眼睛），在 `password` 和 `text` 之间切换 | 点小眼睛能看到明文，再点恢复隐藏 |
| 13 | 手机上点输入框页面放大 | iOS Safari 对字号小于 16px 的输入框聚焦时自动缩放 | 输入框字号 ≥16px；手机端登录弹层贴底、全宽、留出安全区 | iPhone 上点手机号框，页面不缩放 |
| 14 | 字段顺序和后端流程对不上 | 注册短信是 `signUp(phone, password)` 发出的，界面却把验证码框放在密码前面，用户先点获取验证码，被提示"请先填密码" | 注册：手机号 → 设置密码 → 确认密码 → 验证码 → 勾选协议 → 注册；找回：手机号 → 验证码 → 新密码 → 确认新密码 | 按界面从上往下填，中途不会被要求回头补填 |

**一次性修复的提示词**（让秒哒按表自查自修；本地打增量包时，这张表就是验收清单）：

```text
请对当前项目的注册、登录、找回密码做一次全链路对抗式检查（前端表单 → Supabase Auth → Edge Function → 数据库触发器 → 后台展示），按下面 14 项逐项检查并修复。每项回报：现状、有没有问题、怎么改的、实测结果。
红线：继续使用 Supabase Auth 原生手机号流程，不自建验证码签发；不删除已有用户和业务数据；不改与登录无关的页面。
1. 手机号三层统一归一化（+86 / 86 / 0086 / 空格 / 横线 → 11 位），调 Auth 统一用 +86 前缀。
2. 找回密码的 OTP 请求加 shouldCreateUser: false，未注册号拒绝并提示先注册。
3. 注册 verifyOtp 成功后 updateUser 设置本次填写的密码。
4. 手机号输入框不截断粘贴内容，归一化后显示 11 位。
5. 登录、注册、重置都校验密码 ≥6 位。
6. 获取验证码按钮：请求中禁用 + 防重入 + 60 秒倒计时。
7. 所有展示统一 11 位，脱敏为 138****8000。
8. 数据库 norm_phone() 函数 + 触发器 + 历史数据归一（只做更新，不删行）。
9. Auth 报错全部映射成中文提示。
10. 注册时获取验证码和提交都要求先勾选协议；协议是能打开的真实页面。
11. 默认显示登录；登录在前、注册在后。
12. 每个密码框有显示 / 隐藏切换。
13. 输入框字号 ≥16px；手机端登录弹层贴底。
14. 注册字段顺序：手机号 → 密码 → 确认密码 → 验证码 → 协议。
完成后用测试号实测：三种格式登录同一账号、未注册号找回被拒、重复注册后新密码可登录、慢网连点只发一条短信；测完清理测试账号。只回报结果，然后停止。
```

**来源与状态**：第 1~8 行来自本命音律用户端 2026-10-22 秒哒对抗式审查回执（v6；回执自报"22 项单元测试通过"，但下载的源码里只有 1 个测试文件、11 项用例，22 项无法核实；线上实测项为回执自报，未独立复测），修复代码已在下载源码里逐项核对存在；第 9~14 行由同批界面审查补充，在本命音律 R2 增量包里实现，R2 上线前只有本地模拟接口测试。

## 会话刷新与浏览器锁竞争

**默认，适用范围**：秒哒项目实际使用 Supabase Auth，出现 `Lock broken by another request with the 'steal' option`、认证刷新卡住或未处理的 `AbortError` 时，先核对锁文件版本、浏览器 Web Locks 调用和真实调用路径。不能按“上传之后出现”就归因于 ZIP 损坏，也不能因本轮没有修改认证代码就排除继承缺陷和验收遗漏。

1. 对照增量 manifest 与上一基线的认证客户端、会话调用、package.json、锁文件字节，区分新增回归、继承问题与未知云端差异。记录首发时间、堆栈与网络时序；依赖内存在相关路径只证明机制可能，不能证明某次线上触发链。
2. 认证验收增加临近过期/已过期会话、慢刷新、同源多标签页和后台恢复。用真实浏览器 Web Locks 复现正常互斥与持锁被抢占，监听 pageerror、unhandledrejection，并验证页面能从加载态恢复。只注入一小时有效会话、令刷新请求立即成功，会漏掉此类竞争。
3. 区分锁等待超时、已持有锁被 steal、业务回调自身失败。任何自定义 auth.lock 都须保留互斥与原调用参数，锁回调只执行一次；不能用 no-op lock、失败后在锁外再跑 fn、全局吞 AbortError 或关掉自动刷新来掩盖故障。若将已确认的锁抢占错误转换为 SDK 支持的超时类型，需证明不会误吞 fetch/业务 AbortError；调用层提供有界恢复或可理解错误，不能把所有未知错误静默当成未登录。
4. 云端热修后按 [workflow 第8阶段](../workflow.md#第-8-阶段秒哒校验合并构建路径-b) 回收变更文件与哈希；未取回时明确保留热修文件及发布适配，不用本地旧全量源码覆盖。源码摘要不是逐字节基线证明。

**版本边界**：本次核验的 `@supabase/auth-js@2.103.1` 在 `navigatorLock` 的正超时分支会分类处理抢锁异常，但 `acquireTimeout=0` 的已持锁被抢占会透传原始 AbortError。该版本自动刷新 tick 使用 0；`getSession()` 使用配置的 `lockAcquireTimeout`（默认5000ms），不能照抄修复摘要说它固定传0。升级后重新审查，不把特定版本机制写成秒哒永久限制。来源与实测范围：[十一创导航R9复盘](./case-shiyichuang-r9-auth-lock.md)。

## 历史兼容：仅对已有手机号拼邮箱方案规范化

本节仅用于已经采用手机号映射 Auth email 的旧项目，不能用于原生 phone/OTP 项目，更不能把手机号存在当作已完成短信验证。新项目和言剪当前认证禁止为套用本模板新增邮箱旁路；唯一身份应按实际平台签发的稳定用户标识绑定，手机号仅按合同规范化。

**适用场景**：手机号裸号与 `+86` 写法被注册成两个账户；手机号登录偶发“密码错误”；旧用户兼容登录失败；注册成功但 session 为 `null` 后表单被清空。对应根因和验收清单见 [pitfalls.md #22](../pitfalls.md#22-手机号未做唯一身份规范化--86-与裸号变成两个账户--登录失败)。

**提示词模板**：

```text
请严格修复当前 Login.tsx 的手机号注册与登录一致性问题。本批只允许修改登录/注册相关的前端逻辑和既有的用户查询调用；不要修改订单、支付、权限、业务数据表或无关页面。

红线（必须遵守）：
- 手机号是唯一身份键，不是展示字符串。`+8613xxxxxxxxx` 与 `13xxxxxxxxx` 必须识别为同一个用户。
- 任何注册、登录、RPC 查询、catch 兜底、旧用户兼容、Auth email 拼接都禁止继续使用原始 input；只能使用规范化后的 normalizedInput。
- 不要在不同分支手写 `${input}@miaoda.com`、`phone_${input}@miaoda.com` 或其他 email 拼接；必须集中为一个 helper。
- 修改前先检查当前注册分支和已存在用户实际使用的 Auth email 公式。不要猜是 `phone_<手机号>@miaoda.com` 还是 `<手机号>@miaoda.com`，不要批量改写旧用户 email，也不要自动合并已有账户。
- 保持现有 Supabase Auth / 秒哒内置用户体系，不要新增自写登录 Edge Function。

任务：
1. 新建或复用 normalizeChinaPhone(raw)；清理空格和连接符，输入以 +86 开头时去掉 +86，最终只接受 11 位、1 开头的中国手机号。得到 normalizedInput 后，后续逻辑只传这个值。
2. 新建或复用 toPhoneAuthEmail(normalizedPhone)。它必须使用当前注册流程已生效的 email 公式；注册、正常登录、catch 兜底和旧用户兼容路径都调用它。
3. getUserByPhone 必须传 normalizedInput。RPC 异常进入 catch 时，也必须用 toPhoneAuthEmail(normalizedInput) 登录，绝不能使用原始 input。
4. 旧用户兼容路径的 getUserByUsername 必须传 normalizedInput；成功后的 Auth email 同样调用 toPhoneAuthEmail(normalizedInput)。
5. 注册成功但 session 为 null 时，自动切换到登录 Tab，并把 normalizedInput 预填进当前“用户名/手机号”表单字段；用户只需要补输密码。
6. 注册前先按 normalizedInput 查重，阻止 +86 与裸号再次产生两个新账户。

验收要求：
1. 用 13xxxxxxxxx 注册后，再用 +8613xxxxxxxxx 登录，必须命中同一个用户 ID。
2. 用 +8613xxxxxxxxx 注册后，再用 13xxxxxxxxx 登录，必须命中同一个用户 ID。
3. 模拟 getUserByPhone 抛异常时，catch 兜底仍能用规范化手机号登录，不能误报密码错误。
4. 旧用户兼容分支在两种输入格式下都能命中同一用户。
5. 模拟注册成功但 session 为 null 时，页面自动进入登录 Tab，手机号字段已预填规范化号码。
6. 输出实际确认的 email 公式、修改的文件/函数、未处理的旧账户迁移风险；不要只给 Summary。
```
