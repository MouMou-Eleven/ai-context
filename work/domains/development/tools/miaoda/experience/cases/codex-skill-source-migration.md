# 案例：Codex 调用秒哒 Skill，结合源码增量推进言剪迁移

日期：2026-09-25 起。记录对象：百度秒哒 `miaoda.cn`，不是飞书妙搭 Spark。本文件按发生顺序保存迁移经验，不维护当前产品进度。后文“后端未接入”“登录禁用”“R4上传受阻”等仅描述当时阶段，不代表当前状态；实际进度与未解决项统一读取[言剪项目入口](../../../../../../projects/yancut-ai/README.md#当前进度)。自动上传被安全审查拒绝后不得绕过，后续用户手动上传属于另一通道。

## 背景与目标

建委要求将言剪 AI 从现有 Next/Vercel 项目迁移到秒哒，优先修复工作台交互，再保留完整源码与功能逐步交接。目标不是让秒哒凭自然语言另造相似页面，而是由 Codex 修改、验证、分包，秒哒接收真实源码并适配云端环境。后续迭代以秒哒为目标，同时维护本地、GitHub 与项目上下文。

这是“外部 Agent 调秒哒”的 Skill 用法；与“秒哒应用调用模型或第三方内部 Skill”是两条不同方向。前者编排应用开发，后者属于最终产品运行时。

## 本轮实际分工与入口

|动作|本轮实测方式|不能据此推断|
|---|---|---|
|创建／查看应用与继续对话|官方CLI的chat、app及context绑定；使用fetchtrajectory读取执行轨迹|不能仅凭对话摘要认定源码已合并、构建或发布|
|上传源码ZIP与验收文件|浏览器filechooser实际选择本地附件|当前CLI没有attachment参数，不得把浏览器上传写成CLI上传|
|生成前置文档与触发应用生成|先让平台生成PRD文档，再由文档中的generateApp结构按钮触发一次generate-app|“文字说开始生成”不等于该结构动作已触发；不应重复点击创建并行生成|
|校验基线与增量|R1全量文件SHA-256，R2/R3旧目标hash逐层叠加复验|不能在未知云端目录上直接覆盖增量，也不能把包完整当作运行兼容|
|开启后端|需后端真实probe验证|按钮显示开启或模型声称成功，不等于数据库、存储、函数均可调用|

本轮网页附件界面显示每轮最多5件、每件20MB，因此源码与说明按批上传。该限制针对本次账号、日期和源码对话附件入口，不是所有秒哒版本或应用内部上传的永久上限。后续任务仍先看当前界面。

实际应用和会话标识、源码提交与交付状态保留在言剪项目修订中；此案例不复制凭据、内部网络地址或个人联系方式。

## 已执行的源码交接

R1是完整源码基线，不是增量。R1源码提交`cf9fd133`，包覆盖1488文件；R2基线为R1，目标`80d49a91`；R3基线为R2，目标`ba81b374`。R3是新增Vite壳、Deno基础服务和SQL事务合同的候选，不是47个原API全部迁完的产品。

本地执行顺序是：核对包级hash→恢复完整R1并校验每文件→叠加R2并验证旧／新hash→叠加R3并再次验证→冻结依赖安装→目标运行时构建。R3的37项增量在独立恢复树通过hash校验、Bun1.2.18冻结安装和Vite生产构建。Deno13项测试、前端8项／48断言、SQL隔离89项行为验证通过；这些记录不能替代云端真实服务验收。

源码包保留前端、原生产素材、WASM、workspace依赖、原API源码、数据库迁移和许可证，排除真实.env、密钥、依赖目录、构建输出及本机配置。每包有manifest，包外另有安装说明和可独立打开的问题验收清单。回包只读检查工具先核对ZIP路径穿越、重复路径、符号链接和秘密文件路径，再比较R3基线；不执行收到的云端代码，不输出可能含秘密的正文。

## 实际问题与纠正

### 1. CLI调用与上传不是同一能力

官方CLI承担应用／会话调度，附件上传实际依靠浏览器filechooser。正确记录应明确每步由哪个入口执行，不能概括为“Skill已经自动上传全部文件”。后续若CLI新增附件参数，需核验对应版本再更新，本轮不预判。

### 2. PRD会扩写没有源码依据的接口

本轮PRD出现不属于当前原项目合同的API描述，必须用原源码47条API清单逐项校正。PRD用于描述产品和迁移约束，不能反过来作为新接口已经实现的证明。对已有项目应让源码合同约束文档，保留未迁能力清单，不让平台用新造接口或假成功替代原链路。

### 3. 先有PRD，才核对结构化生成入口

本轮验证到生成前需先形成平台PRD文档，并由generateApp结构按钮触发generate-app动作。应确认文档版本、附件已齐、hash已过和本轮动作状态，再触发一次。当前记录不将“找到按钮／已具备触发条件”写成生成已完成，更不写成已publish。

### 4. 云端重新解析依赖不能冒充原锁验证

云端曾采用Bun1.4.2或pnpm重新解析依赖，导致与交付锁文件不一致。逐层hash核验使锁文件污染能够被发现，而不是带着不同依赖继续宣布原包构建通过。

本轮要求恢复交付锁，按声明Bun1.2.18重新执行冻结安装。最终回执没有足够证据认定云端复测通过；后续生成轨迹已在事件825以平台错误终止。应分别保存实际工具版本、安装参数、锁文件hash、退出码和构建结果；确需升级依赖时，把它作为明确变更生成新版本并重新验收，不能偷偷替换后沿用旧版本证据。

### 5. 运行时迁移与基础设施开启要分开验证

本次目标环境核验为Vite SPA + Supabase Deno Edge，原项目为Next16.1.3服务端应用，所以增加适配壳和服务端迁移层。不能把“有云端服务器／存储”推导为可原样跑Next、Chromium、Remotion或HyperFrames。

用户本轮新授权采用平台原生手机号Auth，覆盖先前自建密码／Bearer作为最终认证方向；尚未实测其注册、登录、会话和旧用户映射。授权代表允许实施，不代表已接入。后端开启同样需要真实probe，确认实际返回、权限和失败行为后再迁移数据。旧数据库、Blob、用户、积分账本没有因为上传源码而自动迁入。

## 本次形成的执行检查

适用：现有本地项目通过外部Agent／官方Skill进行秒哒源码交接，尤其是多轮增量和跨运行时适配。不适用：仅凭提示词新建小页面、没有权威源码基线，或飞书妙搭的应用发布。

1. 先绑定正确应用／会话context，读取轨迹确认当前阶段；不要往错误应用发送增量。
2. 先生成可复建全量基线，再交接增量。附件上传与CLI调度分别留证据。
3. 所有附件齐全、路径与hash验证通过后才进入适配。核对原源码接口清单，纠正PRD的擅自扩展。
4. 文档和结构按钮的状态分别判断，generate-app只触发一次；持续读取真实轨迹，未完成不标完成。
5. 云端与本地分别核对依赖版本、锁文件和实际构建。偏离锁文件须作为新变更审查。
6. 对Auth、数据库、对象存储和函数分别做真实probe；使用授权、开关状态、代码存在、服务可用是不同证据。
7. 接收云端修改回包后先静态检查并比较基线，确认范围再合入权威源码。正式域名真实版本、登录权限和剪辑导出通过后，才能称迁移验收完成。

## 追加执行事实：生成动作与平台故障

轨迹中已实际出现 `data.actions[].event.name=generateApp`（事件777），随后通过官方CLI调用一次`generate-app --app-id <同一应用> --context-id <同一会话>`，返回了对应标识。后续轨迹825却返回“服务暂时不可用，秒点已返还”，因此提交成功不等于生成成功。此前同一应用两轮chat也因平台错误终止；暂未publish。后续恢复先查app-detail与轨迹，不重复generate-app；既有项目继续用chat修复推进，避免重建丢上下文。

事件825错误类型为`ServiceUnavailable / MCPGenerateError GenerateStartHook unexpected error Response is not valid JSON`。随后同应用只提交chat恢复，没有再次generate-app；事件827请求、829运行、831回复“恢复迁移”均未证明恢复成功。最终17:58:40事件835为terminal true，仍返回`MCPGenerateError: GenerateStartHook unexpected error: Response is not valid JSON`及ValueError，用户可见平台遇到问题与秒点返还提示。此后本轮不再重复请求，不向未授权的客服发送消息。没有观察到完整云端锁文件构建或发布，不能用本地证据填补。

`app-detail`实测本实例`supabaseState.state`及`prodState`为`ACTIVE_HEALTHY`，且此前Edge服务端角色插入探针成功。这证明实例已启用并存在可执行写路径，不证明全部业务表、私有桶和短信认证已完成。私有对象存储上传/签名/清理、手机号注册与验证码接收仍待实际验证。

用户再次明确“生成需求文档”是进入网页生成流程的关键步骤；记录为本项目执行要求，并结合已读Skill的结构动作判断，不能把一句关键词当成平台已执行生成的证据。

## 用户接力上传后的校验与接线

适用场景：自动上传受阻、用户手动上传增量后，由代理继续核对应用结果。不能因为“用户上传成功”就省略完整性检查，也不能因为之前某轮失败就假定后续源码必然缺失。

本次 R4 于事件 1069 完成，先重建干净的 R1→R2→R3，1524 个基线文件全部通过，再应用 7 项变更，1528 个目标文件全部通过。旧工作树中的锁文件污染和缺文件被隔离处理，未直接覆盖。标记文件的 308 字节差异经查是 CRLF/LF 序列化不同：从可信 manifest 恢复原序列化并复验，未跳过哈希检查。这个原因只解释本次标记文件，不可推广为任意校验失败的豁免。

接力后的顺序仍然是读取终态、确认结果、再发送下一命令。1071 停止后才由 1076 启动后端与手机号认证接线，该轮随后在 1406 completed；未终止时仅读取进度，没有重复发生成指令。项目中的“生成需求文档”关键词与结构化生成入口继续保留，既有应用增量修复不重复 `generate-app`。

后端开关开启和官方登录技能已添加，与应用实际调用成功是不同检查项。本次 R4 只应用源码，未执行 SQL、未部署业务函数、未更新前端 API 配置，也未重建静态预览。因此旧页面显示后端未接入，不能仅修改提示文字掩盖。下一步应分别核对数据库迁移、Edge Function 响应、前端地址与鉴权、短信会话、管理员与积分归属。

静态产物也必须独立验收：改源码后重新构建，确认根入口载入新版本；`base=/yancut/` 加上拷贝目录可能使绝对资源路径重复。本次品牌图片请求 `/yancut/brand/`，需实际返回图片而非 HTML 或落到 `/yancut/yancut/brand/`。这条经验适用于具有静态构建与子路径发布的当前方案，不要求所有秒哒应用使用同一目录结构。

最新业务和品牌交付状态仍以[言剪迁移修订](../../../../../../projects/yancut-ai/revisions/2026-09-25-miaoda-source-migration.md)为唯一入口；旧 Vercel／Neon 和本机原片不因接线操作被改写。完整登录、AI、识别、导出链路和真实付费调用未验收前，不称全项目迁移完成。

后续 R5 再次在独立恢复目录检验 R4→R5，完整目标哈希、篡改拒绝、CRLF 标记语义、声明版本冻结安装和构建均通过。本地品牌管理交互使用模拟 API，仅证明前端行为，不证明云端数据库持久化。1076 执行过程中出现“已完成迁移／尝试部署”文字，也出现 Deno.lock v5 与模块缺失启动问题；应继续等终态并独立请求接口，不能挑选成功片段当作最终结果。新包仍由用户手动上传，不因后续 CLI 对话可用而推断 CLI 支持附件。

1406 的完成报告仍保留 36 个未迁 API、私有存储与真实短信待测、未正式发布等缺口。随后源码复核又发现“手机号存在”被当作“完成短信验证”：在该环境启用 `phone_autoconfirm` 时，两者不等价，尤其不能直接据此认领首个管理员。统筹等该轮完成后才提交下一轮安全修复，要求检查经签发方验证的会话及 OTP `amr` 证明，并关闭旧注册旁路。适用的检查原则是把页面、身份资料、凭据验证、业务归属和管理员权限逐层验收；不将本次环境的具体字段或某个通用 JWT 解析结果直接当作所有平台的认证方案。

后续 1408→1519 只完成代码修改，没有部署；1521→1579 才报告部署与外部探针。fixture 通过、函数部署和有效凭据的实际请求是三层证据。特别是测试用户已清理后的 password-only 请求返回 401，不能单独证明有效 password-only 凭据被新门控拒绝。最终真实短信仍未测试，首管保持未认领；完整云端修改只返回 sandbox 包路径，未下载检查前不视为已同步源码。后续增量需先回收并比较云端安全修改，避免正确应用旧基线包却覆盖新安全门。
