# Codex 辅助秒哒开发工作流

> 来源：2026-06 德锦周锦网站整改提示词迭代。该经验不只适用于备案整改，而是适用于“用户在秒哒云端开发中遇到问题，把问题交给 Codex，Codex 产出低风险、可执行的秒哒提示词，再由用户粘贴到秒哒执行”的通用协作模式。

## 先判断走哪条工作流

- 项目已经在秒哒云端，Codex 不能直接读取权威源码：继续使用本文的“证据 → 分批提示词 → 秒哒执行 → 反馈迭代”。
- Codex 已在本地直接开发并验证权威源码，需要交给秒哒生成和部署：改读 [codex-source-package-deployment.md](./codex-source-package-deployment.md)，先做运行时闭包、分包、哈希和对象存储交接。

不要把本地源码交接简化为普通提示词迭代，也不要让秒哒在文件未收齐时先行重写。

## 核心定位

秒哒是云端 AI 应用开发平台。用户通常不能像本地代码仓库一样直接打开所有源码、数据库、后端服务和部署环境，而是主要通过秒哒对话框让平台 AI 修改当前项目。

因此，Codex 在这个工作流里的价值不是“直接替秒哒改云端代码”，而是：

1. 吃透用户的真实问题。
2. 结合 AI Context 仓库里的秒哒经验，判断秒哒容易在哪些地方误改、漏改或自由发挥。
3. 把问题拆成秒哒能稳定执行的小批次。
4. 写出可以直接粘贴到秒哒对话框的提示词。
5. 明确每批“只许改什么、严禁动什么、完成后怎么回报”。
6. 用户把秒哒执行结果反馈回来后，Codex 再继续诊断和修正下一轮提示词。

这个流程的目标是降低秒哒执行出错率，让“Codex 负责分析和提示词工程，秒哒负责云端项目修改”形成稳定配合。

## 什么时候使用

| 场景 | 是否适用 |
|---|---|
| 秒哒项目里出现 bug，需要修复但不能乱动其他功能 | 适用 |
| 秒哒项目需要新增功能，但要保护已有支付、订单、登录等稳定能力 | 适用 |
| 需要调整公开文案、SEO、页面结构、栏目、样式 | 适用 |
| 需要接入第三方接口、支付、上传、通知等高风险能力 | 适用，但要优先查对应专项处方 |
| 用户只想让 Codex 直接改本地代码仓库 | 不适用，走普通代码开发流程 |

## 角色分工

| 角色 | 负责什么 | 不负责什么 |
|---|---|---|
| 用户 | 描述问题、提供截图/报错/秒哒执行结果，把 Codex 产出的提示词粘贴到秒哒 | 不需要自己设计技术方案 |
| Codex | 读取 AI Context、分析问题、拆任务、写秒哒可执行提示词、设计验收清单 | 不直接假装自己能访问秒哒云端项目内部状态 |
| 秒哒 AI | 在当前云端项目里执行修改、返回改动摘要 | 不负责长期记忆和跨轮规划 |

## 标准工作流

### 1. Codex 先确认问题类型

先判断用户的问题属于哪一类：

- 内容整改：文案、SEO、分享、栏目、主体口径、页面说明。
- 前端体验：布局、样式、移动端、交互、显示异常。
- 数据展示：列表、详情、筛选、排序、后台字段映射。
- 后端能力：Edge Function、密钥、第三方接口、支付、上传、通知。
- 交易链路：购物车、订单、退款、支付状态、售后。

不同类型的提示词拆法不同。不要把所有问题都套成同一种“请检查并修复”。

### 2. Codex 查相关经验

进入 Miaoda 目录后优先看：

- [llms.txt](../../llms.txt)：决定该读哪篇。
- [prompt-patterns.md](../prompt-patterns.md)：通用提示词写法。
- [pitfalls.md](../pitfalls.md)：秒哒常见坑。
- `patterns/*.md`：专项处方，如 SEO、大视频上传、内容整改。
- 具体案例文件：如支付接入案例。

如果用户明确说“我之前在 GitHub 里写过秒哒经验”，必须先读这些资料，再写提示词。

### 3. Codex 收集当前证据

能查到的尽量查，不要凭空猜：

- 当前线上页面、页面源码、SEO/分享 meta。
- 用户提供的报错、截图、秒哒返回摘要。
- 秒哒预览页面的可见现象。
- 相关平台文档或 AI Context 里的既有经验。

对于不能直接确认的云端内部状态，要在提示词中要求秒哒自己检查并回报，不要让 Codex 假装已经确认。

### 4. 先划边界，再拆任务

Codex 产出提示词前，必须先明确：

- 本次允许改哪些范围。
- 哪些能力绝对不能动。
- 哪些数据不能删。
- 哪些关系不能编造。
- 哪些功能必须保持可用。

然后按风险和依赖关系拆批：

1. 先改最孤立、最高风险、最容易验证的部分。
2. 再改公共组件。
3. 再改单页或单模块。
4. 最后做残留清理和验收。

### 5. 每批提示词要能独立执行

秒哒没有可靠的长期规划能力。每一批都要自包含，但不是靠废话自包含，而是靠重复核心口径：

- 本批只改什么。
- 严禁改什么。
- 具体新文案或代码策略是什么。
- 完成后必须输出哪些检查结果。
- 完成后停止。

不建议写：

- “你是百度秒哒 MIAODA 项目内置开发助手。”
- “不要依赖上一轮对话记忆。”
- “请访问某某网站。”
- “先分析一下再告诉我怎么做。”
- “第 0 批先做检查。”

除非用户当前目标就是诊断，否则第一批应是可执行的修改批。

### 6. 用户逐批粘贴到秒哒

用户不要一次性把所有批次发给秒哒。建议节奏：

1. 粘贴第 1 批。
2. 等秒哒执行完成。
3. 在预览环境检查关键页面。
4. 保存秒哒输出摘要或截图。
5. 如果正常，再发下一批。
6. 如果异常，把秒哒输出和现象交给 Codex，Codex 重新写修复批。

### 7. Codex 根据执行结果迭代

如果秒哒执行后出现问题，Codex 不要直接继续原计划，而要先判断：

- 秒哒是否改错范围。
- 是否误删数据或隐藏了过多内容。
- 是否只改了 index.html 但漏了运行时页面。
- 是否新建了不必要的接口或函数。
- 是否破坏了已有支付/订单/登录/上传链路。

然后写“修复批”提示词，要求秒哒回滚错误范围或做最小修复。

## Codex 交付物格式

面对秒哒问题，Codex 最好交付这几类内容：

1. **执行顺序**：告诉用户先发哪一批、每批发完看什么。
2. **分批提示词**：每批一个代码块，可直接粘贴到秒哒。
3. **验收清单**：用户在秒哒预览里逐项检查。
4. **人工确认项**：哪些身份、法律关系、密钥、支付参数不能由 AI 编造。
5. **异常回传要求**：如果失败，用户需要把秒哒摘要、报错、截图或页面现象发回来。

## 通用提示词骨架

```text
请严格、严谨、认真、负责地完成本批任务。不要编造，不要夸大，不要自行扩展任务。

本批只修改：
<允许修改的范围>

严禁修改：
- <不能动的功能/数据/配置>
- <不能动的功能/数据/配置>
- <不能动的功能/数据/配置>

目标：
<本批完成后应该达到什么状态>

请按以下方式修改：
1. <具体动作>
2. <具体动作>
3. <具体动作>

完成后请只输出：
1. 修改了哪些文件、页面或配置。
2. 哪些风险点仍未处理。
3. 是否未修改严禁修改的范围。
4. 需要人工确认的事项。
完成后停止。
```

## 按问题类型拆批的经验

### 内容 / SEO / 主体口径

参考：[content-rectification-prompts.md](./content-rectification-prompts.md)

优先顺序：

1. SEO、分享、JSON-LD、隐藏平台文案。
2. 导航、页脚、公共组件。
3. 首页首屏。
4. 高风险主体页面。
5. 关于页/人物页。
6. 商品/详情/售后主体。
7. 资讯/文章/出版物。
8. 残留风险词清理。

### 前端 UI / 移动端问题

优先顺序：

1. 只改样式和当前组件，不动数据加载。
2. 保持桌面端已有效果。
3. 单独要求秒哒检查移动端菜单、按钮、弹窗、滚动区域。
4. 如果问题难复现，让秒哒加临时可复制日志面板，并要求上线前隐藏或移除。

#### 云端动态问题诊断的正确分工

秒哒的开发、构建和发布都在云端完成，但秒哒 AI 不能像 Codex 一样控制真实浏览器、手机或 Playwright 完成动态复现。不要把 Codex 的本地调试流程原样写进秒哒提示词。

正确闭环：

1. Codex 根据现象定义需要记录的状态、事件和采样频率，并写成窄范围诊断提示词。
2. 秒哒只在当前云端源码中加入临时应用内日志面板，完成它能执行的静态检查、测试和构建。
3. 用户在秒哒预览版或已发布版本中手动复现问题，点击“复制全部”或“下载 JSON”。
4. 用户把日志交给 Codex；Codex 基于真实状态转换定位根因，再写修复提示词。
5. 问题确认解决后，秒哒隐藏或删除诊断 UI 和高频采样代码。

禁止做法：

- 不要要求用户先手工拼接 `?debug=1`、`?enemyTrace=1` 才能看到诊断入口；诊断版本应直接显示临时按钮。
- 不要要求秒哒“打开浏览器、自动点击、运行 Playwright、完成真机验证”；它只能回报源码检查、测试和构建结果。
- 不要只写 `console.log`。手机端主证据必须进入有容量上限的应用内日志缓冲，并支持复制或下载。
- 不要逐帧打印。记录状态转换、异常事件和限频快照，避免日志本身造成卡顿。

### 支付 / 订单 / 退款

先读：

- [case-yungouos-jsapi.md](../cases/yungouos-jsapi.md)
- [pitfalls.md](../pitfalls.md)

原则：

- 原有稳定支付链路一行不动。
- 新增通道必须按 `pay_channel` 或等价字段分流。
- 密钥不进前端、不进源码、不进日志。
- 每个新 Edge Function 先验证环境变量名。

### 上传 / 存储 / 大文件

先读：

- [large-video-upload.md](./large-video-upload.md)

原则：

- 先确认会员与对象存储容量：免费版单文件 50MB，专业版及以上 500MB；付费项目要同步修改前后端限制。
- 用接近真实业务大小的文件验证当前环境，不默认沿用旧的永久分片结论。
- 平台原生上传通过时，优先使用当前原生能力或云存储原生 multipart / 断点续传。
- 只有旧项目仍复现 CORS / 413 / supervisor kill 时，才启用旧的永久分片 + Range 代理，并把参考实现路径塞进提示词。

## 反面模式

这些写法会降低秒哒执行稳定性：

```text
你先帮我完整分析一下这个网站，然后告诉我怎么改。
```

问题：用户想整改时，这会让秒哒产出分析文本或乱扫项目，而不是直接执行最关键修改。

```text
你是百度秒哒 MIAODA 项目内置开发助手。请不要依赖上一轮记忆。
```

问题：这是对外部 Agent 有意义的提示，不是秒哒当前项目执行的关键约束。

```text
帮我把这个功能修好，不要影响其他功能。
```

问题：范围太大，没有指出哪些不能动，秒哒容易顺手重构。

```text
把我这份方案全部一次性改完。
```

问题：任务太大，秒哒容易中途漏改、误改、总结过度乐观。

## 正向模式

```text
请严格、严谨、认真、负责地完成本批任务。不要编造，不要夸大，不要自行扩展任务。

本批只修改 <明确范围>。

严禁修改：
- <明确不能动的功能>

请把 <旧文案/旧逻辑> 改为 <新文案/新逻辑>。

完成后请只输出：
1. 改了哪里。
2. 是否还有残留。
3. 是否未动禁改范围。
完成后停止。
```

这种写法更像工单，秒哒更容易稳定执行。

## 沉淀规则

每完成一次“Codex 出方案 -> 用户贴给秒哒 -> 秒哒执行 -> 用户反馈结果”的成功流程，都应该考虑回写：

- 新坑：补到 [pitfalls.md](../pitfalls.md)
- 新提示词片段：补到 [prompt-patterns.md](../prompt-patterns.md)
- 可重复的复杂流程：补到 `patterns/*.md`
- 完整案例：新建 `case-*.md`

如果这次经验不是某个具体功能，而是“怎么让 Codex 和秒哒配合得更稳”，就补到本文。
