# Codex × 百度秒哒版本化增量迭代闭环

> 状态：当前有效
> 适用平台：百度秒哒 MIAODA（`miaoda.cn`、`*.appmiaoda.com`）
> 最近整理：2026-09-25；明确本地权威源码、附件与调度通道、串行验收及云端回包用途；保留每包独立的问题对照与手动验收清单

## 适用场景

适用于“Codex 在本地权威源码修改、测试并打包，用户上传，秒哒按包应用和适配云端环境，Codex 根据回执与实际产物复核”的长期项目。不能把它理解为 Codex 只写长提示词、秒哒自由重写、最后再整理。每轮改动都必须可追踪、可验收、可回滚，不能只依赖秒哒的一段完成摘要。

这不是飞书妙搭发布流程，也不把秒哒当 Git 仓库。职责边界如下：

| 角色 | 负责 | 不负责 |
|---|---|---|
| 用户 | 描述现象、上传增量包、提供线上截图和回执 | 不需要自行设计技术方案 |
| Codex | 读取上下文、诊断、改权威源码、测试、审查、打包、生成验收清单 | 不假装已访问秒哒内部源码或数据库 |
| 秒哒 | 接收增量包、合并源码、执行迁移、构建和部署 | 不负责跨轮记忆、版本治理或证明正式域名已切换 |

### 交接通道、串行规则与文档用途

2026-09-26 用户明确补充成本约束：源码导出会扣积分，**不得默认每轮索要全量导出**。已知完整源码加历次实际交付 ZIP 是本地重建基线；新包校验待替换文件的 before/after hash，云端环境配置作为保护项不覆盖。秒哒摘要、任务数、“修复成功”只作线索，不能作为已完成标准；用户真实操作失败应重新打开该问题。已知热修若仅涉及本轮不改的配置，明确保留即可继续；仅当实际待改文件出现无法解释的差异时，请求那几个具体文件/哈希或错误日志，不升级为每轮全量导出要求。无法还原的冲突不能猜写，也不能用“需全量源码”停止所有独立可做工作。

2026-09-25 建委再次确认：最初按 01、02 等编号上传完整基线，后续每轮按问题交付增量包。同应用冲突的云端写入串行；同批多包一次接收后顺序应用，不要求用户逐个子包回传。其间可本地独立开发，失败问题保留编号和状态。

- Skill/CLI 调度与附件上传是两种能力。当前百度 `miaoda-app-builder` CLI 仅暴露文本 chat 等命令，无附件上传参数；早期浏览器上传成功不证明 CLI 支持上传。浏览器操作受自动审批阻止时，由用户手动上传，不绕过拒绝，也不改成长提示词替代源码。
- 初次生成需需求文档与结构化生成入口；既有应用不重复 `generate-app`。后续仅在需求变化时更新相关文档，不要求每轮重写 PRD，不因文档生成失败反复重做已完成代码。
- 提示词只说明包版本、基线、允许改动、校验、迁移与验收顺序；实现以包内代码为准。云端必要适配须有差异记录，回收到本地后才作为下一轮基线。
- 默认回报执行结果，无需每轮输出 ZIP。只有云端实际改了本地没有的代码，或确需审查证据时，才输出无密钥差异包。Codex 收到后实际解压、检查、测试并吸收或明确拒绝；拿不到文件时标明尚未完整审查。SQL 创建成功、mock RPC 测试通过，都不能替代真实数据库成功路径验证。
- 每轮报告相对目标能力的进度：哪些仅有页面、哪些接口已通、哪些真实业务已验、哪些未迁；R5 等序号不是完成百分比。剩余批次为可调整计划，不能当成固定上传次数承诺。

适用证据见[言剪源码迁移案例](../cases/codex-skill-source-migration.md)及其项目修订；用户指定参考任务为 `01a075eb-f731-7583-92b7-2a9f830a7484`。纯提示词新建小应用不强套完整源码增量流程。

## 一次交付批次与有效完成

2026-09-26建委确认：保持“反馈问题→Codex修改测试→交付代码包→上传验证”。适用于已有源码的持续迭代或跨平台迁移；仅查状态、套餐及用户接受的无源码提示词开发不适用。

- 功能阶段、ZIP编号、上传轮次分开。R8/R9/R10是内部范围，不必各占一次上传；总验收默认是清单与测试，不增加重复覆盖前包的总包。
- 同批多包一起交付、一起上传、顺序应用。标明batchId、依赖、文件归属、前后hash和唯一manifest。依赖失败暂停后继应用，云端冲突写入仍须串行；其间可继续本地独立开发。
- 用户2026-09-26报告其入口一次可上传5个ZIP、每个20MB；当前按此约束，建议单包低于19,000,000字节留余量。仅描述当前账号、日期、入口，不推成永久平台限制。
- 安装、迁移、校验、回滚随代码同包交付；另给可打开的问题清单。不得先让用户上传纯说明、等勘察后才开始本可本地完成的实现；纯文档ZIP不是功能增量。
- 测试使用目标实际文件、包内相对路径及声明依赖，禁止作者电脑绝对路径、未交付临时目录和全局包。在另一干净目录解压应用复测，不能只测开发树。
- 维护一个可重建源码基线，记录原站参照commit、交付基线、云端差异和待吸收项。临时目录不冒充已推送源码；基线对齐由Codex负责，不默认要求用户付费全量导出。
- 未知差异只暂停会覆盖它的目标，其他独立开发继续。相关修复可以和后续实现合批，原问题编号及失败状态必须保留，不能换号掩盖。
- 最大还原按能力矩阵验收：原实现/依赖、迁移文件、目标接口、自动测试、线上实测逐项对应。原站未完成项单列，不删功能、假成功或占位凑数；缺Key、会话或外部Worker保留真实边界。

可观察检查：ZIP含实现；干净解压可复测；依赖顺序可复现；没有作者路径；原能力有去向；入口与最新回执一致；推送hash与报告一致。路由命中仅证明触发，不代表迁移功能已通过。来源见[言剪批次修订](../../../../../../projects/yancut-ai/revisions/2026-09-26-batch-delivery-and-effective-context.md)。

## 版本和包命名

每轮都必须产生唯一版本号，推荐：

```text
<project>-JW-YYYYMMDD-R<序号>-<topic>-v<包格式版本>.zip
```

例如：`jianwei-JW-20260906-R8-dynamic-types-video-docs-increment-v4.zip`。

规则：

1. `R` 序号只递增，不复用已经交给用户的编号。
2. 同一版本拆成多个包时，每个包都使用唯一 manifest 文件名。
3. 禁止使用“最新版”“最终包”“修复包”等不可追踪名称。
4. 版本说明必须写明基线版本、改动范围、未改范围和数据库迁移状态。
5. 线上尚未确认切换时，不能把“已上传”标为“已发布”。状态至少区分：已生成、已上传、已合并、已构建、已部署、已验收。

## 增量包合同

增量包只放本轮需要交给秒哒的文件，至少包含：

- 可覆盖到项目中的相对路径文件；
- `MIAODA-PACKAGE-MANIFEST-<version>.json`；
- 变更说明和禁止修改范围；
- 数据库迁移脚本或明确的“无需迁移”；
- 秒哒执行提示词；
- 验收清单和回滚说明。

### 问题对照与手动验收清单（每包必交）

建委于 2026-09-16 明确要求：每次制作秒嗒增量包，除了 ZIP，还必须交付一份可单独打开的「问题对照与验收清单」，方便他逐项手动验证。不能只把清单藏在压缩包里，也不能用开发摘要代替。

1. 将本轮问题与尚未完成的前轮问题合并编号，保留用户截图序号和原始现象。新补充的问题追加进入同一清单；前轮已交付的改动列为回归项，避免重复实施或遗漏。
2. 每项写清：问题编号、对应截图或需求、修改后的行为、访问入口、操作步骤、预期结果、实际验证结果，以及供用户填写的验收状态。测试账号角色、前置数据和分页边界等必要条件应写明。
3. 区分「代码已修改」「本地已验证」「等待云端迁移/部署」「用户手动验收通过」。模拟接口、静态检查和构建通过不能标成真实云端通过；失败、未测试及限制须保留。
4. 安装说明、ZIP、manifest 和清单使用同一版本号。最终回复分别提供增量包、安装说明、问题清单的链接；秒嗒回执也按同一编号报告结果。
5. 用户反馈未通过后，沿用原问题编号追踪原因、修复和复验；拆包时明确每个问题落在哪个包，不用一句「全部已修复」关闭尚未验收的项。

建议表头：`编号 | 截图/原问题 | 改后行为 | 入口与操作 | 预期结果 | 已做验证/待验证 | 用户验收`。步骤较多时按编号展开段落，不强行塞进宽表。

manifest 每个文件至少记录版本、基线、路径、字节数和 SHA-256：

```json
{
  "version": "JW-20260906-R8",
  "baseVersion": "JW-20260906-R7",
  "baseSource": {"kind": "git-commit-or-full-archive", "reference": "<对应全量源码commit或存档路径>", "sha256": "<全量存档时填写其SHA-256；Git基线记录commit>"},
  "package": "jianwei-JW-20260906-R8-dynamic-types-video-docs-increment-v4.zip",
  "files": [{"path": "src/pages/Admin/Works.tsx", "bytes": 12345, "sha256": "..."}],
  "databaseMigration": "required|not-required|manual-review",
  "createdAt": "2026-09-07"
}
```

交付门禁：增量包只含变更，不能单独解压到空目录后执行安装或构建。先准备可重现的 `baseVersion` **全量源码树**，再叠加本轮增量，得到完整目标版本后才能复跑安装、检查和构建。

干净复建顺序：

1. 在独立干净目录还原 `baseVersion` 对应的Git commit或全量存档；核对基线来源与commit/存档哈希。仅有一个名称、未知内容的线上目录或缺失全量基线时，不能判定可复建。
2. 先校验增量manifest、包内相对路径、文件字节数与SHA-256，再覆盖到还原树；新增文件不得漏项，删除/重命名必须明确登记与核对，不能靠解压自动完成删除。
3. 叠加后对manifest中的目标路径再次校验字节数与SHA-256，确认基线未被其他本地修改污染、未漏依赖/锁文件/迁移/资源；如有完整目标树清单，同时核对它。
4. 在**重建的完整目标树**按项目锁文件安装依赖，再跑TypeScript、静态检查、相关测试与生产构建；增量包自身不要求含完整package.json和全部依赖。
5. 保存基线标识、增量版本、校验结果与实际命令输出。任一步失败停止交付，不用当前开发目录的通过结果替代干净复建。

若交付的是完整源码包，则按 [全量源码分包部署](./codex-source-package-deployment.md) 解压全部编号包并复建；不要混用全量与增量合同。

默认排除 `node_modules`、`dist`、日志、截图、缓存、密钥、原始母版、未引用素材和本机部署配置。

## 每轮标准流程

### 执行卡与恢复检查：先全局，再处理当前问题

每个实际项目维护一份当前执行卡，放在项目自己的状态记录中；本方法只定义字段，不另存第二份项目进度。开始、长任务恢复、换轮以及交付前读它，不能只接着最后一条报错跑。

| 必填信息 | 检查动作 |
|---|---|
| 本轮目标、验收标准、明确不做的事项 | 确认仍是用户最新要求；只查能力不启动修改 |
| 应用/会话、目标环境、基线和本批版本 | 与实际回执对应，不能把预览当生产或拿旧包覆盖云端差异 |
| 当前阶段与上一轮终态 | 区分准备/已上传/执行中/待取证/待验收/通过/失败/取消；执行中不发下一命令，取消不自动重发 |
| 本次已读规范及采用动作 | 能力边界、增量合同、实际涉及的专项规则；标题或路径命中不算正文已读 |
| 未解决问题、取证需求及责任方 | 每个问题保留编号、阻塞影响、证据和下一步；未取得回包不能标已审查 |
| 已验证结果、未验证范围、下一步 | 本地测试、云端回执和正式站验收分开，不靠包序号估完成度 |

进入技术细节前，先判断它是否阻塞本轮验收；非阻塞项留在问题清单，不顺手扩大改动。遇到重复错误且没有新证据，停止同样重试，改为取得缺失日志、源码或环境信息；不要靠再发一长段提示词碰运气。关键材料缺失时可继续不依赖它的工作，但不发布依赖缺失材料的增量。

交付前逐项对照执行卡关闭本轮验收项，未过的保留到下一轮；下一轮先看未解决清单和新反馈再实施。规则变更只改唯一正文，并同步入口与已知冲突引用；历史记录标明适用版本和被替代部分，避免不断追加后出现多个“当前规则”。

### 增量包内的云端取证与回传合同

2026-09-25 建委确认：本地制作下一包所需的云端数据，可以随本轮增量包写好采集要求，让秒哒执行时输出，再由用户回传辅助交叉验证。不是每轮固定导出全部源码或数据库，也不是只有截图才能反馈。

每包按实际问题携带一份 `EVIDENCE-REQUEST-<version>.md`，必要时附经过本地审查的只读查询或检查脚本；执行范围写入 manifest/INSTALL。内容包括：

1. **目的和范围**：为验证哪个问题、哪一批基线，需要哪些具体文件、接口、表结构或约束；禁止自行扩大到全库导出。
2. **执行时机**：基线/哈希在改前采集；本轮代码和数据库验收在改后采集。先校验附件与基线再按安装说明执行，不因取证要求擅自改业务或发收费请求。
3. **必要输出**：应用与版本标识、采集时间、文件路径/字节数/SHA-256、实际改动列表、迁移编号和状态、检查命令/退出码/结果；数据库按需给 Schema、函数定义、约束和脱敏统计，不索取密钥、Token、密码哈希或用户原始数据。
4. **回传形式**：简短的非敏感结果直接写最终回复，便于 Skill 读轨迹；需要完整文件的部分输出一个有清单和哈希的无密钥审查包。已有文件能满足就引用并回传，不重复生成无用途文档/ZIP。
5. **停止条件**：失败、权限不足、文件缺失或结果超长时明确回报，不编造成功或自动补建数据。当前轮结束后停止，等待审查，不能自行启动下一增量。

Codex 收到后核对版本与目标、路径安全和哈希，比较本地基线与云端差异；SQL 同时检查真实成功/失败路径，不能只读“迁移成功”。记录证据是“云端回执”“本地独立复现”还是“正式站实际验证”，避免同一模型自报结果被算作两份独立证据。若只有 sandbox 路径且当前 Skill 无读取命令，由用户回传；若实际内联了完整正文，则可直接审查，但仍检查截断和版本。

可随包采用的短执行要求：

```text
完成本批安装与测试后，按 EVIDENCE-REQUEST-<version>.md 采集指定证据。
最终回复写明实际版本、每项检查结果、失败与未执行项。
需要回传的完整文件按清单打一个无密钥审查包，列出路径、字节数与SHA-256。
不要输出未要求的全库数据，不要额外生成需求文档，不要启动下一批。完成后停止。
```

该合同适用于已有权威源码的跨环境增量验证；纯文案修改没有数据库变化时不额外要求数据库取证。Skill 当前实际读取能力见[能力矩阵](../../development/skill-as-callable.md#本机已安装版本的能力核查2026-09-25)。

### 1. 先确定事实和基线

读取项目 README、上轮版本说明、数据库变更记录、截图和秒哒回执，确认：权威源码、用户认为的线上版本、实际线上版本标记、允许修改范围，以及不能动的登录、支付、订单、权限、上传和历史数据。

### 2. 在权威源码修复并回归

前后端一致性问题必须沿着“录入 → 保存 → 查询 → 渲染 → 预览/发布”检查。对作品类型、分类、行业、版权、AI 标记、描述、所属单位、精选时间、附件和下载权限等字段，建立字段矩阵：后台字段、数据库列、公开 API、列表、详情、预览和空值处理逐列对应。前端显示不等于后端已保存，后端字段存在也不等于公开端已渲染。

### 3. 生成增量包

只收集本轮修改文件和必要新资源。不要让秒哒在文件未齐时自由重写，也不要用占位图、猜测字段或重建表补缺失内容。

### 4. 秒哒先校验，再合并和部署

提示词必须要求：核对当前云端版本是否匹配baseVersion及全量基线，校验增量路径/字节数/SHA-256；失败立即停止，不强行套到不同版本。通过后建立可回滚版本、在完整基线树上叠加增量并再次校验目标文件，再执行约定迁移、安装、检查、构建与部署，回报实际结果。

### 5. 正式域名真实验收

“执行成功”“构建成功”“发布完成”都不是正式域名已切换的证明。必须检查：

- `/jianwei-release.json` 或项目约定的 release manifest；
- HTML 的 `data-release` 或等价版本标记；
- 实际 JS/CSS/CDN URL 是否属于本轮版本；
- 真实浏览器 DOM 是否包含新增字段和交互；
- Console、网络状态码、MIME、缓存、CORS、权限行为；
- 未登录、普通用户、管理员、移动端和无痕窗口。

manifest 已更新但 HTML 仍引用旧资源，或页面仍显示旧 `data-release`，应判为“回执成功但正式域名未切换”。

### 6. 反馈闭环和状态保留

用户反馈后先分类根因：未上传、未合并、未迁移、未构建、未切换、缓存、权限、数据映射或视觉回归。每轮保留版本、基线、现象、根因、改动、验证结果、遗留风险和下一步，不用“已解决”覆盖中间状态。

## 专项验收

### 视频和静态资源

先按当前套餐和对象存储能力测试原生上传、Range、MIME、CORS、缓存、拖动和弱网恢复。原生能力可用时优先使用平台或对象存储 multipart/断点续传；旧环境只有在仍复现已验证限制时才用兼容性的分片和 Range 代理。不能靠删素材、压低画质或 Base64 掩盖问题。

### 预览和正式发布

预览必须使用与正式发布相同的数据读取、渲染组件、权限分支、媒体 URL 和 CSS 入口。至少覆盖真实记录、空字段、长文本、附件、视频、移动端和未登录状态。

### 数据库迁移

每次新增字段、枚举、索引、权限或表，都交付迁移顺序、旧数据默认值、回滚方式和迁移后查询验证。只改前端类型或只创建迁移文件但未在秒哒环境执行，都不算完成。

### 托管网关与云端热修复

数据库表达式验证与实际托管网关验证分别执行；GET可读不证明相同过滤器能用于PATCH。用户已通过秒哒自动修复的问题，必须先吸收回执或最新源码，再制作增量包；保留云端其他改动，明确未知差异。测试须覆盖旧失败请求及修复后的保存重载，不以构建成功替代线上写入。2026-09-15的具体证据、预读与并发边界见[踩坑 #28](../pitfalls.md#28-patch-的-json-路径过滤触发网关白名单错误被误读为数据库缺列)。

### 构建时公共环境变量与跨层契约

前端代码、云端构建脚本、Edge 参数和数据库约束属于同一条运行链，不能分层各自用不同假数据测试后宣称闭环通过。每个涉及认证、存储、支付或供应商调用的增量包至少执行：

1. 从目标前端源码枚举 `import.meta.env.VITE_*`／等价公开变量，与 `.env.example`、云端构建脚本和实际构建命令逐项对照；遗漏任一必需变量即停止。只核对云端 `.env` 里“存在”不够，必须确认打包进目标静态产物或通过受控 runtime config 提供。
2. 对 200/204、空 body、非 JSON 错误、超时和配置缺失分别测试；配置缺失不得被笼统包装成“网络异常”。
3. 服务端传给数据库 RPC 的值必须用数据库同一正则、枚举、长度和空值规则做契约断言；至少有一项测试执行真实 RPC/SQL，而不是数据库替身恒成功。旧错误值应在回归中明确失败。
4. 静态构建和 UI 出现只证明编译/渲染；验收关键操作必须点击到真实请求，并核对请求 URL、状态码、响应语义和后端副作用。需要真实短信、付费模型或真实支付时由用户手动完成一次，自动化不擅自重复消费。
5. 秒哒直接对话产生的云端热修复视为新的基线差异：先回收文件/哈希并合入本地权威源码，或在下一包写明保留与窄范围合并合同；未回收前不能整文件覆盖，仅暂停实际冲突目标，其余独立开发继续。

批次完成门禁按用户可验证的主成功路径判断，不按包号、测试数量或秒哒总结判断。主路径失败保留原问题编号与状态；可与后续独立实现合批，不能换号掩盖失败。具体实战见[踩坑 #29](../pitfalls.md#29-增量包修复了业务代码却漏掉云端构建变量且跨层假数据掩盖格式错误)。

## 对抗式审查

- 是否只改了需求范围，是否顺手重构或删掉旧能力？
- 后台能保存的字段，公开端和预览是否真的显示？
- 枚举新增、改名、排序、停用后，旧记录、筛选和空状态是否正常？
- 未登录能浏览但不能下载的边界是否在前端和后端都成立？
- 视频、图片、附件在刷新、无痕窗口、移动端和弱网下是否仍可用？
- 成功和失败是否都有明确提示？
- 是否还原了baseVersion全量树再叠加增量，校验manifest/hash后在完整目标树构建？是否漏新文件、依赖、资源或迁移？
- 秒哒回执是否和正式域名真实资源一致？
- 是否把未验收内容误标为完成？
- 枚举出的前端公共环境变量是否全部由目标构建脚本注入，配置缺失是否被错误包装成网络故障？
- Edge 实际 RPC 参数是否通过数据库同一合同，而不是仅在各层使用不同假数据分别通过？
- 当前批次的用户主成功路径是否真实完成；若失败，是否错误地把补丁推迟到下一批？

## 可直接复用的秒哒提示词

```text
请严格执行本次百度秒哒增量包交付，不要编造、不要自行扩展、不要用占位内容补缺失文件。

版本：<当前版本>
基线版本：<基线版本>
增量包：<zip 文件名>

本批只允许修改 manifest 中列出的相对路径文件，以及明确列出的数据库迁移。
严禁删除或重建未列出的表、数据、接口、登录、权限、支付、订单和上传链路；严禁改变未列出的对象存储路径、环境变量和公开 URL；严禁在校验前开始创作或部署。

请按顺序执行：
1. 确认当前版本与baseVersion一致，并定位可还原的全量源码基线；缺失或不一致立即停止并回报，不从增量包猜补全量工程。
2. 校验增量文件相对路径、字节数和SHA-256；失败停止。建立可回滚版本，在干净目录还原baseVersion全量树并按manifest叠加增量。
3. 对叠加后的目标文件再次校验manifest/hash，核对新文件、删除清单、依赖锁文件、资源和迁移；不能将仅解压的增量包当完整工程构建。
4. 在重建的完整目标树安装依赖、执行静态检查、相关测试与生产构建；数据库迁移按本包已明确顺序执行并验证。
5. 按随包的「问题对照与验收清单」逐项回报实际结果；区分本地、云端和待用户手动验收，不将构建成功视为全部问题通过。回报基线来源、实际改动、校验/测试/构建/迁移结果、当前部署版本与未解决风险。

完成后不要只回复“已完成”，完成后停止。
```

## 历史案例与批次归属

本处方最初来自建委网站的 R6、R7、R8 迭代，不是言剪 AI 的同名批次。动态作品类型、视频播放回退、附件/文档类型与 iframe 的旧案例说明：秒哒执行摘要和正式域名资源可能不同步。跨项改动需要 manifest、字段矩阵、迁移说明和正式域名核验，不以“上传成功”替代“线上版本已切换”。引用批次必须同时写项目、日期和环境，不能仅凭 R6/R7 编号串联不同项目。
