# Codex × 百度秒哒版本化增量迭代闭环

> 状态：当前有效
> 适用平台：百度秒哒 MIAODA（`miaoda.cn`、`*.appmiaoda.com`）
> 最近整理：2026-09-12；修正增量包干净复建顺序，既有案例日期不变

## 适用场景

适用于“秒哒负责云端开发，Codex负责审查和整理，用户负责上传执行并反馈”的长期项目。每轮改动都必须可追踪、可验收、可回滚，不能只依赖秒哒的一段完成摘要。

这不是飞书妙搭发布流程，也不把秒哒当 Git 仓库。职责边界如下：

| 角色 | 负责 | 不负责 |
|---|---|---|
| 用户 | 描述现象、上传增量包、提供线上截图和回执 | 不需要自行设计技术方案 |
| Codex | 读取上下文、诊断、改权威源码、测试、审查、打包、生成验收清单 | 不假装已访问秒哒内部源码或数据库 |
| 秒哒 | 接收增量包、合并源码、执行迁移、构建和部署 | 不负责跨轮记忆、版本治理或证明正式域名已切换 |

## 版本和包命名

每轮都必须产生唯一版本号，推荐：

```text
<project>-JW-YYYYMMDD-R<序号>-<topic>-v<包格式版本>.zip
```

例如：`jianwei-JW-20260906-R8-dynamic-types-video-docs-increment-v4.zip`。

规则：

1. `R` 序号只递增，不复用已经交给用户的编号。
2. 同一版本拆成多个包时，每个包都使用唯一 manifest 文件名。
3. 禁止使用“最新版”“最终包”“修复包”等不可追踪名称。
4. 版本说明必须写明基线版本、改动范围、未改范围和数据库迁移状态。
5. 线上尚未确认切换时，不能把“已上传”标为“已发布”。状态至少区分：已生成、已上传、已合并、已构建、已部署、已验收。

## 增量包合同

增量包只放本轮需要交给秒哒的文件，至少包含：

- 可覆盖到项目中的相对路径文件；
- `MIAODA-PACKAGE-MANIFEST-<version>.json`；
- 变更说明和禁止修改范围；
- 数据库迁移脚本或明确的“无需迁移”；
- 秒哒执行提示词；
- 验收清单和回滚说明。

manifest 每个文件至少记录版本、基线、路径、字节数和 SHA-256：

```json
{
  "version": "JW-20260906-R8",
  "baseVersion": "JW-20260906-R7",
  "baseSource": {"kind": "git-commit-or-full-archive", "reference": "<对应全量源码commit或存档路径>", "sha256": "<全量存档时填写其SHA-256；Git基线记录commit>"},
  "package": "jianwei-JW-20260906-R8-dynamic-types-video-docs-increment-v4.zip",
  "files": [{"path": "src/pages/Admin/Works.tsx", "bytes": 12345, "sha256": "..."}],
  "databaseMigration": "required|not-required|manual-review",
  "createdAt": "2026-09-07"
}
```

交付门禁：增量包只含变更，不能单独解压到空目录后执行安装或构建。先准备可重现的 `baseVersion` **全量源码树**，再叠加本轮增量，得到完整目标版本后才能复跑安装、检查和构建。

干净复建顺序：

1. 在独立干净目录还原 `baseVersion` 对应的Git commit或全量存档；核对基线来源与commit/存档哈希。仅有一个名称、未知内容的线上目录或缺失全量基线时，不能判定可复建。
2. 先校验增量manifest、包内相对路径、文件字节数与SHA-256，再覆盖到还原树；新增文件不得漏项，删除/重命名必须明确登记与核对，不能靠解压自动完成删除。
3. 叠加后对manifest中的目标路径再次校验字节数与SHA-256，确认基线未被其他本地修改污染、未漏依赖/锁文件/迁移/资源；如有完整目标树清单，同时核对它。
4. 在**重建的完整目标树**按项目锁文件安装依赖，再跑TypeScript、静态检查、相关测试与生产构建；增量包自身不要求含完整package.json和全部依赖。
5. 保存基线标识、增量版本、校验结果与实际命令输出。任一步失败停止交付，不用当前开发目录的通过结果替代干净复建。

若交付的是完整源码包，则按 [全量源码分包部署](./codex-source-package-deployment.md) 解压全部编号包并复建；不要混用全量与增量合同。

默认排除 `node_modules`、`dist`、日志、截图、缓存、密钥、原始母版、未引用素材和本机部署配置。

## 每轮标准流程

### 1. 先确定事实和基线

读取项目 README、上轮版本说明、数据库变更记录、截图和秒哒回执，确认：权威源码、用户认为的线上版本、实际线上版本标记、允许修改范围，以及不能动的登录、支付、订单、权限、上传和历史数据。

### 2. 在权威源码修复并回归

前后端一致性问题必须沿着“录入 → 保存 → 查询 → 渲染 → 预览/发布”检查。对作品类型、分类、行业、版权、AI 标记、描述、所属单位、精选时间、附件和下载权限等字段，建立字段矩阵：后台字段、数据库列、公开 API、列表、详情、预览和空值处理逐列对应。前端显示不等于后端已保存，后端字段存在也不等于公开端已渲染。

### 3. 生成增量包

只收集本轮修改文件和必要新资源。不要让秒哒在文件未齐时自由重写，也不要用占位图、猜测字段或重建表补缺失内容。

### 4. 秒哒先校验，再合并和部署

提示词必须要求：核对当前云端版本是否匹配baseVersion及全量基线，校验增量路径/字节数/SHA-256；失败立即停止，不强行套到不同版本。通过后建立可回滚版本、在完整基线树上叠加增量并再次校验目标文件，再执行约定迁移、安装、检查、构建与部署，回报实际结果。

### 5. 正式域名真实验收

“执行成功”“构建成功”“发布完成”都不是正式域名已切换的证明。必须检查：

- `/jianwei-release.json` 或项目约定的 release manifest；
- HTML 的 `data-release` 或等价版本标记；
- 实际 JS/CSS/CDN URL 是否属于本轮版本；
- 真实浏览器 DOM 是否包含新增字段和交互；
- Console、网络状态码、MIME、缓存、CORS、权限行为；
- 未登录、普通用户、管理员、移动端和无痕窗口。

manifest 已更新但 HTML 仍引用旧资源，或页面仍显示旧 `data-release`，应判为“回执成功但正式域名未切换”。

### 6. 反馈闭环和状态保留

用户反馈后先分类根因：未上传、未合并、未迁移、未构建、未切换、缓存、权限、数据映射或视觉回归。每轮保留版本、基线、现象、根因、改动、验证结果、遗留风险和下一步，不用“已解决”覆盖中间状态。

## 专项验收

### 视频和静态资源

先按当前套餐和对象存储能力测试原生上传、Range、MIME、CORS、缓存、拖动和弱网恢复。原生能力可用时优先使用平台或对象存储 multipart/断点续传；旧环境只有在仍复现已验证限制时才用兼容性的分片和 Range 代理。不能靠删素材、压低画质或 Base64 掩盖问题。

### 预览和正式发布

预览必须使用与正式发布相同的数据读取、渲染组件、权限分支、媒体 URL 和 CSS 入口。至少覆盖真实记录、空字段、长文本、附件、视频、移动端和未登录状态。

### 数据库迁移

每次新增字段、枚举、索引、权限或表，都交付迁移顺序、旧数据默认值、回滚方式和迁移后查询验证。只改前端类型或只创建迁移文件但未在秒哒环境执行，都不算完成。

## 对抗式审查

- 是否只改了需求范围，是否顺手重构或删掉旧能力？
- 后台能保存的字段，公开端和预览是否真的显示？
- 枚举新增、改名、排序、停用后，旧记录、筛选和空状态是否正常？
- 未登录能浏览但不能下载的边界是否在前端和后端都成立？
- 视频、图片、附件在刷新、无痕窗口、移动端和弱网下是否仍可用？
- 成功和失败是否都有明确提示？
- 是否还原了baseVersion全量树再叠加增量，校验manifest/hash后在完整目标树构建？是否漏新文件、依赖、资源或迁移？
- 秒哒回执是否和正式域名真实资源一致？
- 是否把未验收内容误标为完成？

## 可直接复用的秒哒提示词

```text
请严格执行本次百度秒哒增量包交付，不要编造、不要自行扩展、不要用占位内容补缺失文件。

版本：<当前版本>
基线版本：<基线版本>
增量包：<zip 文件名>

本批只允许修改 manifest 中列出的相对路径文件，以及明确列出的数据库迁移。
严禁删除或重建未列出的表、数据、接口、登录、权限、支付、订单和上传链路；严禁改变未列出的对象存储路径、环境变量和公开 URL；严禁在校验前开始创作或部署。

请按顺序执行：
1. 确认当前版本与baseVersion一致，并定位可还原的全量源码基线；缺失或不一致立即停止并回报，不从增量包猜补全量工程。
2. 校验增量文件相对路径、字节数和SHA-256；失败停止。建立可回滚版本，在干净目录还原baseVersion全量树并按manifest叠加增量。
3. 对叠加后的目标文件再次校验manifest/hash，核对新文件、删除清单、依赖锁文件、资源和迁移；不能将仅解压的增量包当完整工程构建。
4. 在重建的完整目标树安装依赖、执行静态检查、相关测试与生产构建；数据库迁移按本包已明确顺序执行并验证。
5. 回报基线来源、实际改动、校验/测试/构建/迁移结果、当前部署版本与未解决风险。

完成后不要只回复“已完成”，完成后停止。
```

## 当前案例

R6、R7、R8 的线上排查共同说明：秒哒执行摘要和正式域名实际资源可能不同步。R8 又把动态作品类型、视频播放回退、附件/文档类型和 iframe 嵌入等跨前后端改动放在同一增量包，因此更需要 manifest、字段矩阵、迁移说明和正式域名核验。以后每个版本都沿用本处方，不再以“上传成功”替代“线上版本已切换”。
