# AI 编程通用经验

不绑定某个工具、所有 AI 编程项目都能用的经验。某个工具特有的做法放在 `tools/<工具>/`，比如[秒哒](../tools/miaoda/README.md)；某个项目自己的事实放在 `projects/<项目>/`。

## 写入规则

建委在开发中纠正或认可成品时，按[进化机制](../../../../system/repository/evolution.md)先记观察、查重查冲突，再决定写不写进来；建委说“沉淀成通用经验”时直接写。写进这里之前过四关：

1. **放对层。** 换了工具、换了项目都成立的才写这里；只在某个工具上成立的写进该工具目录（如秒哒的写 `tools/miaoda/`，这里只留链接）；只是某个项目的进度、版本、参数写项目。
2. **写成动作，不写成事例。** 标题写“遇到什么情况做什么”，不写项目名；正文写场景、怎么做、正例、反例、为什么。把项目名、页面名、版本号换掉后这句话仍然对，才算通用（换位测试见[写入规范 · 从一个项目里提炼](../../../../system/repository/ingestion-workflow.md#从一个项目里提炼写给下一个不同的项目默认)）。项目事例只当反例写一两句，配一个换了项目也成立的正例。反例：把“作品网站后台改了站名前台不变”写成一条规则，下次做别的系统没人会想到它；应写成“加功能、改功能先列影响面”，作品网站只是其中的反例。
3. **能被读到。** 写完用两三句真实任务说法（如“给网站加个新分类”“新功能界面和原来的不一样”）顺着 AGENTS → 入口 → 本表走一遍，读不到就补上方表格的“什么时候读”、秒哒入口的读取表，必要时补 AGENTS；能在成品上核对的，同时在[开发交付前八项](../../../../system/repository/execution-checks.md)加一行填值。
4. **一条规则只一个家。** 先搜已有条目，同类错误补证据、改原文，不在末尾追加意思相近的新条；标级别（默认、可灵活；红线只有建委能定）；来源和验证状态放文件末尾。
