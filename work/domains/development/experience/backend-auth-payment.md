# 后端、登录、支付的通用经验

所有 AI 编程项目都适用。秒哒上的具体做法和提示词见秒哒专题：[登录](../tools/miaoda/topics/authentication.md)、[支付](../tools/miaoda/topics/payment.md)、[后端存储](../tools/miaoda/topics/backend-storage.md)。

> 来源：秒哒项目实战，原始记录在[秒哒踩坑](../tools/miaoda/pitfalls.md)（编号见各条）。

## 数据存哪（默认）

- 需要查询、权限控制、跨设备保存的业务数据（用户、订单、存档、后台内容）放真实数据库。
- 图片、视频、音频、文档放对象存储，数据库只存地址，不要把二进制塞进表里。
- `localStorage` 只能存无关紧要的偏好或缓存，不能冒充业务数据库。
- 没有登录、没有跨设备需求的项目，不要为了显得完整硬加数据库。

## 登录与身份（红线）

- **手机号是身份键，不是展示字符串。** 注册、登录、异常兜底、旧用户兼容，所有路径只做一次规范化（去空格、去 `+86`），然后都用同一个函数。否则 `+86138…` 和 `138…` 会变成两个账户，或者用户明明密码对了却提示"密码错误"。（踩坑 #22）
- **两种登录方式并存 = 可能变成两个账户。** 微信登录和账号密码登录默认是两个身份，要并存就先设计账号绑定规则，不能只说"再加一种登录方式"。（踩坑 #20）
- 已经存在的重复账户，不要在同一次修复里自动合并，要先核对身份和业务数据，再单独迁移。

## 签名与加密（红线）

- **Web Crypto 不支持 MD5。** Deno、浏览器、新版 Node 的 `crypto.subtle.digest("MD5")` 会直接报错。需要 MD5 签名时用纯 JS 实现或服务端语言的库。（踩坑 #2）
- **签名排序不要用 `localeCompare`。** 在下划线、连字符这些字符上它和 ASCII 排序不一样，签名会对不上。用 `a < b ? -1 : a > b ? 1 : 0`。（踩坑 #6）
- 已经验证过的签名代码直接贴给 AI，明确"禁止重写"。AI 很喜欢自己另写一份，结果算错。（踩坑 #5）

## 密钥（红线）

- 密钥、service-role key、数据库密码、支付私钥只放服务端，不进前端代码、提示词正文、日志、公开源码。
- 只有可以公开给浏览器的 URL、anon/public key 才能进前端构建变量。
- 检查平台或插件生成的代码里有没有明文密钥。（踩坑 #3）

## 支付（默认）

- 新增支付通道时，原来稳定的支付链路一行不动，新通道按 `pay_channel` 之类的字段分流。
- 多通道并存时，退款也要按通道路由，否则会拿 A 通道的订单去 B 通道退款。（踩坑 #13）
- 每个新的服务端函数先打印一次它能读到的环境变量名，确认密钥名没拼错、确实注入了。（踩坑 #11、#12）

## 兑换码、积分这类共享额度（默认）

多人共用一个兑换码时：码记录加行锁、每个用户只能领一次、总额度校验，钱包、流水、领取记录、计数在同一个事务里。测试时故意让中途失败，确认会整体回滚。本地用的单连接数据库测不出真正的并发竞争，要在云端另外验。

## 换账号时的缓存（默认）

切换账号时，旧账号的查询缓存和还没回来的请求都要作废，不然新账号会看到旧数据。敏感的写操作不要自动重试。
