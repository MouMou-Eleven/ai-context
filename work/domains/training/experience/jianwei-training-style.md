# 建委的培训风格：课件就是建委拿着能直接讲的稿子

写、改、审建委的培训课件前先读本页。本页是培训风格的总纲：先讲清建委为什么要这种风格，再分几部分讲怎么做。课程内容怎么组织见[课程组织](./demo-driven-course-design.md)，技术概念怎么讲见[从问题推导概念](./technical-explanation/problem-driven-technical-explanation.md)。

> 来源：会员社群、济南市图书馆、分享活动等多轮课件修改与讲后反馈，归属见[来源表](./sources.md)。口径确认 2026-09-07；2026-10-21 社群第7课两轮反馈后，按建委讲清的"为什么"重组本页，并并入原"飞书课堂文档可视化与口语化"和"备课与课件设计"两份文件。

## 先弄清前提：这份文档是怎么被用的

建委讲课（直播、线下培训）**不是按部就班地念稿子，会临场发挥**。同一份飞书文档同时有三个用处：

1. **建委的讲稿**：他拿着它讲，有时逐句念，有时看到一个知识点就脱稿发挥。
2. **学员同时在看的课件**：屏幕上、学员手里看到的是同一份。
3. **学员课后回看的资料**。

下面每一条规则都是从这个前提推出来的，不是一个个独立的偏好。规则拿不准时，回到这三个用处判断。

| 建委要的 | 为什么 | 不这样会怎样 |
|---|---|---|
| 按建委说话的逻辑写，拿起来就能念 | 是讲稿，读着顺不等于讲着顺 | 读起来没问题，但他直播时不会这么说，只能边看边在脑子里改，节奏断 |
| 必讲知识点加粗加红 | 他会临场发挥、整段跳过；发挥完要一眼找到下一个必讲点 | 只能一段段往下扫，找不到接回来的地方 |
| 先背景、再价值、再案例演示、最后方法 | 有背景才立得住，有价值才凸显，有演示才证明这是能解决问题的实在东西 | 上来就讲方法，学员不知道为什么要学，也不信它有用 |
| 难懂的东西用图、真实截图、可运行的案例 | 学员同时在看，讲到哪儿就要能看见哪儿 | 纯文字讲概念，听着就累，也讲不透 |
| 不写讲师安排、时长，也不写讲课用不到的实现细节 | 学员同时在看；讲课用不到的内容只会占位置 | 学员看到"讲师这里演示"；稿子里一段他永远不会念的说明 |

**这套风格只管培训课件。** 公众号文章、宣传文案、对外方案、书稿各有各的读者和用法，不能把"全篇口语、加红锚点"搬过去。比如建委2026-10-21提到，公众号文章可能是半口语、半书面的写法，按[自媒体](../../self-media/README.md)的方法走，不按本页。

规则分级：标了**红线**的不能违反；其余为**默认**，有更好的理由可以变通，但要跟建委说一句为什么。

## 一、像建委在讲，而不是一篇好读的文章（默认）

动笔前先读[口语样稿](../../../../system/expression/voice-samples.md)（其中样稿三就是建委本人对同一段课件的讲法）。写完以后，用"建委直播时会不会这么说"去读每一段，不是用"读着顺不顺"。

### 建委讲课的说话逻辑

从建委亲口示范的讲法里总结出来的（原文见口语样稿三）：

1. **直接交代自己做了什么，再把结果告诉大家。** "这里我给大家做了一个实验，然后直接把实验的结果告诉大家。在这里呢，我做了一个报名页……"不用"咱们光说没意思，直接做个实验"这种起兴的话。
2. **讲现象时顺带点出它为什么是个问题。** "通过这个提示，你无论是截图给 AI 还是描述给它，AI 其实都找不到问题的根源。"
3. **对比时把错在哪、代价是什么、对的好在哪都说出来。** 错的：AI 盲猜很多方向，浪费 Token，还可能把原本没问题的功能改坏；对的：一次定位、一次修好，省效率也省 Token。不只描述两边各是什么样。
4. **把结论落到学员身上，打消顾虑。** "最关键的是，这两种方式都不需要你去懂代码，只需要知道这个窗口是什么意思、那个窗口是什么意思。"
5. **把每一段挂回今天的主线。** "用今天教给大家的方法""等一下我要给大家讲到的方式"。
6. **讲师第一人称讲经历和总结。** "我在线下培训的过程中了解到""我给大家总结了五级阶梯法"。这是建委的说话方式，不算红线 1 里的讲师安排。
7. **用说话时的顺序词串结构。** "首先……然后是第二级……接下来是第三级，这个也是今天的重点……最后是第五级"，一听就知道讲到了哪儿。
8. **"呢"放在话题转换处。** "在这里呢""那右边这种呢"，是讲话的停顿，不是每句都加。

| 像建委讲的 | 不像（读着顺，但他不会这么说） |
|---|---|
| "你开了一个月会员，可能这个月总共就用了五次，剩下的用不了就是浪费。" | "订阅模式存在资源利用率偏低的问题。" |
| "有的人安装不了，有的人汉化不了，还有的人压根就打不开。" | "学员可能遇到各类技术问题。" |
| 从上一节做完的事接着说："上一节课我带大家了解了秒哒……那这一节课呢，其实就是为了解决大家的后顾之忧。" | "本节将系统介绍……" |
| 开场直接说学完能干什么："学完今天这节课，以后遇到任何开发上的 Bug，你都能清楚地知道怎么用 AI 解决。" | "先判断它属于哪一类，再把对应的证据交给 AI。" |
| "我在线下培训的过程中了解到，很多学员……做出第一版后不知道怎么迭代，越聊越乱，最后放弃了。" | "很多人卡住，不是卡在做不出第一版，而是卡在……" |
| "左边呢，就是错误的问法……这样不仅解决不了问题，反而可能把原本没问题的功能也改出问题来。" | "左边这种问法，AI 其实也挺努力的，它把能想到的可能都列了一遍。" |
| "谁能把问题更好地描述给 AI。" | "谁能把现场交给 AI。" |

口语化不是加"其实、然后、就是说"，也不是为了句子显得高级去挑词："现场""证据""判定"这类词有距离感，能换成"问题""报错""情况""判断"就换。靠的是具体的人、事、数字，一句讲一层意思，连接词用说话时的"因为、而且、但是、所以"。

## 二、必讲知识点加粗加红（默认）

**为什么**：建委会临场发挥、会整段跳过不念。加红的地方就是他讲课的定位点：只要这几处讲清楚了，中间的字没有逐句念也不影响整节课；发挥完一眼就能找到下一个要讲的点。

**怎么标**：

- 标的是"这一段讲完学员必须带走的那句话"：结论、判断方法、方法名字、关键的分界（比如"4 开头多半是这边的问题，5 开头是后厨出事了"）。不标装饰性的词，不整段标。
- 每个小节通常 1～3 处，整节课翻下来，只看红字就能串起主线。
- 飞书写法：`<span text-color="red"><b>……</b></span>`；已经在加粗里的，只加 `text-color`。整篇读取（`docs +fetch` 不带范围）时颜色会被省略，核对红字要按关键词或段落读取。
- 建委自己已有的标红保留，不改色、不挪位置（见第六部分红线 2）。

## 三、先立住，再展开：一节课的骨架（默认）

**为什么**：学员先要知道为什么要学、学了能解决什么，并且亲眼看到它真的有用，后面的方法才听得进去。

1. **背景**：从学员上一节做完的事、或建委在培训里看到的真实困扰接着说。系列课不重复总定位，只讲这一节独有的痛点。
2. **价值**：学会以后能解决什么，还能用到哪里（比如修 Bug 练出来的"把问题描述清楚"，改 PPT、问客服一样用得上）。
3. **案例演示**：用真实实验、真实结果证明它管用，比如同一个问题、同一个模型，只换问法的对比。
4. **方法**：总结成一个有名字、能记住的方法（"五级阶梯法"），再一级一级展开；每一级都说清上一级为什么不够、这一级补了什么。
5. **带走的东西**：可复制的提示词模板、分诊表、练习。

用一个学员一眼能懂的场景串起整节课（比如一个奶茶点单小程序，藏着从简单到难的几个问题），比每个知识点换一个例子更清楚。具体组织方法见[课程组织](./demo-driven-course-design.md)。

## 四、能看见：画面、真实截图和可运行的案例（默认）

**为什么**：学员同时在看，讲到哪儿就要能看见哪儿；难懂的东西光靠嘴讲，学员要靠想象，讲的人也累。

写正文前先按知识点列一张媒体清单，写完逐个知识点检查有没有对应的画面：

| 要讲的 | 用什么 | 不能怎样替代 |
|---|---|---|
| 真实软件界面、按钮、路径、价格、操作结果 | 真实截图（**红线 3**：不用 AI 生图仿造界面） | 不用逻辑图猜按钮位置 |
| 动效、交互、操作过程 | 视频、动图或能运行的案例 | 不把核心过程压成一张静态图 |
| 流程、关系、机制、对比 | 逻辑图、流程图 | 不用一张平台截图代替关系 |
| 抽象概念、生活场景、前后反差 | AI 生成图片 | 不重复正文，不仿造真实界面 |
| 三个以上对象的横向比较 | 表格 | 不把讲过的正文再排成一张表 |
| 特别容易出错的边界 | 少量高亮块 | 不把普通信息都包成提示框 |

- **每个画面都要回答"它让学员多看懂了什么"**。生图前写清它补充的唯一理解点；生成后检查是不是只把正文排进图里、是否和截图或别的生图重复、文字和关系是否准确。去掉它学员也不少懂什么，就不放。
- **画面放在它解释的地方**：先告诉学员看什么，再放画面，画面后说怎么判断。不集中堆到文末，不放错章节。
- **开发者工具、软件操作类的截图用中文界面**；打开方式、截图、录屏这类快捷键按 Windows 和 Mac 分别写全。
- **提示词、文字和画面互相对应**：提示词里要求保留什么，正文就在结果处提醒核对什么。
- 要现场实操演示时用飞书文档；纯演讲用 PPT（[设计：PPT](../../design/graphic/ppt/README.md)）。用生图还是现场演示、篇幅深浅，看知识点和受众（可灵活）。

## 五、学员同时在看：写什么，不写什么

**红线 1：学员视角，不写讲师安排。** 正文、标题、表头、提示框里都不出现时长（"本节 20 分钟"）、讲师动作（"讲师这里打开""接下来演示"）、备课栏目（"课堂要看什么""转场""备注"），以及 AI 的执行过程和资料整理过程。讲师第一人称讲经历、讲总结不在此列（见第一部分第 6 条）。

**讲课用不到的不写（默认）。** 每段问一句"建委讲课时会不会讲"。演示页怎么实现的、请求发到哪个测试服务、仓库里的来源和核验状态，这些讲课用不到，删掉。

**分清交付物。** 建委只说"课件""分享资料""讲课文档""拿着讲两小时"时，默认做课堂主文档；"讲两小时"只说明内容量，不代表要写时间表。其他交付物只在建委明确要求时才做：

| 交付物 | 谁用 | 写什么 | 不混入 |
|---|---|---|---|
| 课堂主文档（默认） | 建委拿着讲，学员同时看 | 能直接讲的口语正文、加红知识点、案例、画面、判断、必要的提示词 | 时长、转场、讲师提醒、备用方案 |
| 讲师备课稿 | 建委自己 | 讲课顺序、时间、演示准备、互动、转场 | 不直接当学员课件发 |
| 课后阅读资料 | 学员自己读 | 书面一点的完整解释和步骤 | 为现场节奏省掉的关键说明 |
| 实操教程 | 学员跟着做 | 按[教程写法](./tutorial-writing.md) | 和当前操作无关的扩展 |
| 作业或练习 | 学员课后做 | 任务、素材、提交方式、验收标准 | 未经要求自动生成 |

当前案例必须通过 AI 完成时，保留完整、可复制的提示词；和案例无关的"以后可以这样问 AI"不加。学员不需要背命令，少量真实操作是为了帮助理解。仓库不规定课程固定时长，听建委当次的安排。

## 六、改已有的飞书课件

**红线 2：保护建委的成果。** 局部改，不整篇覆盖；必须整篇重写时，先完整备份当前版本，并把建委手动改过的地方（字句、加粗、标红）逐一保留进新稿。建委插入的截图、视频、附件、案例顺序、评论、红色标注都保留，不改色。

- 改之前先列清现有资源（标题、图片、视频、附件、链接、评论、标红），改完按清单逐项回读，数量、位置、用途都要对上。
- 补的图片插在对应知识点附近。
- 删了章节后检查编号、列表、图片位置和残留内容。

## 七、反复出现过的错误

下面的错误在不同课程里出现过不止一次，交付前逐条检查：

| 错误 | 在哪些课出现过 | 怎么检查 |
|---|---|---|
| 写成书面文章或 AI 报告 | 网页基础设施课、秒哒进阶课、秒哒开发流程课、社群第7课 Bug 课（2026-10-21 第一稿） | 对照口语样稿逐段读；搜"现场""证据""判定""先判断……再……"；开场是不是直接说了学完能干什么 |
| 读着顺，但不是建委讲课的说法 | 社群第7课 Bug 课（2026-10-21 第二稿） | 每段按第一部分"说话逻辑"八条过一遍：有没有起兴过渡句；对比有没有说出代价和好处；结论有没有落到学员身上；有没有挂回今天的主线 |
| 没有讲课定位点 | 社群第7课 Bug 课（2026-10-21 第二稿） | 只看红字能不能串起整节课的主线；每个小节有没有 1～3 个必讲点 |
| 只改被点到的那几处 | 社群第7课 Bug 课（2026-10-21） | 建委举例纠错时，先说出例子背后的原因，再全篇按这个原因改，而不是只改例子那两句 |
| 写进讲课用不到的实现说明 | 社群第7课 Bug 课（演示页请求发到哪个测试服务） | 每段问"讲课时会不会讲" |
| 讲师备课内容混进学员正文 | 网页美化/静态网页发布课、秒哒开发流程课、GPT-6 Astra 分享资料 | 搜"分钟""讲师""演示""课堂要看"，看标题和表头 |
| 文字很多，缺画面和真实案例 | 静态网页发布课、秒哒进阶课、秒哒开发流程课 | 按知识点对照媒体清单 |
| 生图或表格只是把文字重复一遍 | 网页美化/静态网页发布课、秒哒开发流程课 | 每张图、每张表问一句"它让学员多看懂了什么" |
| 修改时弄丢图片、视频、评论、标注 | 秒哒进阶课、秒哒开发流程课 | 改前列清单，改后逐项回看 |

同样的错再出现时，在"在哪些课出现过"补上这次的课名，并想办法把"怎么检查"写得更具体。不要另加一条规则。

## 交付前

能运行 Python 时，先用脚本扫一遍讲师视角词：

```text
python system/repository/maintenance/check-deliverable.py <草稿路径> --profile learner
```

脚本只查已知的几类问题。然后自己按上面"反复出现过的错误"表逐条检查实际成品，写入飞书后再回读一遍（红字按段落读取核对）。各类成品的通用自查方法见[成品自查](../../../../system/repository/execution-checks.md)。
