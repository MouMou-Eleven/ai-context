# 培训方法

建委讲课、写课件的通用方法，适用于会员社群、企业培训、图书馆、夜校和其他分享。

## 这几份文件是什么关系

总纲是[培训风格](./jianwei-training-style.md)：它先讲清建委的课件是怎么被用的（是他拿着讲的稿子，他会临场发挥；学员同时在看；课后还要回看），再从这个前提推出怎么写、怎么标重点、怎么排骨架、怎么配画面、什么不写。其他文件都是在这个总纲下面，各管一件具体的事：

| 文件 | 管什么 | 什么时候读 |
|---|---|---|
| [培训风格](./jianwei-training-style.md)（总纲） | 为什么要这种风格；说话逻辑、加红知识点、一节课的骨架、画面、交付物边界、改稿保护、反复出现的错误 | 写、改、审任何培训课件前必读 |
| [课程组织](./demo-driven-course-design.md) | 一节课的内容具体怎么组织：学习坐标、宏观与落地、演示与案例、故障类课程、演讲分享结构、讲后复盘 | 设计课程结构、案例和演示时 |
| [从问题推导概念](./technical-explanation/problem-driven-technical-explanation.md)（[目录说明](./technical-explanation/README.md)） | 技术概念值不值得讲、从什么角度讲；其他领域也会借用它的解释逻辑 | 课里出现 API、MCP、数据库这类概念时 |
| [实操教程写法](./tutorial-writing.md) | 学员要跟着一步步做出结果的教程 | 交付物是教程，而不是课堂主文档时 |
| [培训方案与课程大纲](./external-proposal-design.md) | 给主办方看的方案 | 培训接洽后写方案、大纲时 |
| [岗位与行业场景](./role-specific-scenarios.md) | 各岗位、各行业专属的 AI 应用场景和风险点（宣传岗、电力咨询……） | 培训对象是某个具体岗位或行业，写方案、设计案例时 |
| [方法来源与课程身份](./sources.md) | 每条方法来自哪次课、哪类反馈 | 核对来源和归属时；日常创作不用读 |

一个问题只在一个文件里写。发现两个文件讲同一件事，合并到表里负责的那一个。具体课程的事实、标题、案例顺序和进度放在对应项目或场次记录里，不放这里。

做课件、方案、教程时先读哪个、再读哪个，见[培训入口](../README.md#先分清你要做的是哪一种)。

## 外部来源已形成的方法

| 来源 | 提炼结果 | 使用方式 |
|---|---|---|
| 飞天闪客技术科普逐字稿 | [从问题推导概念](./technical-explanation/problem-driven-technical-explanation.md) | 课程需要解释 AI 或技术概念时读提炼方法；不默认读原逐字稿，不模仿作者个人措辞 |

外部来源只提供可验证的方法证据，不能覆盖建委真实授课反馈、当前课程事实和项目要求。

## 多个来源的讲法冲突时

本节是培训方法里处理多个来源（建委反馈、外部讲师或创作者、原始逐字稿）的唯一正文，技术概念讲解也按这里。

按这个顺序取舍：建委这次的要求 → 项目事实 → 建委真实授课后的反馈 → 本目录已有方法 → 外部讲师或创作者的方法 → 原始逐字稿。

- **新来源和已有方法说的是同一条路**（例：同样是“问题—旧办法—缺口—新方法”）：只补证据或完善已有的那一步，不另建一套同义方法。
- **新来源给了一条不同但有效的路**：写明它适合什么受众、什么难度、什么课型，有什么限制。
- **能分工的可以前后组合**（比如先用问题引出概念，再用演示证明），但一次讲解、同一段只用一种开头、一条主线，不把几位作者的开头、节奏和句式拼成混合风格。
- **只学方法，不学人**：本目录保存的是“怎样讲”的方法，不保存或激活某位创作者的完整个人风格；外部作者的固定口头禅、标志性句式、个人经历和没核实过的判断，不并进方法。
- **建委真实授课反馈证明某条方法不适用时**，按授课反馈改那条方法，并在文件末尾写明原因。

拿不准时问建委。

## 讲完课怎样沉淀

建委说"复盘一下""把经验记下来"时：

0. **先判断这一场有没有新东西**（建委 2026-11-19 明确要求，默认）。培训经验要像训练集：只放筛选、去重以后真正新的东西，不是每讲一场就记一遍。
   - 只是换了单位例子的通用办公课（用 WorkBuddy 调 Excel、Word、PPT、知识库、Skill；高速用高速的例子、图书馆用图书馆的例子），只记场次事实，**不进本目录**。
   - 出现了**岗位或行业专属的新场景**（如宣传岗的稿件、海报、素材整理、安全使用，财务、工会等），或者工具和场景组合不一样（如用 DeepSeek 做脱敏），就把这些场景提炼进[岗位与行业场景](./role-specific-scenarios.md)，让培训经验一个行业一个行业地变丰富。
   - 建委备课时给的参考资料（如某工具的设计资料、宣传口径），提炼其中可复用的精华写进对应方法，原文不整篇搬进来。
1. **这一场的事实**（讲了什么、学员反应、哪里卡住）写进这一场的记录：企业、机关、图书馆等培训在 [AI 培训项目](../../../projects/ai-training/sessions-index.md)对应场次，会员社群在[社群项目](../../../projects/paid-community-course/README.md)。
2. **下次还能用的做法**，直接改本目录里负责这件事的那个文件，改原文，不要追加；新的常讲课题、新讲法补进[常讲课题](../topics.md)。每条写清场景、做法、例子、原因和级别，按[写入规范 · 写清楚](../../../../system/repository/ingestion-workflow.md#第四步写清楚)。
3. **建委举例纠错时，先弄清例子背后的原因。** 建委的每个要求都有它的逻辑（比如加红是为了临场发挥后能接回来）；沉淀的是这个原因和由它推出的做法，写进总纲里对应的部分，不是把例子那两句话当成新规则。
4. **写进去之前，把相关的旧结论都找出来对一遍。** 之前的课件、AI 当时的判断、别的文件里的规则，和这次的反馈放在一起看：哪里冲突、各自对在哪、错在哪，想清楚以后改造成一个说得通的版本；来龙去脉写在那个文件末尾，正文只写现在怎么做。不能把建委这次说的话直接贴进去（2026-11-21：只听“用回八层手册”就把八层原样写回，连第 3 课已判定过时的情绪写法也写了进去，被建委指出自相矛盾）。
5. **同一个错误又犯了**：按[培训风格 · 反复出现过的错误](./jianwei-training-style.md#七反复出现过的错误)表末尾的办法处理，不要再加一条"必须"。
6. 每条反馈给出一个结论：只留这一场的记录 / 新增方法 / 改了哪个通用方法 / 同一错误又犯（第 5 步）/ 信息不够，暂不推广。

备课时的修改和真实讲完后的反馈要分清，讲完后的反馈更有分量。AI 自己检查通过不等于教学效果好。具体写入规则见[写入规范](../../../../system/repository/ingestion-workflow.md)。
