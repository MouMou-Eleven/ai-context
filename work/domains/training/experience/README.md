# 培训方法

建委讲课、写课件的通用方法，适用于会员社群、企业培训、图书馆、夜校和其他分享。

## 这几份文件是什么关系

总纲是[培训风格](./jianwei-training-style.md)：它先讲清建委的课件是怎么被用的（是他拿着讲的稿子，他会临场发挥；学员同时在看；课后还要回看），再从这个前提推出怎么写、怎么标重点、怎么排骨架、怎么配画面、什么不写。其他文件都是在这个总纲下面，各管一件具体的事：

| 文件 | 管什么 | 什么时候读 |
|---|---|---|
| [培训风格](./jianwei-training-style.md)（总纲） | 为什么要这种风格；说话逻辑、加红知识点、一节课的骨架、画面、交付物边界、改稿保护、反复出现的错误 | 写、改、审任何培训课件前必读 |
| [课程组织](./demo-driven-course-design.md) | 一节课的内容具体怎么组织：学习坐标、宏观与落地、演示与案例、故障类课程、演讲分享结构、讲后复盘 | 设计课程结构、案例和演示时 |
| [从问题推导概念](./technical-explanation/problem-driven-technical-explanation.md)（[目录说明](./technical-explanation/README.md)） | 技术概念值不值得讲、从什么角度讲；其他领域也会借用它的解释逻辑 | 课里出现 API、MCP、数据库这类概念时 |
| [实操教程写法](./tutorial-writing.md) | 学员要跟着一步步做出结果的教程 | 交付物是教程，而不是课堂主文档时 |
| [培训方案与课程大纲](./external-proposal-design.md) | 给主办方看的方案 | 培训接洽后写方案、大纲时 |
| [方法来源与课程身份](./sources.md) | 每条方法来自哪次课、哪类反馈 | 核对来源和归属时；日常创作不用读 |

一个问题只在一个文件里写。发现两个文件讲同一件事，合并到表里负责的那一个。具体课程的事实、标题、案例顺序和进度放在对应项目或场次记录里，不放这里。

## 做课件时的读取顺序

只查事实、位置、进度时，直接按[培训入口](../README.md)查对应资料，不走下面的顺序。

1. 读[培训风格](./jianwei-training-style.md)和[口语样稿](../../../../system/expression/voice-samples.md)。
2. 确认培训对象、已有基础、授课场景和要做出的结果；判断交付物（默认课堂主文档）。演讲与对外分享先看[可选三层结构](./demo-driven-course-design.md#演讲与对外分享问题含义现实事例可灵活)是否适配。
3. 核实项目与系列归属，读当前事实和同一系列的前课；归属不明从[培训资料总入口](../../../projects/ai-training/sessions-index.md)按主题核对，不能按课号接续社群。
4. 用[课程组织](./demo-driven-course-design.md)设计课程逻辑、案例和画面。
5. 出现技术概念时，用[从问题推导概念](./technical-explanation/problem-driven-technical-explanation.md)先筛选要不要讲，再决定角度。
6. 学员确实要跟着操作时，再叠加[教程写法](./tutorial-writing.md)。

文章、短视频、销售页、飞书书稿、教师微课不因为内容里出现"课程""技术"就套用本目录：付费社群课程先读项目 README；招生物料走 AI 自媒体并取真实项目事实；正式授课按实际步骤调用编程、设计或视频依赖，不叠加销售话术；教师微课、精品课、参赛课进入[教育作品](../../design/video/education/README.md)。

## 外部来源已形成的方法

| 来源 | 提炼结果 | 使用方式 |
|---|---|---|
| 飞天闪客技术科普逐字稿 | [从问题推导概念](./technical-explanation/problem-driven-technical-explanation.md) | 课程需要解释 AI 或技术概念时读提炼方法；不默认读原逐字稿，不模仿作者个人措辞 |

外部来源只提供可验证的方法证据，不能覆盖建委真实授课反馈、当前课程事实和项目要求。

## 多个来源的讲法冲突时

按这个顺序取舍：建委这次的要求 → 项目事实 → 建委真实授课后的反馈 → 本目录已有方法 → 外部讲师或创作者的方法 → 原始逐字稿。

不同人的讲法可以前后分工（比如先用问题引出概念，再用演示证明），但同一段只用一种开头、一种主结构。拿不准时问建委。

## 讲完课怎样沉淀

建委说"复盘一下""把经验记下来"时：

1. **这一场的事实**（讲了什么、学员反应、哪里卡住）写进这一场的记录：企业、机关、图书馆等培训在 [AI 培训项目](../../../projects/ai-training/sessions-index.md)对应场次，会员社群在[社群项目](../../../projects/paid-community-course/README.md)。
2. **下次还能用的做法**，直接改本目录里负责这件事的那个文件，改原文，不要追加。
3. **建委举例纠错时，先弄清例子背后的原因。** 建委的每个要求都有它的逻辑（比如加红是为了临场发挥后能接回来）；沉淀的是这个原因和由它推出的做法，写进总纲里对应的部分，不是把例子那两句话当成新规则。
4. **同一个错误又犯了**：在[培训风格](./jianwei-training-style.md)的"反复出现过的错误"表里补上这次的课名，把"怎么检查"写得更具体。不要再加一条"必须"。
5. 每条反馈给出一个结论：只留这一场的记录 / 改了哪个通用方法 / 信息不够，暂不推广。

备课时的修改和真实讲完后的反馈要分清，讲完后的反馈更有分量。AI 自己检查通过不等于教学效果好。具体写入规则见[写入规范](../../../../system/repository/ingestion-workflow.md)。
