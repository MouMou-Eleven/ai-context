# 视频与微课交互式制作工作台

- ID：`interactive-video-production-workbench`
- 主归属：视频共用制作方法与工具
- 状态：当前采用
- 确认依据：2026-09-15，建委根据《小树叶》制作页面的实际使用，确认交互式工作台比纯文档更直观、便于执行，并要求沉淀为视频、动画与教育作品的共用经验。
- 验证程度：《小树叶》页面已实际完成分段音频播放和提示词复制检查；工作台形态得到建委确认。尚缺第二个不同片型的完整复用记录，不能据此宣称所有项目均应开发完整应用。

## 什么时候使用

当一个视频或微课包含多个音频段、分镜、参考图、提示词和反复修改记录，需要人工逐段生成、检查与回填结果时，优先制作交互式工作台。它适合以下任务：

- 歌曲、旁白或课程音频需要按时间段制作对应画面；
- 每段同时存在场景图提示词、视频提示词、参考图职责和验收条件；
- 操作者需要频繁试听、复制提示词、切换段落并记录返工状态；
- 需要让客户、制作人员或后续 AI 快速理解整片结构，而不是在长文档中来回查找；
- 一个项目会经历多轮生图、生视频和后期修改，需要保留每段的当前版本和问题。

以下情况可以不做完整工作台：只有一两个简单镜头、没有分段音频和参考资产、一次交付即可完成时，用短分镜表和文件夹即可。工作台是制作控制界面，不是最终给观众播放的成片，也不能代替剪辑软件、素材存储或项目事实记录。多人实时协作、云端权限、审核流和数据库统计属于应用开发，应另行设计系统。

## 核心定位

纯文档适合说明方法，工作台适合执行项目。两者承担的任务不同：

| 载体 | 主要作用 | 保存内容 |
|---|---|---|
| 方法文档 | 告诉 AI 和制作人员“这类工作怎样做” | 原则、步骤、模板、边界和验收方法 |
| 项目案例 | 记录“这次项目实际发生了什么” | 输入、选择、失败修正、结果和证据 |
| 交互式工作台 | 支持“现在逐段制作和检查” | 音频、分镜卡、参考图、提示词、状态、版本和操作按钮 |

工作台不是把 Markdown 换一种皮肤展示。每个交互都应减少一次查找、复制、定位或误用素材的成本。

## 一、先建立单一数据源

先完成音频分段和分镜设计，再生成页面。页面数据应来自一份结构化清单，例如 JSON、JavaScript 对象或表格导出，避免在导航、卡片和提示词区分别手工维护同一时间码。

每个生成段至少包含：

| 字段 | 必须表达的内容 |
|---|---|
| 段号与标题 | `P01`、本段动作或叙事名称 |
| 起止时间与时长 | 后期精确定位；能够发现漏段、重叠和时长不符 |
| 内容依据 | 对应歌词、旁白、知识点或“纯音乐转场” |
| 叙事作用 | 建立环境、解释知识、推进动作、表达情绪或完成转场 |
| 起始与结束状态 | 承接上一段，并为下一段留下明确状态 |
| 段内镜头 | 一次生成内的镜头顺序、景别、主体动作和结束画面 |
| 制作方式 | 文生视频、关键图加图生视频、实拍、录屏、AE、Remotion或后期合成 |
| 参考资产及职责 | 每张图负责角色、风格、场景、首帧或目标状态中的哪一项 |
| 图片与视频提示词 | 可以一键复制的最终可执行文本 |
| 验收条件 | 本段必须看到什么、绝不能出现什么 |
| 制作状态 | 待准备、待生图、待生视频、待复核、需返工、已通过 |
| 结果与修改记录 | 当前文件、版本、失败原因和下一步修正 |

提示词正文只保存一份。页面显示、复制按钮和导出的 TXT 应从同一字段生成，防止页面中的提示词与实际上传版本不一致。

## 二、页面信息结构

### 1. 项目总览

页面顶部先让操作者确认当前项目，而不是直接落入一大段提示词。建议展示：

- 项目名称、总时长、画幅、视觉风格、目标平台与当前版本；
- 原始音频播放入口和文案入口；
- 已通过、待制作、需返工的段数；
- 全片共用的角色资产、风格锚点和禁止项；
- 本轮最重要的制作说明，例如“原音频是唯一时间线”“每段不少于当前模型有效时长”。

### 2. 分段导航

用 `P01—P09` 一类稳定编号建立目录、时间轴或标签导航。每个编号同时显示标题、时间范围和状态颜色，点击后定位到对应分镜卡。URL 锚点应可直达某一段，例如 `#P03`，方便反馈时直接指向问题位置。

状态颜色只做辅助，必须同时显示文字，避免只靠红绿判断。编号在项目中保持稳定；调整时长不随意重排编号，确需新增时可以使用明确的新编号并同步全部导出物。

### 3. 一段一张执行卡

每张分镜卡建议按实际操作顺序排列：

1. 时间、内容依据和试听按钮；
2. 本段叙事作用、起始状态、结束状态和段内镜头；
3. 参考图缩略图及每张图的职责说明；
4. 场景图提示词和复制按钮；
5. 整段视频提示词和复制按钮；
6. 硬约束与验收清单；
7. 当前结果、失败原因、修改记录和制作状态。

这样操作者试听后可以直接判断画面，再复制本段提示词，不需要在音频文件夹、分镜文档和多个 TXT 之间来回切换。

### 4. 详情按需展开

常用信息保持可见，较长提示词、失败记录和历史版本允许折叠。默认展开当前要执行的内容，避免所有长文本同时铺开造成滚动负担。桌面端可以使用“左侧分段导航 + 右侧内容卡”；窄屏改为单列，按钮保持足够大的点击区域。

## 三、必须具备的交互

### 分段音频播放

- 每张卡播放对应裁切音频，并显示该段时间范围和实际时长；
- 同一时间只播放一个音频，切换段落时停止上一段；
- 播放失败要显示具体提示，不能点击后毫无反应；
- 原始音频与分段音频分开标识，防止把全曲当成本段素材上传；
- 浏览器通常限制自动播放，页面应由用户点击后开始播放。

### 一键复制

- 图片提示词、视频提示词分别设置按钮，按钮紧邻对应文本；
- 复制内容必须与界面显示和导出 TXT 完全一致；
- 成功后显示短暂反馈，例如“已复制 P03 视频提示词”；
- `navigator.clipboard` 不可用时提供文本选择或兼容回退，不能让按钮静默失效；
- 不把标题、按钮文字或折叠说明混入复制内容。

### 参考图查看

- 显示缩略图、文件名和职责，例如“只锁定主角形象，不复制背景”；
- 点击可放大查看，缺图时显示缺失文件名；
- 每段只列剧情需要的资产，不能因为全片存在某角色就默认上传；
- 错误参考图标记为停用，不继续出现在正式视频参考列表。

### 状态与问题记录

- 状态必须表达当前制作动作，而不是模糊的“处理中”；
- 返工段记录问题、判断依据和下一次只改什么；
- 当前采用版本与废弃版本分开，页面默认展示当前版本；
- 只有实际看图、播放视频或检查导出结果后，才能标记“已通过”。

搜索、筛选、全局进度、批量导出和版本对比属于增强功能；只有项目规模需要时再增加，不能让装饰性功能压过试听、复制、看图和验收。

## 四、工作台怎样进入制作流程

1. **读取输入**：核对完整音频、文案、客户要求、平台、画幅和交付格式。
2. **建立分段**：以音频为主时间线，记录歌词、旁白、纯音乐和每段叙事作用。
3. **设计资产**：建立可复用角色与风格资产，并按剧情状态准备场景关键图。
4. **写入单一数据源**：把时间、镜头、参考职责、图片提示词、视频提示词和验收条件放入同一段记录。
5. **生成工作台**：由数据渲染导航和分镜卡，同时生成对应 TXT 或清单。
6. **逐段制作**：试听本段，查看参考职责，复制提示词，完成生图或生视频。
7. **回填与复核**：登记结果文件、失败原因、修正内容和状态；通过后再进入下一段或后期。
8. **最终剪辑**：以原始音频重新对齐全部镜头，工作台状态不能代替成片时序和画面验收。

需求、分镜或提示词变化时，先改数据源，再重新生成或刷新页面。不要只改页面可见文字却留下旧 TXT，也不要只改 TXT 而让工作台继续复制旧版本。

## 五、本地 HTML 的实现与交付边界

静态单页 HTML 适合本地、轻量、无需登录的制作包。建议使用相对路径组织音频、图片和提示词文件，保证整个文件夹移动后仍能运行。中文文件名和空格必须经过实际浏览器请求测试，不能只检查文件存在。

直接用 `file://` 打开时，浏览器可能限制音频、模块脚本或剪贴板权限。正式交付应提供一条简单的本地 HTTP 启动方式，例如在制作包目录运行：

```powershell
python -m http.server 8765
```

然后访问 `http://127.0.0.1:8765/页面文件名.html`。端口只是示例，占用时可以更换。页面不能写死某台电脑的绝对路径，也不能把客户隐私或本机目录暴露在对外交付版本中。

如果需要多人同步状态、云端保存结果、权限管理或在线审核，静态 HTML 不再足够，应进入应用开发流程。`localStorage` 只适合保存单机偏好或临时状态，不能当作可靠的项目数据库。

## 六、视觉与可用性要求

- 先突出段号、时间、内容依据和当前动作，再显示说明性文字；
- 提示词使用便于选择和阅读的等宽区域，但字号不能过小；
- 图片提示词与视频提示词使用稳定标签和不同按钮，不能只靠颜色区分；
- 参考图、提示词和验收条件在同一张卡中保持邻近，减少错误上传；
- 长页面保留当前位置反馈，返回导航后仍能知道正在处理哪一段；
- 交互状态包含默认、悬停、按下、成功、失败和不可用；
- 适配常见桌面宽度和手机窄屏，不能通过水平滚动才能看到复制按钮；
- 装饰、渐变和动画服务于层级，不能抢过音频、分镜和操作入口。

涉及实际前端开发时，同时读取[前端 UI 质量标准](../../../development/experience/frontend-ui-quality-standards.md)，检查响应式、键盘、触控、加载和错误状态。

## 七、交付前实际验收

| 检查项 | 通过标准 |
|---|---|
| 音频覆盖 | 所有分段覆盖完整音频；无意外漏段或重叠；每段显示时间与真实文件一致 |
| 音频交互 | 实际点击每段播放、暂停和切换；页面有可见状态，失败有提示 |
| 提示词复制 | 图片和视频按钮逐个抽查；复制内容与当前页面及导出 TXT 一致 |
| 参考图 | 缩略图可加载、可放大、职责明确；停用图不出现在正式列表 |
| 导航 | 段号、锚点、上一段／下一段跳转正确，刷新后能定位指定段落 |
| 分镜完整 | 每段有内容依据、叙事作用、起止状态、制作方式和验收条件 |
| 状态可信 | “已通过”有实际媒体检查依据，返工项写清问题和下一步 |
| 响应式 | 桌面与窄屏内容不遮挡，按钮可操作，长提示词不撑破布局 |
| 路径与交付 | 换到交付目录后仍能通过本地 HTTP 打开；无本机绝对路径和隐私信息 |
| 最终成片 | 另行播放成片检查画面、文字、比例、时序和声音；网页检查不能替代成片检查 |

测试不能只看页面是否成功打开。《小树叶》实际暴露的问题是：页面存在，但 `file://` 下音频点击没有反应；修复后通过本地 HTTP 服务逐项测试播放和复制按钮，才算交互可用。

## 八、让 AI 生成工作台时的任务骨架

```text
请把本项目的音频分段、分镜、参考图、图片提示词、视频提示词和验收条件整理成一个本地可运行的交互式制作工作台。

输入：原始音频与文案、分段时间表、参考资产目录、每段提示词和当前制作状态。

要求：
1. 使用单一结构化数据源生成页面，不在多个区域重复维护同一字段。
2. 页面包含项目总览、分段导航和“一段一张执行卡”。
3. 每段可播放对应音频、查看并放大参考图、了解参考图职责、复制图片提示词和视频提示词、查看起止状态与验收条件。
4. 支持URL锚点直达段落，显示待制作、需返工和已通过状态。
5. 音频或复制失败必须给出可见提示；复制文本不得混入界面标签。
6. 使用相对路径，提供本地HTTP启动说明，不写死本机绝对路径。
7. 桌面和手机窄屏均可操作，长提示词不破坏布局。
8. 交付前实际测试全部音频、复制按钮、图片路径、锚点和响应式布局，并报告未验证部分。
```

具体项目仍需把真实分段、素材职责、提示词和平台限制填入任务，不能只给这段骨架让 AI 自行猜测。
