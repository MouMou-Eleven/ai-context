# 对外方案的内容设计与验收

状态：当前采用。2026-09-17建委明确纠正；依据见[修订记录](../revisions/2026-09-17-external-proposal-and-word-format.md)。

## 何时使用

面向政府、企业、合作单位或项目组织方提交培训方案、课程纲要、项目策划或合作方案时使用。先读[内外稿边界](external-deliverable-language.md)，再确定方案接收者的决策需要。培训方案属于对外方案，不因含“培训、实操、时长”就自动变成学员课件或讲师备课稿。

不适用：用户明确要内部讨论、逐字稿、操作教程、研究报告、技术尽调或合同；这些体裁按自身规则保留需要的信息。没有禁止所有方案出现流程、限制和来源：接收方明确要求实施流程、验收依据或采购责任时，呈现完成该用途所必需的内容。

## 从接收者的问题决定内容

| 接收者需要知道 | 对外方案写什么 | 默认留内部 |
|---|---|---|
| 适合谁，解决什么问题 | 对象、目标、课程或项目定位 | AI怎样判断受众、如何查证资料 |
| 包含哪些内容 | 模块主题、应用场景及简要介绍 | 提示词、软件逐步操作、讲师切屏路径 |
| 能获得什么 | 学习收获、成果类型、可理解的价值 | 辨错脚本、故障预案、模拟输出、核验流水账 |
| 由谁承担，规模如何 | 讲师介绍、主讲主题、时长与规模 | 两位讲师如何对齐术语、内部协作及排练分工 |
| 怎样组织 | 与规模相适配的授课形式或必要实施安排 | 账号彩排、预录回退、版本切换和执行检查卡 |

具体任务决定栏目数量，不固定套六章或固定页数。AI培训方案可围绕“基本信息—培训定位—课程内容—方式与收获—讲师介绍”组织；其他项目围绕其目标、内容、成果和必要合作事项展开。

## 研究要充分，正文要有取舍

- 真实场景、政策、功能和讲师事实仍须核验；来源、网址、资料日期、能力限制及未实测项保存在内部工作记录。用户未要求时，对外培训方案不附网址、参考文献、证据范围或工具依据章节。
- 案例在方案中交代“具体工作场景、涉及工具、学习内容或成果”。不搬入原文事项表、证据表、材料缺口、逐步操作或提示词。
- “讲解脱敏与人工审核”是课程内容，可以简洁保留；“现场不预设AI一定出错”“未实测所以不保证”等是制作说明或免责话语，移出方案。安全培训不等于在整份方案里反复写安全免责声明。
- 讲师姓名、资历和主讲主题帮助选择课程，应保留；如何衔接、谁准备材料、哪些内容不重复属于内部备课分工。
- 时长采用用户确认值或原有区间。内部设计过90／105／120分钟，不代表应在外稿呈现三套配置和联动计算。截图作为排版参考时，不移植其中日期、姓名、身份或课程时长；与用户文字冲突时以最近明确文字为准或澄清。
- 未确认的日期、费用、履约条件不编造。无关字段可不列；影响合作决策的问题先向建委单独说明。用户要含商务条件的方案或合同时，不能用本规则隐去必要条件。

## 场景型培训方案的内容深度

2026-09-18本人明确调整的[干部培训方案](../../../../projects/external-training/jinan-cadre-ai/README.md)采用全景到场景的逻辑。对外稿先说明各环节讲什么、帮助学员怎样选择和应用，再用工作任务、AI作用和成果说明场景；详细课程组织见[演示驱动方法](../../../training/experience/demo-driven-course-design.md)。

用户暂不确定品牌时，写能力类别与组合方法，不擅自补品牌清单。提示词是教学主题时应说明学习内容和收益；本文件要求移出的是提示词原文、逐步操作和讲师脚本，不能连教学主题一起删除。工作台、自动化和本地化可作为课程内容，但不把计划演示写成已交付系统或实测效果。给组织方理解的功能介绍与讲师逐步操作仍需区分。

## 本次真实反例怎样改

| 被指出的问题 | 处理动作 |
|---|---|
| “以公开真实材料为基础，以可核验的工作成果为落点” | 从方案删去制作原则；直接说明培训内容与收获 |
| “本方案为课程设计文件；培训日期、场地与理论环节讲师由组织单位统筹安排” | 删除无意义的文档自述及未定事项包装；有确认信息才填写 |
| “两场授课的分工”“课前统一能力边界与术语” | 删除内部协作章节，保留讲师姓名与主讲主题 |
| “各配置的内容边界”“整体时长联动” | 删除内部版本设计，保留实际时长或用户给定区间 |
| “每个案例使用同一条操作路径”“现场不预设AI一定出错” | 删除教法执行与保证式解释，不把方案写成教案 |
| “原文中的事项”“应当保留的判断边界”“清单记载” | 从案例复核表改为应用场景与课程内容介绍 |
| “公开政策与案例来源”“工具依据与使用说明”“案例与演示的证据范围” | 从对外方案移到内部证据记录 |

这些是反例的处理判断，不是可用同义改写绕过的禁词表。即使没有出现“内部”“讲师提醒”，段落仍可能只对制作者有用。

## 交付前必须取得的实际证据

1. 草稿按“接收者要理解或决定什么”逐段审查；删掉以后不影响理解、只解释制作过程的段落，移回工作记录。
2. 对用户点名删除的内容检查全文及同义表达，不只删原句；核对工具、姓名和时长等最新要求。
3. 对实际DOCX运行 `python system/repository/maintenance/check-deliverable.py <文件> --profile external-proposal`；采用政企Word样式时加 `--layout gov-enterprise-word`。已知反例和网址进入复核清单；不是发现风险就把检测解释重新贴回外稿。
4. 人工审读正文，检查是否有具体内容与价值；脚本未命中不能证明语义合格。保留hash及实际修改记录。
5. 按[交付格式](../delivery-formats/README.md)选择已确认样式，渲染全部页面并查看主标题、正文、分页和末页。不以“生成成功”或“页数正确”代替视觉验收。

本规则用于减少已发生的失误；跨任务效果以真实交付反馈验证，不承诺依靠仓库文本就杜绝所有模型错误。
