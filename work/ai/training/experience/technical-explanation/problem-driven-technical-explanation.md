## 一句话原则

不要从定义开始讲一个技术。先让读者知道它为什么会出现、上一个办法哪里不够用，再顺着问题把新概念推出来。

这类文稿像真人，不是因为用了很多口头语，而是因为作者一直在做真实的思考：提出疑问、拆开问题、比较方案、承认意外，最后给出自己的判断。

## 一、最值得学习的叙事顺序

### 1. 先抛出现象，再问真正的问题

开头不要写“随着人工智能技术不断发展”。从读者最近看见的现象开始，然后追问一句真正值得解释的问题。

例如，不要从“上下文窗口的定义”开始。可以先说：现在很多模型都开始支持很长的上下文，但能放进去很多文字，和能不能准确找到信息、连续完成任务，其实不是一回事。问题自然出现后，再解释上下文、注意力和长程任务。

### 2. 先把复杂问题压缩成少数几个矛盾

面对复杂主题，先回答“这件事本质上在解决哪两三个问题”。这一步不是为了凑三点，而是为了给读者一个能够记住的坐标系。

好的分类应满足三个条件：彼此不重复、能够覆盖后文、每一项都能继续展开。无法解释后文的分类不要放在开头。

### 3. 用“问题—旧办法—新问题—改进办法”完成推导

不要直接扔出一串缩写。先说原来的做法解决了什么，再说它为什么不够，最后介绍新方案怎样补上缺口。

推荐链路：

```text
现实需求
→ 直接做会遇到什么问题
→ 最早的解决办法
→ 旧办法留下的缺口
→ 新方法解决了哪一部分
→ 仍有哪些限制
```

读者沿着这条链路走到新概念时，会感觉它是“自然出现的”，而不是被迫背下来的。

### 4. 用真实任务检验，不只报参数和跑分

参数只能说明模型被怎样设计，不能自动说明它在真实工作中好不好用。课程和文章中应优先加入具体任务、输入、过程、结果和失败情况。

真实体验里可以出现报错、超时、断网、第一次没做对、追加要求后才修好。这些细节不会削弱专业性，反而让判断更可信。不要为了让案例显得完美而删除所有意外。

### 5. 结尾给判断，不机械复述目录

结尾不要再写一遍“本文介绍了 A、B、C”。应回答开头的问题，并把技术落回成本、工程现实、人的工作方式或行业变化。

好的结尾不是拔高口号，而是把文章里已经证明的内容收成一句明确判断。

## 二、抽象概念怎样讲得像人话

### 先讲“它解决什么”，再讲“它叫什么”

普通人不关心一个缩写有几个英文单词，先关心它和自己有什么关系。术语第一次出现时，优先回答四个问题：

1. 没有它时会遇到什么麻烦？
2. 它具体改变了哪一步？
3. 可以用什么日常场景理解？
4. 最后用哪一句话记住？

### 一个概念只配一个主要比喻

比喻要来自日常经验，例如新员工、工具箱、书桌、仓库、道路或接口。比喻的作用是降低第一次理解的门槛，不是替代技术事实。

同一段不要连续换三个比喻。选一个最贴切的，把对应关系说清楚，然后及时回到真实概念。

### 用动作替代抽象名词

“提升效率、实现赋能、构建能力闭环”很难形成画面。优先写人或系统实际做了什么：找到哪份文件、比较哪两段内容、修改哪个页面、运行什么测试、生成什么结果。

### 给术语留下一句能记住的话

一句话记忆点应该准确、具体，并能覆盖后文。它不是夸张口号。

例如解释渐进式披露，可以说：先看目录，确定相关后再读正文，执行到具体步骤时才加载脚本和附件。读者记住的是信息怎样进入上下文，而不是只记住一个名词。

## 三、让语言减少“AI 味”的具体规则

### 应该保留

- 长短句交替，不把每段写成同样长度。
- 具体的人、场景、任务、时间点、错误和结果。
- 清楚的因果连接：为什么、所以、但问题是、这就导致。
- 作者自己的判断，但判断必须有前文证据。
- 少量自然口语，让读者感觉在听一个懂行的人解释。
- 对不确定性和失败的诚实说明。

### 应该删除

- “随着……不断发展”“在当今时代”“赋能千行百业”等空开场。
- 为了整齐而连续使用“第一、第二、第三”或“一方面、另一方面”。
- 每一节都用同一种“定义—优点—应用—总结”模板。
- 没有动作和对象的抽象词组，例如“能力构建、价值闭环、范式升级”。
- 把同一句意思换几个近义词连续说三遍。
- 读者看不懂、作者也无法落到场景中的概念组合。
- 过度顺滑的成功案例，以及没有依据的绝对判断。
- 为了显得像真人而堆网络梗、感叹号和语气词。

## 四、课程、文章和口播稿要分别处理

### 课程正文

课程要让学员形成稳定理解，不能只追求开头抓人。先建立坐标系，再用案例逐步展开；术语、图表和案例必须能在后文闭环。口语可以自然，但不能留下含义模糊的指代词。

### 技术文章

文章可以强化问题推导和方案比较，但每一处技术事实都要给来源或重新核验。不要因为参考稿使用某个模型版本，就沿用旧参数和旧排行榜。

### 视频口播稿

口播可以有更强的节奏、转折和态度。句子要便于说出口，避免一个句子塞入多层括号和五六个并列概念。画面中能够展示的内容，不必全部用旁白复述。

### 保姆级教程

教程仍以读者能否完成操作为第一目标。可以借鉴参考稿的场景开头和大白话解释，但不能牺牲步骤、界面路径、输入准备和验收标准。

## 五、AI 执行写作任务时的默认流程

### 写之前

1. 确认受众是谁，以及他已经知道什么。
2. 用一句话写出全文真正要回答的问题。
3. 找出两到四个能够覆盖全文的核心矛盾，不为了排比硬凑数量。
4. 为每个抽象概念准备一个具体场景或真实案例。
5. 区分已核验事实、个人判断和待确认信息。

### 写的时候

1. 从现象或场景进入，不从宏大背景进入。
2. 每出现一个新概念，先交代它解决上一步的什么问题。
3. 比喻出现后马上说明它与真实概念的对应关系。
4. 用真实任务展示能力，保留必要的失败和修正过程。
5. 段落之间要有因果或问题承接，不能只靠标题并排。

### 写完以后

1. 删除所有没有新信息的排比句和同义复述。
2. 检查“它、这个、这一步”是否能唯一指向前文对象。
3. 把抽象名词换成明确动作、对象和结果。
4. 检查每个术语是否有出现原因、作用和例子。
5. 朗读一遍，删掉正常说话时不会说出口的句子。
6. 对参数、产品能力、版本和排行榜重新查证。

## 六、写作时可以直接给 AI 的风格约束

```text
请先找到读者真正会问的问题，再开始写正文。

不要从定义、行业背景或“随着技术发展”开始。先给一个具体场景或现象，然后追问它背后的关键问题。

每讲一个新概念，都按这个顺序处理：
1. 为什么会出现；
2. 它解决上一种做法的什么问题；
3. 用一个日常场景帮助理解；
4. 回到准确的技术含义；
5. 用真实案例说明效果和限制。

语言要自然、具体、有判断。不要连续排比，不要堆抽象名词，不要为了整齐硬凑三点，不要把所有章节写成相同模板。允许出现失败、意外和修正过程，但不要编造体验。

结尾回答开头的问题，并给出经过正文支撑的判断，不机械重复目录。
```

## 七、交付前自检

- [ ] 开头是否出现了读者熟悉的现象或问题。
- [ ] 全文是否有一个明确的核心问题，而不是知识点拼盘。
- [ ] 新概念是否由前一个问题自然推导出来。
- [ ] 每个比喻是否准确，并及时回到了真实概念。
- [ ] 是否使用了具体任务、动作和结果，而不是只写能力标签。
- [ ] 是否保留了必要的失败、限制或不确定性。
- [ ] 是否删除了空泛排比、同义复述和抽象黑话。
- [ ] 结尾是否给出判断，而不是复述文章结构。
- [ ] 技术参数、产品能力和版本是否重新核验。
- [ ] 整篇朗读时是否像一个懂行的人在解释，而不是 AI 在填模板。
