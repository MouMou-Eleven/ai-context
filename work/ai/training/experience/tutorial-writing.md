# 面向普通用户的保姆级教程写作方法

> 状态：当前有效
> 口径确认：2026-07-13
> 适用范围：对外经验帖、社群学员教程、工具实操教程、可公开分享的飞书文档

## 一句话原则

教程不是任务完成报告，也不是 AI 的执行日志。教程只保留读者为了开始操作、作出选择、跟着完成和判断结果而真正需要的信息。

## 先判断交付物属于哪一种

| 类型 | 面向谁 | 核心问题 | 可以出现什么 | 不应该出现什么 |
|---|---|---|---|---|
| 面向用户的教程 | 普通读者、学员、工具使用者 | 我怎样从零开始做出结果 | 前置条件、步骤、界面路径、提示词、截图、案例、验收、常见问题 | AI 内部日志、本地私有路径、个人上下文、实现统计、读者不会执行的代码 |
| 项目交付记录 | 项目成员、维护者 | 这次具体做了什么 | 文件清单、版本、决策、检查结果、问题记录 | 面向大众的冗长铺垫 |
| 技术实现文档 | 开发者、维护者 | 系统怎样实现和排错 | 架构、命令、配置、数据结构、测试 | 把专业细节伪装成小白教程 |
| 讲师备课资料 | 讲师 | 应该怎样讲 | 讲课顺序、逐字稿、演示提示、时间安排 | 直接作为学员正文发布 |

用户要求“教程、经验帖、保姆级、给学员看、可以分享”时，默认进入第一种，不得把项目交付记录或技术实现文档直接改标题后交付。

## 读者感知过滤器

每一段内容写入正文前，依次问四个问题：

1. 读者是否需要亲自执行这一步？
2. 读者是否需要根据这段信息作出选择？
3. 读者是否需要用它判断自己做对了没有？
4. 不知道这段内容，读者是否会卡住、误操作或无法得到结果？

四个答案都是否定时，内容不进入公开教程。它可以保留在项目记录里，但不能占用读者注意力。

## 推荐的信息顺序

面向普通人的工具教程，优先按下面的理解顺序组织：

1. **先说能解决什么问题。** 用读者熟悉的场景和结果开场，不写“本文记录了某次任务”。
2. **展示前后对比。** 能展示原始状态和最终结果时，优先直接放可观看、可打开的案例。
3. **列出真正绕不过去的前置条件。** 只写用户必须准备的账号、权限、软件、素材或设备。
4. **完成一次性安装或配置。** 优先提供一段可直接复制给 AI 的提示词，减少普通人手动执行命令。
5. **教用户怎样准备输入。** 说明文件命名、素材分类、必填信息和容易遗漏的约束。
6. **先分析和确认，再执行。** 对不可逆或成本较高的任务，先让 AI 给方案，用户确认后再生成。
7. **给出主操作提示词。** 提示词要包含目标、输入、约束、输出、确认节点和验收标准。
8. **教用户怎样审片或验收。** 使用普通语言的检查清单，不只写“系统会自动验证”。
9. **提供修改反馈示例。** 让读者知道如何按时间点、页面区域或结果差异反馈。
10. **补充常见问题和必要链接。** 只保留会真实阻塞操作的问题。

## 环境与代码的取舍

### 什么时候应该写环境

只有下面三种情况才写入面向用户的教程：

- 用户必须亲自安装或授权，否则无法开始。
- 安装过程需要管理员权限、付费账号或人工确认。
- 缺少该环境会产生一个读者能识别的明确错误，需要提前规避。

如果 Codex 或其他 Agent 能自动检查和安装，就写“让 Agent 自动处理，出现人工确认时再操作”，不要把 Agent 执行的全部底层命令抄进教程。

### 什么时候应该写代码或命令

满足以下任一条件才保留：

- 用户必须亲自运行，且没有更简单的界面操作或提示词替代。
- 该命令本身就是教程要教会的核心能力。
- 用户需要复制它才能完成下一步。

转写数据结构、时间轴 JSON、内部剪辑区间、渲染参数、检测日志、依赖安装细节等，如果由 AI 自动完成，就不进入普通用户教程。

## AI 工具教程应以提示词为主要操作界面

普通用户使用 Agent 时，真正可复用的操作通常是提示词，而不是底层代码。提示词至少应包含：

| 要素 | 要回答的问题 |
|---|---|
| 任务目标 | 最终要做出什么 |
| 输入位置 | 文件、文件夹、链接或数据在哪里 |
| 必须保留 | 哪些内容不能删、不能改、不能公开 |
| 可接受边界 | 同义表达、时长、比例、风格能否变化 |
| 执行顺序 | 是否要先分析、先提方案、等待确认 |
| 输出要求 | 交付什么格式、放在哪里、是否先给预览 |
| 验收标准 | 怎样算完成，哪些错误必须自行检查 |

安装提示词、首次分析提示词、正式执行提示词和修改反馈提示词应分开。不要把所有要求塞进一个没有阶段控制的长提示词。

## 图片与案例的使用规则

图片不是装饰，每张图都要回答一个具体问题。

- 前后对比图回答“使用后发生了什么变化”。
- 步骤截图回答“这一项在哪里、应该点什么”。
- 局部放大图回答“容易看错或容易漏掉的细节是什么”。
- 时间线、波形或结构图回答“AI 如何区分或用户如何验收”。
- 抽象技术概念优先使用机制型可视化：直接画出对象怎样组成、文件怎样传递、页面怎样变化。只写概念名称、放一个图标或用思维导图重复正文，不算有效配图。
- 能用真实 HTML/CSS/JavaScript 精确呈现的结构和交互，优先制作可运行案例并截图；课程明确要演示某个案例时，同时交付可以运行、修改和上传的文件。

图片放在它所解释的步骤附近，不能全部堆在文末。图片前后必须有一句说明：读者应该看哪里、这张图证明什么。只要条件允许，案例应同时提供原始版本和最终版本，避免只展示结果而无法形成对比。

## 语言和视角

- 使用“你要准备什么、你会看到什么、接下来怎样做”的读者视角。
- 当课程已经确认读者的角色、学习目标和知识深度时，正文直接陈述结论，不写“如果你的目标是……”“不必一开始……”“可以先……”等条件式或阶段式建议。必须明确告诉读者哪些概念要理解、哪些技术细节不需要深入，以及人和 AI 分别负责什么。
- 不写“用户点名了某插件”“本次调用了某工具”“此次参考了某文件”等内部工作口吻。
- 不引用读者无法访问的本地文件、私人仓库和个人上下文。
- 不用专业术语证明完整；术语只有在影响操作或验收时才解释。
- 不在开头写任务完成时间、交付结果或版本记录，把注意力直接放在问题和结果上。

## 外部风格参考

需要编写 AI 课程或培训技术讲解，并减少空泛排比、概念堆砌和模板化“AI 味”时，按需读取 [`technical-explanation/problem-driven-technical-explanation.md`](./technical-explanation/problem-driven-technical-explanation.md)。自媒体文章与口播任务进入 AI 自媒体目录，原始来源材料默认不读取。

这份参考强调“先提出真实问题，再推导新概念为什么出现”，适合讲解 Agent、Skill、MCP、RAG、上下文、多模态等抽象技术。它只提供叙事与表达方法；原始逐字稿中的模型版本、参数和排行榜必须重新查证，不能直接当作当前事实。

## 飞书教程的推荐呈现

- 开头用一句话说明用途，再进入具体场景。
- 流程、对比和前置条件使用表格；叙述与判断使用短段落。
- 可复制提示词使用独立的提示词块，不与正文混写。
- 风险提醒使用少量高亮块，避免每一节都做成卡片。
- 视频、截图和案例放在对应步骤附近，并使用清楚的图注。
- 目录只保留真正的章节，不把每个字段和一句话升级成标题。

## 交付前检查清单

- [ ] 标题是否直接说明工具、任务和结果。
- [ ] 开头是否先说读者能解决什么，而不是汇报任务过程。
- [ ] 是否明确了适合谁、需要准备什么。
- [ ] 是否只保留用户必须操作的环境和权限。
- [ ] 是否删除 AI 自己执行的代码、日志、数据结构和检测参数。
- [ ] 是否提供了可复制的提示词，并标明使用阶段。
- [ ] 是否有原始状态与最终结果的对比。
- [ ] 每张图片是否放在合适的位置并说明看点。
- [ ] 抽象概念的图片是否真的表现了机制、关系或前后变化，而不是只重复概念名称。
- [ ] 课程案例是否提供了可运行文件，而不是只有提示词、文件树或结果截图。
- [ ] 是否教会读者怎样反馈修改、怎样验收结果。
- [ ] 是否删除私人路径、个人上下文和外部读者无法访问的引用。
- [ ] 读者从头跟到尾，是否能独立做出一个结果。

## 常见失败方式

- 把“做完了什么”写成第一章，导致文章从一开始就是交付汇报。
- 为了显得专业，加入大量底层工具、命令、数据结构和检查日志。
- 只讲工具原理，不给素材准备方式、提示词和反馈示例。
- 只展示最终结果，不提供原始版本，读者看不出价值差异。
- 图片全部堆在文末，正文与图片没有对应关系。
- 把 AI 能自动完成的步骤变成用户的学习负担。
- 引用私人仓库、本地路径或内部决策，外部读者无法理解也无法访问。

## 适用判断

当任务同时满足“面向普通用户”和“需要跟着操作”时，优先读取本文件。若任务目标是项目复盘、开发维护或讲师备课，应切换到对应文档类型，不要强行套用本教程结构。
