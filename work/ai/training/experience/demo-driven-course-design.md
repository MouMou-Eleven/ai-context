# 从“适合阅读”到“能够讲出来”：演示驱动的课程设计

> 状态：当前有效的通用培训方法
> 确认日期：2026-09-01
> 适用范围：会员社群课程、企业培训、公开课、活动分享和面向普通人的技术概念课
> 验证来源：会员社群第3—5课真实授课、现场取舍和课后复盘

## 一、课程的首要验收标准

一份资料文字很多、结构完整、看起来专业，不代表讲师站在课堂上就有内容可讲。课程除了事实准确，还必须回答：**这段内容能不能通过语言、操作和画面被自然地讲出来。**

课程中的内容至少承担一种作用：

- 让学员看见一个动作或结果；
- 让学员发现前后差别；
- 解释刚才为什么会出现这个结果；
- 给出一个能够用于选择或验收的判断；
- 为下一个知识点建立必要前提。

只让资料显得完整、讲师现场大概率会跳过的段落，不进入课堂主线。

## 二、课程和文章不是同一种交付物

文章允许读者停下来、回看和消化长句。现场课程一直向前推进，学员的注意力还会在讲师、屏幕、操作结果和课件之间切换。

课堂主文档默认使用自然、可朗读的口语化表达。一句话只承载一个主要判断，明确谁做了什么、发生了什么变化。完整背景、延伸资料和书面推导只有在课堂确实需要时才保留；备课节奏、切屏动作和讲师提醒另写备课稿。

## 三、先建立学习坐标，再进入内容

独立课程需要补齐必要背景。系列课程先读取已经讲过的内容，不重复总环境、职业案例和课程总价值，只建立本节独有的痛点、重要性和前后承接。

开场根据实际需要说明：

1. 学员现在怎样做；
2. 当前方式具体卡在哪里；
3. 学完以后会多出什么使用、选择或验收能力；
4. 这项能力后面会在哪里继续用到。

开场不提前堆正文尚未解释的专业名词。痛点从学员熟悉的行为和结果进入，术语在真正需要时出现。

## 四、宏观认知与具体落地使用不同结构

宏观认知的目标是看清范围和关系，可以整体架构先行。例如讲 AI 能够进入哪些行业时，一张全景图比逐个行业拆成实操更有效。

具体落地和实操的目标是让学员真正会使用、选择或验收。课程必须检查概念的前置关系：后面才会单独解释的术语不能提前承担关键说明。必要概念讲清后，再用完整案例串联。

某一篇文章或某一节课的章节不能升级成所有课程的固定模板。通用检查只有四项：本节目标是什么、学员已经知道什么、概念第一次在哪里出现、当前内容怎样承接后文。

## 五、技术内容先经过专门筛选

本方法只解决已经选定的内容怎样变成可讲课程，不维护第二套技术知识筛选标准。每个概念进入课程前，先调用 [`technical-explanation/problem-driven-technical-explanation.md`](./technical-explanation/problem-driven-technical-explanation.md)，判断普通人是否需要学习，并根据功能、风险、选择、性能、额度或使用体验确定解释角度。

只有通过筛选的概念，才继续设计现场动作、画面、对比和可记住的判断。专业目录中存在但不会改变当前使用和结果的内容，不因为需要“凑完整”进入演示环节。

## 六、具体概念怎样变成可讲内容

面向普通人的落地概念，可以优先使用这条链路：

```text
熟悉任务
→ 过去怎样完成
→ 原来的麻烦在哪里
→ AI 或新工具改变了哪一步
→ 屏幕或结果发生什么变化
→ 这个变化叫什么
→ 学员以后怎样使用或判断
```

第3课解释 CLI 时，用鼠标创建文件夹、手工输入命令和让 AI 自动执行同一个任务形成对比。学员先看见操作方式的变化，再理解 CLI 给 AI 提供了怎样的执行入口。实操的作用是帮助理解，不是要求学员背下所有命令。

不是每个概念都要修改电脑。Context 可以用长对话和项目说明文件做记忆对比；API 可以并排展示普通网页和 API 返回结果；Harness 可以让普通聊天工具和 Codex 完成同一任务，再比较过程和结果。关键是让学员看见差别。

### 版本更新类内容先重建使用逻辑

版本发布文章、更新日志和官方教程是事实来源，不是现成的课程结构。制作“新功能、隐藏功能、进阶能力”课程时，先筛选真正会改变学员操作、选择、成本、风险或验收方式的变化，再按实际使用场景和项目阶段重新组织；不能按发布日期、版本号或功能数量逐项搬运。

每个进入主线的新功能至少要能回答四件事：原来在哪个场景会卡住；当前入口和真实操作是什么；操作以后屏幕或业务结果发生什么变化；怎样验证它确实可用。官方截图放在对应动作和结果附近，正文补充截图无法表达的因果、边界和判断。只有截图却没有可讲结论，或者只有更新说明却没有使用场景，都不能形成课堂内容。

多个版本共同构成当前能力时，以当前界面和最新有效口径为准，不把新旧入口混成两套流程。只改善界面便利性、但不会影响当前课程判断的小更新，可以不进入主讲；课程的完整度来自使用链路闭环，不来自把更新日志全部讲完。

## 七、文字、表格、演示和图片必须分工

### 文字解释原因和判断

正文回答“刚才发生了什么、为什么会这样、以后怎样判断”。画面已经能够证明的内容，不用长段文字复述。

### 演示提供真实证据

屏幕操作展示步骤、变化、结果和必要的失败过程。课程说要演示某个网页、工具或项目时，必须准备能够真实运行、修改和上传的文件；提示词和文件树不能替代运行结果。

### 表格只做真正的比较

表格适合三个以上对象的横向差别、选择依据或字段映射。正文已经逐项讲过的内容，不再复制成同义表格。讲师讲完正文会自然跳过的表格，应删除或改成真正有比较价值的内容。

### 图片补足文字缺少的画面

图片用于呈现关系、机制、动作、变化或对比，不是把课件文字重新排版一次。

- 真实软件和云平台的按钮、菜单、路径、价格和状态使用实际截图或真实运行画面。
- 概念、理论、生活场景、优缺点和抽象关系可以使用 AI 生图，但要检查文字、对象关系和技术含义。
- 能用真实 HTML、CSS 或 JavaScript 精确表达的结构和交互，优先制作可运行页面再截图。
- 前后对比尽量使用同一个对象，让学员看见某一项变化具体带来了什么。
- 图片放在对应知识点附近，不要求每张图前后使用固定说明句式。

是否配图只看三个判断：文字是否已经足够形成画面；图片能否增加新信息；图片能否帮助学员理解并帮助讲师讲解。

## 八、简化技术，但不要改变事实

面向小白不等于可以用错误机制换取易懂。类比帮助第一次理解，讲完后要回到真实概念；动态功能、页面路径、价格和参数要重新核验。

严谨主要体现在事实准确、关系讲清和选择依据正确，不体现在每句话后面补例外。常见机制可以直接说清主链路；只有例外会改变当前案例、决定、费用、风险或验收时才展开。课堂不是合同，也不是专业标准全文。

一个简化表达如果已经准确支撑本节理解和后续操作，就完成了教学任务；不需要紧接一段话枚举所有不同架构。具体课程使用的主链路和例子留在对应项目文件，本通用方法不复制第二套案例口径。

## 九、判断一段内容能不能讲

写完以后做一次可讲性检查：

1. 朗读一遍，正常说话时不会使用的句式直接改掉。
2. 找出对应的画面、操作、问题、变化或判断；一个都找不到时移出主线。
3. 检查相邻段落是否只是同义复述，保留最清楚的一版。
4. 检查专业名词是否在被解释前出现，顺序错误时调整结构。
5. 问“讲完以后学员新看见了什么、会做什么决定”。没有新增理解时通常可以删除。
6. 检查标题、问题和答案是否处在同一个角度，不把相关性很低的注意事项硬塞进来。

口语化不等于堆语气词。真正的口语化来自熟悉场景、明确动作、清楚因果和自然停顿。

## 十、讲后复盘怎样变成课程资产

真实授课后优先记录：

- 哪些内容被完整讲了、被一句带过或被直接跳过；
- 哪个演示最容易理解，哪个需要反复解释；
- 哪些句子被讲师临场换成了另一种说法；
- 哪个概念因为缺少前置说明打断了节奏；
- 学员在哪里提问、误解或表现出明显反应；
- 现场补充了哪些原稿没有但特别有效的例子。

复盘不是继续加字。先判断应该删重复、换顺序、补画面、改案例、改口语，还是把专业细节移到课后资料。课程变短不等于内容缩水，可讲内容的密度更重要。

## 十一、交付前检查

- [ ] 本节是系列课还是独立课，是否正确处理了背景。
- [ ] 本节是宏观认知还是具体落地，结构是否匹配。
- [ ] 每个概念是否已经通过技术解释方法完成学习价值筛选和解释角度判断。
- [ ] 每个核心概念是否有操作、画面、测试、对比或可记住的判断。
- [ ] 前置概念是否在第一次承担解释任务前出现。
- [ ] 正文、表格、演示和图片是否各自增加新信息。
- [ ] 课堂主文档是否口语化，并且没有授课时长和讲师内部提示。
- [ ] 提示词是否为当前演示所必需，案例文件是否能够真实运行。
- [ ] 事实是否核验，同时避免了没有教学价值的免责和例外堆叠。
- [ ] 讲师现场大概率会跳过的完整性内容是否已经删除。
