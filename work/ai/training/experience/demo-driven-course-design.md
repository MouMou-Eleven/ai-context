# 从“适合阅读”到“能够讲出来”：演示驱动的课程设计

> 状态：当前有效的通用培训方法
> 确认日期：2026-08-18
> 适用范围：会员社群课程、企业培训、公开课、活动分享和面向普通人的技术概念课
> 首个验证来源：2026-08-16 晚会员社群第3课真实授课及次日复盘

## 一、这次授课确认了什么

一份课程资料可以文字很多、结构完整、看起来很专业，但讲师真正站在课堂上时，仍然可能没有内容可讲。第3课的实际授课暴露出以下问题：

- 文字和表格重复表达同一个意思，讲完正文后表格只能跳过。
- 抽象概念只有定义和组成，没有可操作的前后对比，学员看不到它改变了什么。
- 为了知识完整加入过多工程细节，内容适合阅读或查阅，却不能自然地说出口。
- 新概念在前置概念尚未解释时提前出现，讲课过程中需要临时补定义，节奏被打断。
- 章节数量和字数看起来充足，真正能够展开的讲点很少；多个段落只是在换一种说法重复结论。
- 讲师现场直接跳过了 Harness 八件事、按钮改色、工具失败、长任务循环、学习顺序和标准答案式自检。这些“被跳过的内容”证明课程设计没有转化为可讲动作。

因此，培训课程的首要验收标准不能只是“信息是否完整”，还要增加一个更重要的标准：**这段内容能不能通过语言、操作和画面被自然地讲出来。**

## 二、课程和文章不是同一种交付物

文章允许读者停下来、回看、比较表格和消化长句。现场课程一直向前推进，学员的注意力还会在讲师、屏幕、操作结果和课件之间切换。

课程中的内容至少要承担一种明确作用：

- 让学员看见一个动作。
- 让学员发现前后差别。
- 解释刚才为什么会出现这个结果。
- 给出一个能够记住的判断。
- 为下一个问题建立前提。

如果一个段落不承担这些作用，只是让资料看起来更完整，它更适合放进延伸阅读、参考资料或课后文档，而不是课堂主线。

## 三、先让学员知道为什么学

技术概念课不能打开文档就进入术语定义。学员如果不知道这些概念会改变什么，后面的内容即使准确，也容易被理解成与自己无关的理论。

课程开头先回答四个问题：

1. **学员现在怎样做。**从学员已经存在的使用习惯开始，而不是假设他们已经认同课程价值。
2. **当前方式为什么会卡住。**指出能够被感受到的限制，例如 AI 只能根据一句模糊要求猜、看不到真实项目、不能调用外部工具或无法执行操作。
3. **学完以后会发生什么变化。**说清楚学员会多出哪些判断、连接或执行能力，不只说“提高效率”“系统学习”。
4. **后续会在哪里继续用。**把本节内容与后面的案例、项目或课程连接起来，让学员知道今天建立的是后续操作的地图。

这不是营销开场，而是建立学习坐标。痛点必须来自学员真实行为，收益必须对应课程正文，不能用夸张承诺代替教学目标。

当一节课同时解释多个概念时，先把它们放进同一个熟悉项目。例如第3课使用课程报名网站串联 Prompt、Context、Skill、MCP、CLI、API 和 Harness：每个概念负责解决链路中的一个问题，组合以后，AI 才能从回答问题进一步走向理解资料、连接工具、执行操作和检查结果。学员先看见整条链路，再逐个进入概念，不容易把它们当成互不相关的缩写。

课程开场的验收问题是：**读完开场后，学员能否用自己的话说明“我为什么现在要学、它会解决我的什么问题、后面会在哪里用到”。**不能说明时，先补学习理由，不要急着继续扩写概念正文。

## 四、技术概念的默认讲解顺序

面向普通人的技术概念，优先使用下面这条链路：

```text
学员熟悉的任务
→ 过去怎样完成
→ 旧做法有什么麻烦
→ AI 或新工具怎样完成
→ 屏幕上出现了什么变化
→ 这个变化叫什么
→ 它带来了什么收益
→ 它仍然有什么边界
```

第3课的 CLI 重构就是标准样例。同样是创建文件夹：先用鼠标点击，再手工输入 `mkdir` 和 `cd`，最后只给 AI 一句自然语言，让 AI 自动执行并检查。学员先看见操作方式的变化，再理解“CLI 给了 AI 操作电脑的入口”，概念自然出现。

概念卡可以按下面八项准备：

| 项目 | 要回答的问题 |
|---|---|
| 熟悉任务 | 学员已经做过什么 |
| 旧做法 | 过去具体点击或输入什么 |
| 当前麻烦 | 慢在哪里、容易错在哪里 |
| 新做法 | AI 或新工具具体执行什么 |
| 可见结果 | 屏幕、文件、页面或数据发生什么变化 |
| 一句话概念 | 学员最后怎样记住它 |
| 直接收益 | 速度、批量处理、稳定性或可复用性提高在哪里 |
| 使用边界 | 哪些权限、风险或限制仍需要人处理 |

不是每个概念都必须真的改电脑。Context 可以用长对话与项目说明文件的记忆测试；API 可以并排打开普通网页和 API 地址；Harness 可以把同一任务分别交给普通聊天工具和 Codex，再比较结果。关键是必须出现可观察的差别。

## 五、文字、表格和演示必须分工

### 文字负责解释因果

正文回答“为什么出现”“刚才发生了什么”“这个结果说明什么”。语言应当能直接说出口，一句话只承载一个主要判断，并明确指出动作、对象和结果。

### 演示负责提供证据

屏幕操作负责展示步骤、变化和结果。画面已经能够证明的内容，不再用三段文字逐字复述。演示失败时不要急着隐藏，真实报错和修正过程本身也能成为教学内容。

### 表格负责横向比较

表格适合比较三个以上对象、展示字段样例或帮助选择。正文已经逐项解释过的内容，不再做一张同义表格。检查方法很直接：如果讲师讲完正文后会自然跳过表格，说明表格没有提供新信息，应删除或改成真正的比较。

## 六、判断一段内容能不能讲

写完以后，不只做错别字和事实检查，还要做“可讲性检查”：

1. 朗读这段内容，正常说话时不会使用的句式直接改掉。
2. 找出这段内容对应的画面、操作、问题或判断；一个都找不到时，移出课堂主线。
3. 检查相邻段落是否只是同义复述，保留信息最清楚的一版。
4. 检查专业名词是否在被解释前出现。出现顺序错误时调整课程结构，不靠临时插入定义补救。
5. 问“这段讲完以后，学员新看见了什么”。没有新变化、没有新判断，也没有为后文建立前提时，通常可以删除。
6. 把长句拆成口语能自然停顿的短句，删除“可复现证据、能力闭环、明确用户页面收藏动作和验收结果”等难以当场说明的抽象组合。

口语化不等于堆语气词。真正的口语化来自熟悉场景、明确动作、清楚因果和自然停顿。

## 七、讲后复盘怎样变成课程资产

每次实际授课后，优先记录以下证据：

- 哪些内容被完整讲了，哪些被一句话带过，哪些被直接跳过。
- 哪个演示最容易让学员理解，哪个演示需要反复解释。
- 哪些句子讲师临场换成了另一种说法，原句为什么说不出口。
- 哪个概念因为前置知识没有解释而打断节奏。
- 学员在哪里提问、误解或表现出明显反应。
- 讲师临场补充了哪些原稿没有、但特别有效的例子。

其中，现场临时讲得更清楚的例子和被直接跳过的段落价值最高。前者说明课程缺少真正的教学入口，后者说明内容虽然存在，却没有形成可讲价值。

复盘后不要只在原稿上继续加字。先判断是补演示、换顺序、删重复、改口语，还是把专业细节移动到延伸阅读。课程变短不代表内容缩水；如果每个保留部分都能被讲清楚、被看见并形成记忆，教学密度反而更高。

## 八、学员资料与讲师资料的边界

学员正文可以出现跟做步骤、演示命令、前后结果、关键链接和最后判断，但不要写“讲师这里演示”“这一部分讲多久”等内部提示。标题也遵守同一边界：“把三种方式放在一起演示”描述的是讲师动作，应改成“更加直观的案例演示”这类直接面向学员的内容名称。

讲师备课资料可以另外记录演示准备、备用素材、可能失败的位置、现场提问和节奏安排。授课时长默认不进入学员正文；只有建委明确要求时才加入。

判断一句话属于哪一侧，可以看它的主语：如果主语是“讲师接下来要做什么”，放入备课资料；如果主语是“学员正在理解什么、看到什么或可以怎样操作”，才进入学员正文。课程由讲师使用，不等于正文的观看对象变成讲师。

## 九、简化技术时不能改变事实

面向小白不等于可以用错误机制换取易懂。第3课重构中保留了两项事实修正：

- 鼠标创建文件夹和 `mkdir` 是两种不同界面完成同一结果，不能讲成“鼠标点击实际上调用了 CLI 指令”。
- Compaction 是把较早上下文总结后继续工作，不能讲成上下文窗口已经无限，也不能把结果下降写成固定的 100% 到 80%。更准确的风险是摘要可能丢失细节，模型得到的信息减少后，结果可能变差。

类比出现后必须回到准确概念。动态参数、产品功能和安装方式需要重新查官方资料；无法统一的地方明确写“以当前工具为准”。

## 十、交付前检查

- [ ] 课程主线是否由真实问题推动，而不是术语目录推动。
- [ ] 开场是否讲清当前痛点、学习收益、能力变化和后续用途。
- [ ] 多个概念是否先放进同一个熟悉项目，建立整体协作地图。
- [ ] 每个核心概念是否有操作、画面、测试或产品对比。
- [ ] 是否先展示变化，再给出术语和定义。
- [ ] 正文、表格和演示是否各自提供不同信息。
- [ ] 是否删除了讲师现场大概率会跳过的完整性内容。
- [ ] 前置概念是否在第一次被使用前解释。
- [ ] 正文朗读时是否像在对学员讲话。
- [ ] 学员正文是否没有混入授课时长和讲师内部提示。
- [ ] 标题和列表是否仍在描述讲师动作，而不是学员要理解的内容。
- [ ] 简化后的说法是否仍然符合真实技术机制。
- [ ] 课后是否记录了跳过内容、临场改说法和有效演示。

## 十一、2026-08-19 第4课修订：演示之后只留下知识点

第4课网页美化的复盘进一步确认了“讲师课件”和“学员正文”的边界。讲师现场会打开案例网站、切换页面、展示效果；这些动作不需要被写成一串让小白“观察首屏构图、标题动画和标签”的提示。学员文档应在演示完成后承接三类内容：刚才看到的共同规律、它解决的真实问题、下一步可以复用的操作方法。

这次修订新增以下规则：

- **不把演示动作写成正文。**“课堂过渡”“现场练习”“讲师这里打开”“看完案例后观察”等内部提示，以及“90分钟学习路线”，不进入给学员看的正文。直播节奏属于讲师备课，学员资料保留知识、步骤、结果和验收。
- **案例平台只提供证据。**讲师可以直接打开 Awwwards、GSAP Showcase 或其他案例平台展示多个页面；文档不必替讲师设计一套理想化的观察任务。展示结束后，用一段话说明“好看不是效果多，而是内容、视觉和交互围绕主题”，这才是可迁移的知识点。
- **图片前后必须分工。**图片前的文字只说明这张图对应的真实操作，图片后的文字解释操作结果和页面变化。不能用抽象的“这一条路径解决什么问题”替代截图正在展示的步骤。
- **工具事实要写成真实链路。**组件接入不照抄其他 AI 给出的“方式 A / 方式 B”建议。应按实际流程重构：新建 TXT 文本，用记事本整理完整源码、配置参数和依赖，上传给秒哒，要求秒哒保存并调用组件，最后检查依赖和桌面端 / 手机端效果。
- **用户提供的原始材料不是成稿。**截图、代码、其他 AI 的建议和链接都要先判断它在本节课承担什么作用，再改写成符合当前工具和当前学员的步骤；不能因为原材料看起来完整就原封不动放进正文。
- **不要用字数填充授课时长。**现场操作本身会占用时间，课程文档不需要额外写一张时间路线图来凑完整度。发现某一节只有内部提示、重复总结或无法演示的内容时，优先删除。

这条规则把“演示驱动”再推进一步：**现场展示负责让学员看见，正文负责让学员记住并复用。**

## 十二、2026-08-23：抽象概念默认使用“机制型可视化”

第4课静态网页课程再次确认：AI 培训中的可视化不能只把“浏览器”“网页文件”“HTML”几个字放到图片上，也不能用思维导图或流程图替代所有解释。可视化要把概念正在发生的事情画出来，让学员不依赖长段定义也能看见机制、关系或前后变化。

以后制作 AI 培训课程时，执行以下规则：

- **按知识点逐项判断，不预设只补几张。**网页文件组成、浏览器渲染、盒子嵌套、样式前后对比、交互状态、单文件与多文件、部署、二次更新和常见问题，只要画面比文字更容易理解，就应该有对应可视化。
- **可视化必须表达机制。**讲浏览器时，要画出“文件被读取并渲染成页面”；讲网页文件时，要画出多种文件怎样共同组成网站；讲 HTML 盒子时，要直接显示页面中的大盒子与嵌套小盒子。只有概念名称和装饰图标的图片不算完成。
- **结构和交互优先用代码原生画面。**盒子、文件关系、CSS 前后变化、JavaScript 点击状态和部署路径，优先制作可运行的 HTML/CSS/JavaScript，再从真实页面截图。这样比不可控的生图更准确，也能直接成为课堂演示。
- **图片与正文一一对应。**图片前说明正在解释什么，图片后说明学员从画面里应该理解什么。不能把大量图片集中堆在文末，也不能用一张图承担多个互不相关的知识点。
- **案例不只展示结果，还要交付文件。**课程说要演示个人简介、GitHub Pages 或多文件坦克大战时，必须准备可以实际运行、修改和上传的项目文件。只写提示词、文件树或“讲师可现场演示”不算完成。
- **前后对比必须保持同一对象。**HTML/CSS/JavaScript 的对比使用同一个页面，依次增加结构、样式和交互；这样学员看到的是某一层能力带来的变化，而不是三个无关案例。
- **生成式图片只用于它擅长的画面。**需要精确文字、路径、文件关系和 UI 状态时使用代码原生可视化；需要氛围、人物、场景或非确定性插画时再使用生图。工具选择服从教学准确性。

这项规则不是要求每节课堆满图片，而是要求所有抽象概念都有最合适的证据。能用真实界面说明的用截图，能用前后变化说明的做对比，能用运行案例说明的直接交付案例。
