# Teaching and Course Design — 备课、课程开发与课件设计

> 状态：当前有效的知识入口
> 口径确认：2026-08-18
> 适用范围：建委作为 AI 讲师进行备课、培训课程开发、培训课件设计、教学活动和讲师交付。

## 当前已经确认的边界

这里负责跨课程可复用的“怎样教”，例如课程开发方法、课件设计、讲师课件与学员资料边界、教学活动和课程复盘。它不负责某个课程产品的价格、招生话术或季度大纲。

这里也不负责教师微课、精品课、参赛课或 VR 交互课件制作。此类任务进入 [`../../../design/microcourse-mg-animation/README.md`](../../../design/microcourse-mg-animation/README.md)。

当前仓库尚未形成一套完整、经过建委确认的课程开发和课件视觉规则。AI 不能把通用教学法自行写成“建委的规则”；每次先遵循用户当次要求，确认有效后再沉淀。

## 当前调用顺序

1. 先确认培训对象、已有基础、授课场景和最终要做出的结果。
2. 判断交付物是讲师备课、讲师课件、学员课件、课程正文还是招生内容。
3. 读取所属项目的当前事实，避免课程内容和产品承诺冲突。
4. 学员正文再调用教程写作方法；技术难点再按需调用表达与讲解方法。
5. 课程规则只服务教学，不能自动套进普通文章、短视频、销售页或飞书书稿。

## 学员正文与讲师备课的边界

2026-08-16 建委确认：面向学员的课程正文默认不写“这一部分多少分钟”“每个环节多少时间”等讲师内部授课时长。时长、讲课顺序、现场提示和互动安排属于讲师备课资料；只有建委明确要求时，才在学员资料中出现时间信息。学员正文应把篇幅用于解释为什么学、怎样操作、怎样验证和遇到问题如何判断。

2026-08-18 建委进一步确认：学员正文中的标题、段落和列表也不能伪装成讲师提示。“把三种方式放在一起演示”“讲师这里打开页面”“接下来向学员展示”等措辞属于备课动作，不属于课程内容。学员正文应直接写学员要理解的对象，例如“更加直观的案例演示”“普通网页和 API 地址有什么不同”。课程资料即使由讲师用于授课，默认观看对象仍然是学员。

2026-08-19 第4课继续确认：讲师现场会直接打开案例网站并展示多个效果，学员正文不需要写“先看首屏构图、标题怎么出现、按标签观察”等理想化观察任务。演示完成后，正文只承接刚才看到的共同规律、真实操作链路和验收方法。`课堂过渡`、`现场练习`、讲师切屏提示和 90 分钟路线属于内部备课信息，不能混入学员正文。来自其他 AI 的 A/B 方案、截图和代码只能作为原始材料，必须按建委实际操作重构；组件案例统一按“TXT 整理源码、配置参数和依赖 → 上传秒哒 → 要求保存并调用 → 检查依赖和效果”表达。

2026-08-23 建委确认：AI 培训中的抽象技术概念默认需要机制型可视化，不限定只补固定数量的图片。可视化要直接呈现概念怎样工作，例如“网页文件怎样组成网站”“浏览器怎样把文件渲染成画面”“HTML 盒子怎样嵌套”“加入 CSS / JavaScript 后同一个页面发生什么变化”；只有概念名称、思维导图或装饰图标不能替代机制解释。能够用 HTML/CSS/JavaScript 精确表达的内容，优先制作可运行页面并截图；课程中的案例还必须交付可以实际运行、修改和上传的文件，而不是只写案例说明。

2026-08-29 建委确认：面向学员的正文已经确定学习定位时，必须直接写出结论，不能再用“如果你的目标是……”“不必一开始……”“可以先……”等条件式、阶段式措辞把结论弱化为可选建议。AI 时代的正确分工是：人站在项目策划者和决策者的位置，负责目标、需求、边界、验收和是否采用；AI 负责命令、底层机制和具体技术操作。正文应明确区分“必须理解的项目作用”和“不需要深入的技术细节”，并用实例说明怎样指挥 AI，不给学员保留模棱两可的学习路径。

2026-08-30 建委进一步确认：课程里的判断性表达必须准确描述“谁在做什么”。“至少要问四件事”“用七个问题把需求说清楚”把购买和项目决策改写成了课堂提问动作，弱化了学员真正要承担的判断责任。正确写法是“至少要想清楚四件事”“购买前要想清楚这些信息”，必要时再列出帮助思考的检查项。类似地，“把四个概念放回一个真实小工具”把课程动作写成了抽象口号；应改成“用一个具体工具把今天讲到的概念串起来”，并明确工具中的需求、能力、存放位置和验收证据。

涉及云服务、服务器、数据库、对象存储、域名或 SSL 的课程，不能只放产品定义或官网地址。学员需要看到：是否与服务器一起提供、是否需要单独开通或购买、价格按什么口径变化、购买入口在哪里、普通人怎样根据项目规模和运维能力选择。费用说明要区分“开发者购买时需要评估的成本”和“产品面向用户的收费设计”，不能把容量、请求次数、下载流量等成本简单写成学员当下的使用注意事项。价格必须标注查询日期，并提醒以登录后的配置、订单和续费页面为准。

## 现场授课复盘确认的课程标准

2026-08-16 晚，建委实际讲授会员社群第3课后确认：一份资料看起来信息丰富、阅读顺畅，不代表它能够被自然地讲出来。技术概念课应优先设计现场动作、前后对比和可观察结果，再补充解释；不能先写成长文章，再把文章标题当成课程目录。

当前通用规则：

- 一节课开头先建立学习理由：学员当前怎样使用、为什么会卡住、学完后会多出什么判断和能力、这些内容会在后续哪些任务中继续出现。没有这张地图，概念越多，学员越容易把课程理解成术语记忆。
- 每个核心概念至少对应一个学员能看见的操作、变化或结果。抽象概念可以用受控测试、产品对比或同一任务的前后差异呈现。
- 抽象概念的画面必须呈现机制、关系或变化；按知识点逐项判断是否需要配图，不得把“补三张图”当作整课可视化任务的上限。
- 推荐顺序是“熟悉任务 → 旧做法 → 新做法 → 结果对比 → 概念名称 → 收益与边界”，不要从英文全称和内部组成开始。
- 已确认的学习定位和角色分工直接写成结论；不得用“如果你的目标”“暂时不需要”“不必一开始”等措辞把必学内容、非学习重点和人的责任写成可选项。
- 正文和表格必须分工。正文解释原因和变化，表格只做横向比较、选择或映射；表格只是把正文重写一遍时应删除。
- 学员正文只呈现知识、案例、操作和判断；演示准备、切屏动作、讲师提醒、提问方式和节奏安排另放讲师备课资料。
- 现场被讲师直接跳过的段落不是无关反馈，而是高价值证据。复盘时要判断它属于重复、书面化、无演示、顺序错误、专业细节过早还是只适合作为延伸阅读。
- 技术简化不能制造错误机制。类比和演示必须保留真实边界，例如图形界面操作不等于暗中执行 CLI 命令，上下文压缩也不等于窗口无限或模型能力按固定比例下降。

完整方法、案例和检查表见 [`demo-driven-course-design.md`](./demo-driven-course-design.md)。
