# 执行边界、分批协作与源码交接

> 来源：从原 [prompt-patterns.md](../prompt-patterns.md) 的实战模板按主题整理，原始版本由Git历史保留；2026-09-12仅拆分与明确适用边界，未重新实测秒哒产品能力。
> 模板中的页面名、接口、路径和配置是对应案例条件；执行前替换为当前项目已核验事实。查看模板不代表已授权收费、部署或外部发送。

## 核心结构（按这个顺序写）

```
1. @<技能名>（如果涉及技能调用，必须在最前面 @）
2. 一句话场景陈述 + 调动注意力的措辞
3. 红线段（禁止什么、不要动什么）—— 越靠前越好
4. 具体目标
5. 关键算法/函数的代码片段（不让 AI 自己写）
6. 必须使用的 URL / 文件 / 环境变量清单
7. 强制使用的参考实现（防止 AI 自己另写）
```

## 通用模板

```
@<技能名> 我现在需要 <做什么>，请打起十二分的精神专心进行修改和执行任务！！

<现状陈述：哪些已经稳定运行、本次任务的边界>，请保持不变，不要动 X 的任何代码、配置或环境变量。
本次只 <做什么的边界>。

整体目标：<一句话目标>。

<具体的实现指引，包含必要的代码片段>

<禁止清单>：
- ❌ 不要 ...
- ❌ 不要 ...
- ✅ 必须 ...

<URL / 文件 / 环境变量清单>
```

### 片段 0：Codex 先拆方案，再交给秒哒执行

**背景**：一次真实流程里，用户在秒哒云端项目开发中遇到问题，把问题交给 Codex；Codex 先分析网站和需求，结合本仓库的秒哒经验，产出分批、低风险、可直接粘贴到秒哒对话框的提示词；用户再逐批粘贴给秒哒执行。最终效果比直接让秒哒一次性理解大需求更稳定，出错率更低。

**适用场景**：用户无法直接让 Codex 修改秒哒云端项目，只能通过秒哒 AI 对话框执行修改；同时任务又需要拆解、保护已有功能、控制风险、分批验收。

**Codex 应该交付**：

- 执行顺序：先发哪一批、每批发完看什么。
- 分批提示词：每批一个代码块，可直接粘贴到秒哒。
- 禁改边界：数据库、接口、支付、订单、登录、购物车、退款等是否能动。
- 验收清单：用户在秒哒预览里逐项检查。
- 异常回传要求：失败时用户需要把秒哒摘要、报错、截图或页面现象发回来。

**核心提示词骨架**：

```text
请严格、严谨、认真、负责地完成本批任务。不要编造，不要夸大，不要自行扩展任务。

本批只修改：
<允许修改的范围>

严禁修改：
- <不能动的功能/数据/配置>

目标：
<本批完成后应该达到什么状态>

请按以下方式修改：
1. <具体动作>
2. <具体动作>
3. <具体动作>

完成后请只输出：
1. 修改了哪些文件、页面或配置。
2. 哪些风险点仍未处理。
3. 是否未修改严禁修改的范围。
4. 需要人工确认的事项。
完成后停止。
```

完整工作流见 [patterns/codex-assisted-workflow.md](../patterns/codex-assisted-workflow.md)。

### 片段 4：保护现有功能不被破坏

```
当前 PC 端用的是 X 接口，已经稳定运行，本次任务保持不变，
不要动 PC 端任何代码、配置或环境变量。
JSAPI 路径与 Native 路径必须能并存互不影响。
```

适用场景：新增功能但不能破坏旧功能。秒哒 AI 容易"顺手重构"。

## 不要做的事

- 用户已授权执行时直接写本批动作；当前只诊断或有未决关键事实时明确停止条件，不能把历史执行偏好当成平台必然行为。
- 每批提示词都写清本批基线、范围和验收，不依赖模型记住上一批；可以按项目需要分轮执行。
- ❌ 不要用"看情况"、"建议"、"考虑"等含糊措辞——它会自己发挥
- 已有验证实现时给出准确路径、固定版本和允许适配范围，防止遗漏关键约束。
- ❌ 不要把红线放在文末——它可能"边读边改"，红线放最前才有约束力

## 应该做的事

- ✅ 关键代码段直接贴出来让它原样使用
- ✅ 强约束（禁止 / 必须）写在提示词最前
- ✅ 用具体文件路径指向参考实现，而不是描述"实现一个 X"
- 在结尾给出可验证的成功、失败和回归场景；涉及真实付费的测试按当前授权与环境执行。

## 本地源码分包导入：校验完成后的最终执行句

**适用场景**：Codex 已在本地完成并验证源码，源码包、素材包、PRD 基线和 SHA-256 清单已经上传，秒哒也已把静态素材解压到云端对象存储。

完整的分包、对象存储、数据库、性能和部署流程见 [patterns/codex-source-package-deployment.md](../patterns/codex-source-package-deployment.md)。最终提示词不能只写“开始创建”，必须明确源码优先级和 PRD：

```text
请先确认全部编号压缩包、逐文件 SHA-256 和对象存储 URL 映射均已通过；如有缺失，停止并报告，不得用占位内容补齐。

本项目是 Web 应用，技术栈固定为 React + Vite。禁止 Next.js、SSR、Next API Routes、next 依赖和必须依赖常驻 Node 服务的方案。保留上传源码中的现有功能、交互、素材和测试，不要从零重写，不要替换素材，不要通过删功能或降质量解决性能问题。

生产环境必须通过统一资源解析器读取秒哒云端对象存储中的稳定 HTTPS URL；禁止 Base64 大资源、临时 Blob URL、本地绝对路径和浏览器缓存伪存储。业务数据需要跨设备保存时使用真实后端数据库，并回报表结构、权限和无痕窗口验收结果。

执行 npm install、自动测试和 npm run build；产物必须为 dist/。完成后回报 PRD 路径、修改文件、对象存储映射、数据库表、静态检查与构建结果、需要用户人工完成的桌面与移动端验收清单、剩余风险和人工确认项。不得把构建通过描述成真实设备已经验收通过。

严格依照上传的源码，然后给我生成网页应用，给我生成产品需求文档，并立即开始创作。
```

## 增量包交接

上述源码导入模板用于已收齐的完整源码包；增量包必须还原对应 `baseVersion` 全量树，再叠加增量，核对manifest/hash后安装、检查和构建，不能解压增量包就当完整工程。完整执行顺序见 [版本化增量闭环](../patterns/codex-miaoda-iterative-increment-workflow.md)。
