# 建委 AI 学习社群工作台 Skill

## 任务边界

当用户想把“某种身份/角色 + AI 学习或社群协作”变成一个工作台、产品方案、界面原型或可运行前端时使用。身份可以是学生、教师、管理者、创作者、销售、研究员、企业团队或用户自定义角色。

不要把工作台默认做成通用 CRM、课程商城或营销落地页；先从角色的高频任务、决策和协作关系建模。若用户只要求普通网页视觉稿、品牌宣传页或与学习社群无关的后台，使用更合适的技能。

## 核心目标

交付必须同时回答四件事：

1. 这个身份今天要完成什么，下一步是什么。
2. 学习内容如何进入、被处理、被实践、被反馈并沉淀为成果。
3. 社群成员、导师、AI 和管理者分别在何处协作，权限和隐私如何处理。
4. 同一套体验如何在桌面、平板、移动端和窄屏嵌入场景保持可用。

## 工作协议

### 1. 先读取上下文

- 这是通用 Skill，不绑定任何个人、公司、课程、社群品牌或既有产品事实。不得主动读取或套用建委个人上下文、建委自己的课程/付费社群 README，也不得把演示案例当成默认产品。
- 只有用户明确提供了某个项目仓库、设计系统、品牌资料或产品文档，且要求工作台与其一致时，才读取对应入口；当前对话明确内容优先。
- 需要界面实现时，先检查现有代码的技术栈、路由、设计 token、组件库和运行方式；保留已有系统，不无故换栈。
- 按需读取参考文件：身份不清时读 [role-adaptation.md](references/role-adaptation.md)；需要提问时读 [conversation-protocol.md](references/conversation-protocol.md)；要设计界面时读 [design-system.md](references/design-system.md)；交付前读 [quality-gate.md](references/quality-gate.md)。

### 2. 身份绑定与工作台建模

把用户输入解析为 `Role Profile`，至少包含：身份、场景、核心结果、熟练度、时间预算、协作对象、设备、约束、成功指标。身份含糊时，保留不确定性并用一个高信息量问题确认，不擅自假设。

随后输出 `Workbench Contract`：

- 主任务（一个）与次任务（不超过三个）
- 今日入口和下一步行动
- 学习循环：输入 → 理解 → 练习 → 交付 → 反馈 → 复盘
- 社群循环：提问 → 匹配 → 协作 → 分享 → 激励
- AI 边界：AI 能代办什么、必须让用户确认什么、哪些内容不可自动化
- 数据对象、状态、权限、空状态和失败恢复
- 桌面/平板/移动端的优先级与降级策略

### 3. 对话式生成

对话遵循“先给方向，再问选择”：首轮复述身份与建议的工作台骨架；最多提出 3 个可选择问题，优先询问会改变产品结构的变量（首要目标、使用频率/设备、协作方式）。允许用户直接说“按你的建议生成”，不能为了完整而连续盘问。

每次提问都给出 2–4 个互斥选项和一个“自定义”入口；记录已确认决策，后续不重复问。信息不足但风险低时采用显式默认值并标注“暂定”；涉及权限、隐私、付费、外部发送或不可逆数据操作时必须停下来确认。

### 4. 方案与实现输出

根据用户要的深度选择输出：

- 方向稿：角色判断、产品定位、核心场景、页面地图、关键流程。
- 设计稿：在方向稿之上增加信息架构、组件状态、视觉 token、响应式规则、可访问性与交互文案。
- 实现稿：在设计稿之上直接修改/创建代码，启动开发服务，按桌面和移动视口验证，并报告地址、测试与未覆盖风险。

页面默认采用“工作中枢”而非营销首页：今日行动、进度/成果、待处理反馈、社群入口、AI 助手和最近活动按角色权重排序。重复内容只保留一个权威入口。

### 5. 稳定性规则

- 先写数据模型和状态图，再写页面；避免只生成静态卡片拼贴。
- 所有主操作要有 loading、成功、失败、空状态和撤销/恢复路径。
- 不凭空编造平台 API、课程数据或成员信息；缺数据时使用明确的示例数据结构。
- 不把 API Key、Token、Cookie 或隐私信息写入代码、示例或提交。
- 设计完成后执行 [quality-gate.md](references/quality-gate.md) 的检查；发现违反项先修复再交付。

## 参考方法的吸收

本 Skill 借鉴了 Impeccable 的“先定义产品/设计上下文、区分产品界面与品牌界面、用反套路检查提升质量”，借鉴 UI Skills 的“按任务路由到具体设计能力”，以及 Creator Cockpit 的“本地优先、今日推进、内容管线、目标与复盘、数据备份”思路。仅吸收方法，不复制其代码、品牌或未经验证的产品事实。

## 交付格式

最终交付用短标题组织，并明确标注：`已确认`、`暂定`、`待确认`。至少包含角色画像、工作台结构、关键交互、跨端策略、视觉方向、风险/假设和下一步。若写了代码，附变更文件、运行命令、验证结果和已知缺口。
