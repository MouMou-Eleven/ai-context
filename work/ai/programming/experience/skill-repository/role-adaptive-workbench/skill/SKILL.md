# 身份适配工作台设计 Skill

## 适用范围

当用户想把任意身份、职业或工作场景变成一个可使用的 AI 工作台、产品方案、UI 原型或前端实现时使用。身份可以是设计师、教师、销售、研究员、创作者、学生、管理者、企业团队，也可以是用户临时自定义的任何角色。

这是通用身份适配 Skill，不绑定任何个人、公司、课程、品牌或固定案例。参考模板只用于启发推理，不是角色白名单；不得告诉用户“你的身份不在预设角色里”或“审美不属于参考模板”。

不要把工作台默认做成 CRM、课程产品或营销落地页。先从用户身份的真实任务、输入、决策、交付物和工作结果建模。只有用户明确提出多人协作时，才增加协作模块；不能默认询问无关的协作方式。

## 硬性工作流：两阶段状态机

### 阶段 A：身份澄清提问

触发后，首轮必须只做三件事：

1. 用一句话复述从用户输入中识别出的暂定身份和工作方向。
2. 提出 2–4 个围绕该身份真实工作的选择题。
3. 明确说明“请直接回复选项或补充一句，我收到后再生成工作台方案”。

首轮禁止：输出完整工作台方案、页面地图、模块清单、视觉稿、代码、实现计划或默认协作模块，或声称已经开始开发。提出问题后必须停下，等待用户下一条回答；不能在同一轮自行替用户回答。

问题必须围绕身份和工作结果生成，而不是从固定模板复制。例如：

- 设计师：设计类型/交付物、最耗时的环节、审阅协作、素材与版本管理。
- 教师：备课/授课/作业反馈、学生差异、教学资料沉淀、课堂节奏。
- 销售：线索来源、跟进节点、报价/方案、客户决策阻力。
- 研究员：资料采集、证据整理、分析流程、协作与引用。
- 创作者：选题、生产管线、发布、数据复盘和素材复用。

以上只是生成问题的示例，不得限制用户身份。问题要能改变后续产品结构；不要问与身份无关的颜色偏好、泛化审美或默认协作方式。

### 阶段 B：收到回答后设计与执行

只有收到用户对首轮问题的回答后，才能：

1. 合并原始输入和回答，确认 `Role Profile`，区分 `已确认`、`暂定`、`待确认`。
2. 以产品设计师视角构思完整使用场景、核心任务和业务闭环。
3. 以 UI 设计师视角设计信息架构、交互、组件状态、视觉方向和响应式规则。
4. 用户明确要求实现时，才检查现有代码并开始修改/创建代码、启动服务和验证。

如果仍缺少一个真正会改变产品结构的变量，最多追加 1 个身份相关问题；否则直接继续。不要在开发、设计或执行过程中反复盘问。

## 简短输入的处理

用户通常只会输入“我是设计师，想做一个工作台”这类短句。不要退回要求用户写完整 PRD；从身份推导合理场景，用首轮精准问题补齐关键变量。身份不清时保留不确定性，用问题确认，不自行把用户归类为某个预设角色。

## Role Profile

至少记录：身份、工作场景、核心工作结果、典型输入、关键决策、主要交付物、当前瓶颈、熟练度、时间预算、协作对象、设备、约束、成功指标。身份、设备和协作需求分别处理；协作问题只有在用户提及时才问。

## Workbench Contract

阶段 B 的方案必须覆盖：

- 一个主任务和不超过三个次任务，以及首屏的下一步行动。
- 工作循环：输入 → 分析/创作 → 审阅 → 交付 → 反馈 → 复盘。
- AI 边界：建议、用户确认、执行、结果追溯；哪些内容不可自动化。
- 数据对象、状态、权限、空状态、失败恢复、撤销和导出。
- 用户本人、协作者、客户、团队和 AI 的关系；仅在用户主动提及时增加多人协作循环。
- 桌面、平板、手机和窄屏嵌入场景的优先级与降级策略。

## 设计与实现原则

- 页面默认是工作中枢，不是营销 Hero 或卡片墙；今日行动、进度/成果、待处理反馈、AI 助手和最近活动按角色权重排序。
- 先写数据模型和状态图，再写页面，避免只生成静态卡片拼贴。
- 所有主操作覆盖加载、成功、失败、空状态、权限不足和恢复路径。
- 不凭空编造 API、数据、成员或平台功能；缺数据时使用明确的示例结构。
- 保留现有技术栈、设计 token 和组件库；用户未要求代码时只交付方案。

## 交付格式

阶段 A 只输出“暂定身份 + 身份相关问题 + 回复方式”。阶段 B 再输出“角色画像、产品场景、工作台结构、关键交互、视觉方向、跨端策略、风险假设和下一步”。若写代码，附变更文件、运行命令、验证结果和已知缺口。

## 方法参考边界

可借鉴成熟的设计上下文、任务路由、工作流、目标和复盘方法。方法只用于提高推理质量，不构成预设角色，也不绑定任何个人、组织或产品。
