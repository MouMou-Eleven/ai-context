# 渲染性能与交付流程契约

目标是让用户先用低成本看到完整动作，再决定是否支付全量渲染时间。预览与最终渲染使用同一个 Composition 和时间逻辑；只改变预览分辨率、编码质量和必要的并发设置。

## 1. 固定三段式状态

1. `plan-pending`：只输出制作规划确认单，不能创建工程或渲染。
2. `preview-pending-final-approval`：规划获批后实现并通过质量门槛，渲染覆盖完整时长的低分辨率 MP4，交给用户观看。
3. `final-approved`：用户明确确认当前预览后，才渲染最终规格。

用户修改动作、文案、素材或规格后回到 `plan-pending` 或 `preview-pending-final-approval`，取决于修改是否改变已批准的制作规划。低清预览的存在不等于最终渲染授权。

## 2. 默认预览规格

- 保持原 Composition 的长宽比、fps、音画时长和完整动作链。
- 默认缩放到原图或 Composition 的 50%，长边不超过 960 像素；不足以看清排版时提高到 75%，但先说明原因。
- 默认 H.264 MP4、CRF 28 左右或当前 Remotion CLI 的等价中等质量设置；预览重点是动作、节奏、镜头和最终帧，不是交付码率。
- 同时输出至少一张最终静帧 PNG，用于参考图对比；视频预览不能替代静帧验收。
- 记录实际分辨率、fps、时长、文件大小、编码参数、渲染器和耗时。

示例命令（按当前项目 CLI 帮助校正参数，不要盲目复制旧版本参数）：

```bash
npx remotion still <composition-id> preview/final-still.png --frame=<last-stable-frame>
npx remotion render <composition-id> preview/preview.mp4 --scale=0.5 --crf=28
```

## 3. 渲染路径选择

- 不要在项目配置中默认强制 `swangle` 或其他软件渲染器。先使用当前 Chromium 的正常硬件/默认路径，并对少量代表帧做可重复性检查。
- 只有出现可复现的 GPU 兼容性、崩溃、黑帧或结果不确定时，才回退到软件渲染；报告回退原因和预计速度影响。
- 并发先使用 Remotion 默认值或小样本测出的稳定值；不要为了追求数字盲目把并发拉满导致内存交换。
- 低清预览先完成后再考虑优化全量渲染。若 5 秒片段的低清预览已经异常缓慢，先检查滤镜、素材解码、渲染器和并发，不得直接开始九分钟级别的最终渲染。

## 4. 代码与效果预算

- 复杂但静态的背景、网格、装饰和参考图区域优先复用原素材或预栅格化；只把确实需要动作或编辑的元素做成动态层。
- 全画面动态 blur、重复高半径阴影、SVG `feGaussianBlur`、大型透明叠层和逐帧重解码是优先排查项；能缩小滤镜区域就不要覆盖整屏。
- 生产 Composition 不得叠放整张终帧参考图，也不得在最后稳定区注册终端参考层；这正是造成截图中重影、遮挡和最后一秒跳变的反模式。参考图只能在 `reference/` 或 `public/` 作为离线比较输入，生产源码需通过 `scripts/audit_reference_render_path.py`。
- 把渲染时间花在重复解码整图和大范围淡入也不会提高保真。先让同一套重建元素在目标边界框内连续收正，再用三帧连续性检查确认没有全画布替换。
- 背景基础层优先使用采样得到的纯色或少量渐变停靠点；不要用大范围高亮径向渐变、全屏 blur 或多层白色雾化替代参考图深色背景。局部事件光效用小范围层并在稳定区前归零，通常同时更快、更忠实。
- 在预览报告中区分“效果问题”和“性能问题”：不能为了快删掉用户批准的主动作，也不能为了丰富而增加无关效果。
- 低清预览的 `--scale` 只改变渲染分辨率，不得改变布局、字号、行高、蒙版框或响应式断点。若低清与全尺寸的内容边界不同，视为实现错误；不能把预览播放器缩放或白色页面留边误判为 Composition 裁切。

## 5. 第二确认门文案

低清预览交付后必须明确告知：

> 当前状态：低清预览待确认，尚未执行最终全量渲染。请先核对动作、节奏、镜头和最终帧；确认后我再输出最终全量渲染。

用户明确确认后，使用同一版本工程和 Props 渲染最终文件，并在实施报告中链接预览、最终文件、最终帧对比和真实耗时。没有明确确认时，只交付预览和可继续修改的工程。
