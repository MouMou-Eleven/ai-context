# Commercial - 商业化与对外交付

> 本目录保存跨设计、AI 和其他行业复用的内容经营、商业规范与正式交付经验。它既帮助内容连接真实需求和后续承接，也区分“给建委看的内部工作稿”和“可直接对外发送的成品”。

## 定位与边界

- 本目录是**跨设计、AI 和其他项目复用的商业方法与交付边界层**，可以与培训、视频、设计、出版等一个最具体的专业领域或项目组合使用。
- 本目录归入 `work/other/`，因为商业化不是 AI 或设计的下级门类；AI 项目和设计项目都可能调用这里的规则。
- 本目录不替代具体领域的专业规则，也不改变具体项目 README 中的事实口径。
- [`../../../brain/cognition/business-cognition.md`](../../../brain/cognition/business-cognition.md) 保存建委长期形成的商业判断与认知；只有用户明确要求结合建委的商业思考时才读取。本目录保存可以直接用于内容、方案、脚本、大纲和正式交付物的跨行业方法、规范与检查动作。
- 自媒体内容仍进入 [`../../ai/self-media/`](../../ai/self-media/README.md)，培训内容仍进入 [`../../ai/training/`](../../ai/training/README.md)。内容承担获客、产品价值解释、购买顾虑处理或商业承接时，读取本目录的内容经营方法；需要正式对外提交时，再读取对外交付规则。

## 严格触发规则

出现以下任一情况，必须读取本 README 和当前任务对应的经验文件：

1. 用户明确说“给客户看”“发给客户”“客户审阅”“对外发送”“正式交付”“交付版”“提案版”或同等含义。
2. 用户要求制作面向委托方、合作方、采购方、项目方或外部决策者的课程大纲、脚本、策划方案、项目方案、产品介绍、宣传片旁白、PPT 文案、合作方案等正式内容。
3. 即使提示词没有出现“客户”，但交付物显然会离开内部工作环境并直接代表建委或公司对外呈现，也默认启用对外交付规则。
4. 用户提到“内容即销售、内容获客、产品内容、买点、购买顾虑、精准客户、低播放高转化、干货与营销或内容承接”，读取内容需求与承接方法，再叠加一个最具体的行业或项目。
5. 用户要求商业计划书、项目申报、比赛材料、路演 PPT、融资材料，或内容将交给评委、投资人、孵化机构审阅时，必须读取赛事、路演与融资材料规则。
6. 用户提到案例演示、产品演示、案例答辩、直播案例、结果展示、未来图景、卖结果、课程或社群案例、产品价值演示时，必须读取案例结果叙事方法；再叠加一个最具体的产品、项目或领域规则。

以下情况不单独触发本目录：

- 只讨论某个专业领域的知识，不形成对外商业成品。
- 给建委看的分析、拆解、修改说明、风险提示和内部备忘。
- 单纯自媒体内容或培训内容，且没有对外项目交付语境。

## 组合方式

商业化与对外交付是跨行业商业层，不计作第二个专业领域。默认组合为：

```text
AI 表达基础层
  + 商业化与对外交付层
  + 一个最具体的专业领域或项目事实
```

例如：

- 对外培训大纲：AI 表达 + 商业化与对外交付 + AI 培训。
- 对外产品介绍片脚本：AI 表达 + 商业化与对外交付 + 视频或对应设计专项。
- 对外项目策划方案：AI 表达 + 商业化与对外交付 + 具体项目 README。
- PPT 内容获客：AI 表达 + 内容需求与承接方法 + PPT 设计或具体产品事实。
- AI 培训内容转化：AI 表达 + 内容需求与承接方法 + AI 培训或具体项目事实。

## 对外成品硬规则

1. **不暴露接收者身份。** 正文、标题、页眉、文件名和版本标签默认不出现“客户”“给客户看的”“客户版”“客户审阅版”等内部识别词，除非用户明确要求保留该主体。
2. **使用确定性表达。** 已确认的结构、时长、流程、画面、课程安排和执行方式直接写成确定陈述，不使用“建议采用”“建议突出”“可以考虑”等内部商议口吻。
3. **不混入内部工作话语。** “可再调整”“待客户确认”“供客户参考”“这里暂定”“后续可优化”等内容只留在给建委看的说明中，不进入对外成品。
4. **让业务对象充当主语。** 根据交付物使用“本项目”“本课程”“本片”“平台”“产品”“系统”“实施方案”等主体，不把“客户”作为默认主语。
5. **不伪造确定性。** 对尚未确认的事实，不得擅自补齐后写入对外稿；应先在内部说明中向建委列出待确认项，确认后再进入正式成品。
6. **内部说明与对外正文分开。** 如需同时交付两种内容，先给建委内部说明，再提供一份可直接复制、转发或导出的纯净正文，二者不得混排。
7. **例外必须由用户触发。** 只有用户明确要求“提供建议”“给出推荐意见”“保留客户称谓”“制作待确认清单”或交付物本身必须呈现合同主体时，才使用对应词语和角色。
8. **不暴露内部研发讨论。** 对外材料不主动呈现底层来源、二次开发、兼容分支、内部争议或“照搬、抄袭、不是抄袭”等负面联想词；技术尽调和合规审查按对方明确要求单独提供。
9. **不写无意义的自证式声明。** 不用“本计划书不编造”“本项目不是……”等句子证明可信度；直接给出已确认事实、责任人、验证结果和可核验边界。
10. **外部证据必须可访问。** 不在评委、投资人或合作方材料中放本地路径、`localhost`、私有仓库和内部测试目录；内部记录应转化为可嵌入的截图、数据、公开演示或正式附件。

## 写入规则

- 只有建委明确确认长期有效，或在多个内容经营与交付任务中重复验证的商业方法、规范、经验和注意事项，才写入本目录。
- 每条经验写清触发条件、适用任务、证据、边界、例外条件和交付前检查项。
- 具体项目事实留在项目目录；本目录只保留可跨项目复用的方法。
- 新经验文件必须更新最近一层 README 索引；旧规则被修正后只保留当前有效口径。
