# 思考与决策习惯

> 本文件只记录建委跨领域仍然稳定的思考习惯，不记录单个项目的临时决策。

## 当前稳定习惯

| 习惯 | 具体含义 | 输出要求 |
|---|---|---|
| 先看真实问题 | 不从概念和流行说法出发，先确认真正要解决什么 | 先写目标、现状和卡点 |
| 第一性原理 | 回到目标、限制、资源和可验证事实 | 区分事实、假设和待确认项 |
| 务实落地 | 理论必须能转成动作、结果或判断标准 | 给出执行步骤和验收条件 |
| 效率优先 | 重复且稳定的工作应考虑自动化 | 同时评估风险、成本和维护负担 |
| 迭代验证 | 先形成可验证版本，再根据真实反馈优化 | 不追求未经验证的一步到位 |
| 工具服务结果 | 工具是能力放大器，不是目标 | 说明工具改善了哪个环节 |
| 尊重边界 | 不知道就明确说不知道，不用完整感掩盖事实缺口 | 列出需要补查或确认的信息 |

## 分析问题时的默认顺序

1. 这次真正要得到什么结果。
2. 已确认事实是什么，哪些只是推测。
3. 当前最大的限制和风险是什么。
4. 哪个最小动作能验证方向。
5. 怎样判断结果是否达标。
6. 得到反馈后，下一轮应该保留、修改或停止什么。

## 框架化拆解

学习一个账号、方法、产品或行业案例时，不只观察销量、播放量、页面风格和几句显眼的话，而是拆解它怎样形成结果：

1. 先明确自己要解决的问题，避免为了研究而研究。
2. 同时观察多个案例，不能从一个成功对象直接推出普遍规律。
3. 拆出目标人群、任务场景、内容结构、产品、渠道、承接、交付和限制条件。
4. 区分表面做法与底层机制，判断哪些结果依赖对方特有的品牌、资源、时机和样本。
5. 把可迁移机制改写成适合自身条件的最小方案，不复制原文、视觉、口头禅和个人经历。
6. 每次只验证一个主要变量，用真实反馈决定保留、修正或放弃。

框架化拆解的目标不是把别人完整搬过来，而是把复杂对象看得更细、更小、更能验证。

## 微学习验证闭环

长期学习以能力增长为目标，不以看完多少页、听完多少课或连续打卡为目标。对于当前确实需要提升的一项能力，可以采用低压力的小循环：

```text
选择一个当前问题
→ 用 5～10 分钟获取一小段有效信息
→ 用自己的话复述一个结论
→ 当天找一个小场景应用
→ 记录结果或不明白的地方
→ 决定下一次继续、调整或停止
```

- `5～10 分钟`是降低启动阻力的参考起点，不是必须完成的形式指标。
- 不要求一天读几十页，也不因为某次没有形成结论就判定失败。
- 只输入、不复述、不应用的信息不能直接算作已经掌握的能力。
- 对当前关键能力要保持长期连续性；与当前目标无关的信息不需要无差别摄入。
- 真正进入长期认知的结论，必须经过自己的解释、实际使用或结果验证。

## 写入边界

- 单个项目决策进入项目 README 或项目历史。
- AI 培训、自媒体、视频、设计等领域方法进入对应 `work/` 目录。
- 外部观点只有经过建委确认并转化为长期判断后才能进入本文件。
- 未验证观点必须明确标记“待验证”，不能与稳定原则并列。
