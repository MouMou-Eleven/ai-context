# 第一部分：视频逐字稿（完整整理）

### 视频一：【Kimi K3 架构解密与实测】

**【引子：抛出焦点与核心问题】**
Kimi 最新的 K3 火了，用七个字总结就是：**又大又好还开源**。不过现在大模型是一个比一个大，今天它变大了，明天它又更大了，它们到底在比什么呢？其实呢主要就是三件事：
1. **参数量大**：也就是大模型的“大”字最直接的含义。现在的开源模型已经陆续上了 1T 参数量的排桌了，包括美团的 LongCat、DeepSeek、Kimi（2.5、2.6、2.7 和 K3 都是），之前这些只是闭源模型的专利。
2. **上下文长度**：之前经常用一次对话能不能读完整部《三体》来体现对长度的支持。前沿的大模型中，百万上下文长度也从原来的新噱头，快变成现在的标配了。因为即便是一个普通人，也能产生大量的 Agent 长任务，不只是简单地在网页上聊聊天了。
3. **模态支持**：是否支持更多的除了文字以外的模态，对使用体验还是挺有影响的。比如说我们总是呼吁 DeepSeek 什么时候能支持图片啊，其实就是对多模态的渴望；而 Gemini 当时爆火的一个原因，也是因为原生多模态这个特性的亮相，你看现在的 3.5 Flash 居然支持高达 5 种模态。

这次的 K3 把这三种“大”都集齐了：参数量 2.8T，是目前最大的开源模型；上下文长度也支持百万；而且还支持多模态。而且我比较好奇的是，它一个开源模型，居然在非常多关键的评测跑分中仅次于 GPT-5.6 和 Fable 5，甚至有些拿下了第一名。当然，这些“大”只是表面现象，真正起决定性作用的是背后来支撑这些“大”而用到的技术，今天就给你全讲明白。

**【硬核技术拆解 1：参数量大 $\rightarrow$ LatentMoE & Attention Residuals】**
我们先来看看参数量大会带来什么问题。这是大模型底层的根基 Transformer 架构，其中参数量占比最大的其实是这些 FFN 层（前馈神经网络），它就是个最简单的多层神经网络而已，只不过神经元的个数（也就是参数）特别多罢了。那解决办法也非常简单，就是把它拆成多个小的神经网络，然后每来一个新的 Token 时，通过一个训练好的路由层（Router），路由到其中一个小的神经网络（可以叫它一个专家）。这样呢，总的参数量并没有减少，但是每个 Token 计算时，实际用到的参数却可以变得很少。这就是经典的 MoE 混合专家架构。 DeepSeek 还魔改了一次，增加了共享专家，叫做 DeepSeekMoE。

而 Kimi 次使用的同样是 MoE 架构，共 896 个专家，每次只激活 16 个。而且更具体的，还使用了 LatentMoE 的方案，在专家路由层进一步通过降低维度，优化计算效率。反正你就记住：**什么东西前面加了一个 Latent，都是一个目的，就是通过先降维再升维，以便你在低维空间做计算，而提高效率。** MLA 里的 Latent 也是一样的。

好了，MoE 通过局部推理时减少参数量，缓解了计算压力。但是呢，总参数量还是这么多，训练的时候还是要把所有的参数都练到了。但是当模型大了之后呢，Transformer 的层数就会非常深，进而导致训练的过程容易变得不稳定。当然，一个经典的结构“残差连接”可以很好地解决这个问题，就是 include 在每层变换之外，额外再增加一个链路，无脑地把之前的一个值加过来就好了，非常简单。但是有个问题就是太死板了，比如说 A1 的信息传递到 A4 的时候，已经没剩多少了。所以说字节又提出了方案叫 HC，简单说就是把 A1 复制多份，然后同时往后传的也不是单纯地加过去，而是乘上一个可学习的矩阵。这样呢，传递的信息就有更多的机会被保留下来。但是很麻烦的就是，这个学习矩阵如果不加任何约束，那么连乘起来可能就又失控了。所以 DeepSeek 的 mHC 对这些学习矩阵加了流形约束，简单说就是让这些矩阵不论怎么乘，都在一个可控的范围内，是对 HC 的一种改良。

而 Kimi 呢选择了另外一条路。其实从更宏观的视角看，这几个方法不论怎么优化，都是把残差流从下到上，一层一层地加过去。而 Kimi 呢，直接在残差流中，通过**注意力机制**的方式，把之前的残差来一次加权求和，来保证每层的残差信息都有机会被注意到。这就是 Kimi 的 **Attention Residuals（注意力残差）**。当时还被很多大佬转发点赞，引起了一波社区讨论，我也出过视频。这次的 K3 模型，也是把当时的这篇经典论文中的技术用了起来，不错不错，又有一个新技术开源模型可以观察了。

**【硬核技术拆解 2：百万上下文 $\rightarrow$ Linear Attention / KDA】**
好了，参数量大产生的计算量和训练稳定性的问题，通过老生常谈的 MoE 以及刚刚 Kimi 自研的“注意力残差”解决了。那么，百万上下文所产生的计算量问题怎么办呢？

再回到这张 Transformer 架构图，其实百万上下文最大的问题，就是使得注意力层的计算量变大了。因为注意力层的每个 Token 都需要和其它的所有 Token 做注意力计算，得到一个系数。那怎么样减少这个计算量呢？很简单，一种方法就是把向量的长度减少，比如说 MQA、GQA、MLA 等。不过这些仍然属于稠密类型（Dense Attention），即计算的向量数量没有减少，只是减少了向量的长度。自然还有一类就是**减少计算的向量数量**，比如说固定一个计算窗口来选择 Token，或者呢通过某种办法筛选少量的 Token，而不是全部。经典的方法，比如说 DSA、SWA、CSA、HCA 等等，这些叫做稀疏注意力（Sparse Attention）。

那还有一类最狠的，就是直接把计算的复杂度从 $O(n^2)$ 降到 $O(n)$，这种方案叫做**线性注意力（Linear Attention）**。这里的 KDA 全称就是 **Kimi Delta Attention**，是 Kimi 自研的一种线性注意力方案，同样呢也是用在这次 K3 的模型中了。当然这种线性注意力某种程度上其实退化为了 RNN 的方式，所以通常来说是每隔几层使用一个线性注意力，和正常的注意力层混合着来，所以说整体也叫做混合注意力（Hybrid Attention）。

**【技术架构总结】**
总结一下，其实一个大模型最重要的就两块：**一个 FFN 层的参数量，一个是注意力层的计算量**。而这次的 K3 呢，就是使用 LatentMoE 的方案让 FFN 层的参数量变稀疏，同时在长度上再进行压缩；以及使用 KDA 线性注意力方案，让注意力层的计算量大大降低（也为业界经常讨论的混合注意力方案是否有效提供了一个很好的实践案例）；之后呢再用原创的 Attention Residual 保证了训练的稳定性。我估计后面很多开源工作会将这些技术广泛讨论并引入实践了。

**【Agent 实测与真实体验】**
我自己也亲自测了一下，用我之前做的这个模型测评工具来测，发现很多服务端的超时情况，可能是这次的 K3 实在太破圈了，给服务器挤爆了，也算是个有价值的发觉吧。那具体分数呢，等过几天服务器压力缓解下来，我们再测测看。

当然更重要的是 Agent 的能力。公开测评中 K3 的表现是相当亮眼的，那正好最近我也在整理 Agent 测评的自动化方法，那就试一试。我的方案其实非常简单，就是做这样一个目录，给每个目录分别放一个 `TASK.md`，写上它的任务要求，然后在最上层的根目录要求 Agent 依次完成所有目录中的任务。我的任务包括这些：
1. 阅读三个接口文档写调用页面
2. 后端项目改造为纯前端
3. 3D 模型格式转换
4. 超级屎山代码加功能

这就不但考察模型基本的 Agent 能力，同时呢还考察模型整体的规划能力，而且比较全面，测起来也很简单。而且这里的任务都是我个人平时遇到的真实的、而且当时的 Agent 解决起来很困难的问题。

首先值得肯定的是，K3 清清楚楚并行使用了 4 个独立的子 Agent 完成任务，而且输出的信息非常清晰明了。之前我的一些视频中就表扬过这个 Kimi Code 的易用性，确实看起来非常舒服。然后这里比较有意思的是，它刚好发生了一个意外，帮我测出了它的另一个能力：就是因为我是在酒店跑这个任务，我一会儿要参加 WAIC 大会，所以我提前离开了酒店，它的网就断了，断网之后它第 4 个任务就没有完成。我回到酒店之后把网续上了，所以整整好好测试了一下：如果 Agent 任务中间遇到网络断了的情况下，它能不能接上并很好地完成任务？当时我还觉得哎呀会不会白跑了，不过它非常给力，最终成功完成了所有的任务。

我们再来看看结果：
* 第一个是文生图/文生视频的工作流，接口调用全部正确，页面做得也很直观，而且视频这块之前用 Opus 4.8 轮询逻辑有问题，K3 做对了。
* 第二个是大模型评测项目，要求完全改造为前端，双击能打开，逻辑没问题，测评也能跑通，样式也没变。
* 第三个是 3D 文件格式转换，准确定位到我电脑里的 Blender，也知道命令行格式用法，拖到 PPT 里没有问题。
* 第四个是给屎山代码加功能。刚开始新增的文字添加功能点完完全全没有反应，我们再给它个机会改一下，最后这些问题都被轻松修复了。

结合我这几天的使用体感来看，K3 这次跑分还是很有含金量的。

**【结尾升华】**
最后再说点个人感悟。其实训练一个超级大的模型，有的时候不光是技术问题，更多的是成本和风险的问题。可能训练一次就需要成千上万张卡跑上好几个月，中途一旦训崩了，几乎就等于钱白花了。同时在大模型卷得这么厉害的环境下，也需要瞬间落后了，其实这是个风险很大的事。当然了，我们既要对过分夸大自己模型能力的话保持警惕，同时也要多一份耐心和包容心，明白像炼丹一样的训练大模型过程，其实背后有很多成本、风险以及非技术因素的考量。希望国产大模型能在这条路上走得更远吧，加油！

### 视频二：【上下文 1M 卷爆全场：GLM 5.2 深度解析】

**【引子：行业现状与疑惑】**
1M 上下文曾经是个很新鲜的东西，但是现在已经快成为标配了。国外的 Claude、OpenAI、Gemini，国内的 DeepSeek、MiniMax、MiMo 以及最新的 GLM，都标配支持了 1M 上下文。那为什么大家都开始陆续支持 1M 上下文呢？不同的模型的 1M 上下文效果是一样的吗？智谱最新发布的 GLM 5.2 有什么特殊的地方吗？那这期视频……哎算了，直接开始讲吧，废话真多！

**【底层痛点推导：1M 到底难在哪？】**
1M 上下文主语是某个具体的模型，指的就是支持你一次性喂给他 100 万个 Token。如果你一次性输入内容过长的话，就会提示长度达到上限。所以说上下文窗口小的模型，多轮对话后就不行了，要么清空，要么压缩，对信息都是有损的。如果我需要一轮对话就给到好多信息，那连压缩都没有办法实现，因为压缩本身也是占上下文窗口。

既然有这个痛点，那为什么不从一开始就支持 1M 上下文，而是磨磨唧唧一点一点往上涨呢？主要的难点在于大模型架构中**注意力层的计算量和 KV 缓存**。

简单点说，就是上下文中的每个 Token，都需要和之前的所有 Token 做一次计算，得到一个相关性的系数。如果上下文太多了，计算量就会非常大，每个词之间都需要算一遍，计算复杂度就是 $O(n^2)$ 的增长趋势。同时，每个词的 KV 向量都要以 Cache 的形式存储，占据着显存的空间。

占显存的问题，我们可以通过 MQA、GQA、MLA 等压缩手段得以缓解；而关于计算量的问题，之前有种方法叫 SWA 滑动窗口注意力，其实就是每次只计算一个固定窗口内的 Token，距离太远的就直接不管了。不过呢这样有点治标不治本，单纯用距离的远近来做取舍太粗暴了。所以有了更精细化的管理：**稀疏注意力（Sparse Attention）**，即从所有的 Token 中选取少量的 Token 进行注意力计算。至于具体怎么选，不同厂家有不同的方案：比如 DeepSeek 的方案叫 DSA，MiniMax 方案叫 MSA，智谱最新的模型 GLM 5.2 用的是一套组合的技术来解决这个问题。

**【评测逻辑：1M 上下文怎样才算“真有效”？】**
当然了，光解决这个计算量和存储空间（KV 缓存）的问题还不够，最关键的是**有没有效果**。别说放了一本《三体》进去，结果一问三不知，连叶文洁是谁都说不明白。

那怎么样测试有没有效呢？大概有这么几个方向：
1. **长文定位能力**：从茫茫的信息中找到一段具体的话。当然实际的测试要比这个更变态，比如说经典的 Benchmark MRCR，其中有一个题目就是这样的：整个上下文中包含了几千个小短文，分别是关于不同内容的，最后的题目是“找出第四篇关于鼻子的短文，并在前面加上这一个毫无意义的字符串”。这不但考察模型精准定位能力，还要求输出一字不差，而且还有毫无意义的随机字符串做干扰。直接把整个题目复制给 GLM 5.2 这个模型测试一下，很快模型就给出了答案。对比原文中的正确答案，发现一字不差，那这就说明模型通过了这个考验。
2. **长程任务能力（Long-Horizon Tasks）**：连续执行一个超长的任务，不会经常忘记前面的对话而导致任务越飘越远。比如说这个 FrontierSWE，长上下文能力只是基本要求，更考察 Agent 长时间运行的稳定性。比如有道题目要求对一个模型进行后训练，以解决这个青蛙棋盘问题，这个工程复杂度已经接近人类高级开发甚至是架构师的水平了。还有这种更夸张的 SWE 马拉松，每一个任务都几乎是一个工程团队几个月的工作量了（比如用 Rust 从零重写 C 语言编译器）。

**【GLM 5.2 的技术解法：IndexShare + LayerSplit + Slime】**
总的来说，支持 1M 上下文本身没什么厉害的，关键是要解决**计算量、显存占用、有效性**这三个问题，才能实现性价比高、工程能力优秀的长上下文效果。具体怎么解决呢？以这次新发布的 GLM 5.2 为例：
* **IndexShare（解决计算量）**：刚刚我们也说了，稀疏注意力（如 DSA）有一个 indexer 负责给每个历史 Token 打分，筛选出 Top-K。但是这个 indexer 仍然需要遍历全部 Token。当 Transformer 层数较多时，计算量仍然不可忽视。IndexShare 的做法，顾名思义就是让几个注意力层共用一个 indexer。最下面的一层算完了，其他三层就不用再计算一遍了，直接复用结果，把计算量又降低了一个层级。
* **LayerSplit（解决 KV 缓存占用）**：简单说就是给每张 GPU 不再存储全部层的 KV Cache，而是仅持有部分层的 KV Cache，从而降低单卡的显存占用。
* **Slime RL（提升训练效率）**：为了支持智能体强化学习后训练的复杂任务，智谱开发了一套 Agent 的后训练的基础设施框架 Slime，支持多种训练和任务组织，提升了长程任务的训练效果。

**【结尾总结与思考】**
1M 上下文从之前的有点噱头的宣传点，到现在几乎是各大模型厂的标配了。之前我们总是用一个模型能够塞下一整部《三体》来感受上下文的长度，但实际上我们也发现了，在 Agent 的时代，更重要的是对长程任务的支持。从这个角度上看，**有效的上下文并不只是让模型能够记住很久之前的内容，更重要的是能维持住长期的推理链条**，一直保持思路清晰，前后逻辑匹配，目标贯穿始终。

所以说仅仅支持 1M 上下文在现在已经不够了，谁能有效、高效利用 1M 上下文才是关键。未来上下文的长度一定也会越来越大，但我相信我们一定会找到其他更有效、更聪明的手段来解决这个问题。毕竟我们人脑连一串简单的电话号码都记不下来，但是仍足够聪明。加油吧，人类！

### 技巧解析 1：将高维数学/架构概念“降维直观化”

*   **用极简公式简化技术全貌**：
    *   *博主做法*：“其实一个大模型最重要的就两块：**一个 FFN 层的参数量，一个是注意力层的计算量**。”
    *   *效果*：瞬间将复杂的 Transformer 几十种模块收拢为两个主要矛盾，降低观众的大脑负载。
*   **给算法命名赋予“一句话记忆点”**：
    *   *解释 Latent（隐空间）*：“反正你就记住：**什么东西前面加了一个 Latent，都是一个目的，就是通过先降维再升维，以便你在低维空间做计算**。”
    *   *解释 IndexShare*：“顾名思义就是让几个注意力层共用一个 indexer，一层算完，其他三层复用。”
    *   *解释 Linear Attention*：“把计算复杂度直接从 $O(n^2)$ 降到 $O(n)$。”

### 技巧解析 2：“痛点-演进”对比链条（推导式叙事）

博主在讲任何新词（如 KDA, LayerSplit）之前，**绝不直接甩定义，而是讲历史演进**。

> **示例：讲解残差连接演进逻辑**
> 1. **传统残差**：无脑把之前的值加过来 $\rightarrow$ *缺点*：死板，A1 的信息传到 A4 剩不下多少。
> 2. **字节 HC**：把 A1 复制多份，乘上可学习矩阵 $\rightarrow$ *缺点*：连乘容易失控爆掉。
> 3. **DeepSeek mHC**：加“流形约束”，限定在可控范围内 $\rightarrow$ *缺点*：依然是一层层向上加。
> 4. **Kimi Attention Residuals（主角）**：用注意力机制把前面所有残差做**加权求和**。

*这种“提出问题 $\rightarrow$ 现有方案 $A \rightarrow$ $A$ 的缺陷 $\rightarrow$ 改进方案 $B \rightarrow$ 主角方案 $C$”的推演，会让观众产生“理所当然就应该这么做”的爽快感。*

### 技巧解析 4：结构性“升华”让视频脱离单纯的技术报幕

博主在视频结尾从不单纯停留在“谁赢了跑分”，而是上升到**行业理性与哲学思考**：
