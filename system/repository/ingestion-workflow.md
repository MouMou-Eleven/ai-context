# 往仓库里写东西的规范

适用于：新增、修改、移动、删除、复盘、沉淀经验、收录 Skill。无论哪个 AI 来写（GPT、Claude 或其他），都按本页执行。建委只需要说"沉淀到××"或"把这次经验记下来"，下面的判断和同步都由 AI 完成。

目标：写进去的东西以后能被找到、能被照着做、跟已有内容不打架。

## 第零步：确认在最新的仓库上写（红线）

写之前先 `git pull --ff-only`，确认本地 main 和 GitHub 一致。本机可能有多份仓库副本，旧副本里的规则和目录已经过时，照着旧规则写会把旧结构带回来。提交前检查会拦下落后于远端的提交；被拦时先拉取，再按最新规则重新判断放在哪。

## 建委实际会怎么说，AI 该怎么接

建委不会自己拆"这是事实、这是方法"。他通常只说一句话，拆分和归位全部由 AI 完成：

| 建委的说法 | AI 要做的 |
|---|---|
| "这些是培训的经验，沉淀到培训板块" | 把这轮对话的内容拆成事实、案例、方法三样（见第二步），分别写到 AI 培训项目的场次、培训方法文件、必要时的商业化方法；不要整段贴进一个文件 |
| "在微课与教育交互下面建一个精品课板块，把这个案例沉淀进去，我要能举一反三" | 建委已经点名了位置和名字，**直接建，不再问 A/B**。建出来的板块必须有一个方法文件（下次同类任务怎么做），案例作为证据放在方法旁边；只放案例不写方法不算完成 |
| "记一下""这个要记住" | 按第一步判断属于哪类，写进对应位置 |
| 什么都没说，但对话里纠正了 AI、表达了观点或偏好 | 见下面"建委大脑自动提炼" |

写完后用几句话告诉建委：**这次拆成了几样，每样放到了哪个文件的哪一节，哪些没写以及为什么。**例如："事实写进了 `ai-training/jinan-cadre-ai/README.md` 的讲后反馈；'先演示再讲原理'这条做法改进了 `training/experience/demo-driven-course-design.md` 第三节；学员名单只跟这一场有关，没写。"

### 建委大脑自动提炼

建委很少主动说"存进大脑"。所以任何对话里，只要建委**自己说出了**观点、判断标准、偏好或做事原则，AI 都要顺手判断一次要不要存进 [brain/](../../brain/README.md)：

1. **只取建委自己说的。** 他的原话或明确认可的判断才算；AI 自己总结出来、建委没确认的不算，外部文章的观点也不算。
2. **要抽象，不要项目细节。** "选客户先看适配度，不看单价"可以存；"某客户报价 3 万"不存（那是项目事实）。
3. **先查重。** 在 brain/ 里搜同一个意思。已经有了就不写，最多补一句来源；有相近的就改进那一条，不新增。
4. **有冲突时不擅自覆盖。** 新说法和已有条目矛盾，先问建委"以前记的是 A，这次你说 B，以后按 B 吗？"，确认后替换旧条目。
5. **放进最贴近的主题文件**（商业判断、做事与表达偏好、思考与决策），没有合适主题时按下面"新建目录"的规则问建委。
6. **在本次回复末尾告诉建委存了什么**，一句话即可，方便他纠正。

判断不准是不是建委的稳定观点（比如只是随口一说、带情绪的吐槽），就不存。

## 第一步：判断这次值不值得写

值得写：

- 建委明确说"记下来""沉淀"
- 建委纠正了 AI 的做法，并且以后还会遇到同样的情况
- 一次真实任务里验证有效的做法，下次能直接复用
- 事实变了：价格、进度、平台功能、个人荣誉

不写：

- 只跟这一次对话有关、以后用不上的细节
- AI 自己推测、没被建委确认或实际验证的"经验"
- 已经写过、这次只是又说了一遍的内容（最多补一个来源）

拿不准时问建委一句："这条要不要记进仓库？打算放在 ××。"

## 第二步：分清是什么，放到哪

| 是什么 | 放哪 | 例子 |
|---|---|---|
| 建委本人的事实 | `personal/` 对应文件 | 新荣誉、新聘任、新数字 |
| 建委的原则、偏好、判断方式（抽象的，不针对具体项目） | `brain/` | "选客户看适配度" |
| 能用到别处的做法 | `work/domains/` 对应领域 | 课件怎么写、秒哒怎么打包 |
| 某个项目的事实 | `work/projects/` 对应项目 | 社群价格、言剪进度 |
| 一场培训（企业、机关、图书馆、夜校） | `work/projects/ai-training/<场次>/` | 某单位培训的受众、方案、讲后反馈 |
| 建委认可的口语原文 | `system/expression/voice-samples.md` | 建委给的满意稿子 |
| 通用中文表达问题 | `system/expression/corrections.md` | 跨场景反复出现的病句 |
| 电脑、网络、本机工具 | `system/environment/` | 代理端口、软件路径 |

一件事常常两样都有。比如一次培训复盘，场次事实写进 `work/projects/ai-training/<场次>/`，能复用的做法写进 `training/experience/`，两边互相链接，不要复制正文。

### 先按业务确定归属（默认）

用“这是什么业务、什么交付物”决定主目录，再按受众去引用通用标准。是否收费、是否对外、客户有没有预算、AI 参与了多少，都不改变归属。

- 培训接洽、选题、给主办方写大纲、备课、授课复盘 → 培训。
- 精品课拆页、页面合并、模板设计、客户确认页数 → 设计。
- 跨领域都用得上的报价口径、合同和正式文书、商业计划、路演答辩材料、对外表达标准 → 商业化。

例：精品课客户嫌页数多要求合并，合并怎么做仍写在精品课方法里；只有“合并后怎么重新计价”引用报价方法。

### 一条规则只有一个家（红线）

同一条规则写在好几个地方，改了一处、漏了另一处，几个月后就会互相矛盾，下一个 AI 不知道听哪个。所以每类规则只在一个位置写正文，其他地方只写一句话加链接：

| 规则类型 | 正文只写在 | 其他地方怎么写 |
|---|---|---|
| 什么任务读什么文件 | `AGENTS.md` 任务表（每格只放链接和一句限定） | 领域 README 只列本领域文件 |
| 写入、沉淀、归属、目录、规则怎么写 | 本页 | `AGENTS.md` 第二部分只留摘要和链接 |
| 提交与发布 | `AGENTS.md` 第三部分 | 只链接 |
| 中文表达 | `system/expression/` | 领域方法写“表达按[表达标准]” |
| 某个领域的做法 | 该领域的方法文件 | 其他领域只链接，不抄 |
| 价格 | 报价表 `quotations/price-baselines.md`；计价口径在 `quotations/method.md` | 领域方法只写“报价见……” |
| 建委的原则和偏好 | `brain/`，一两句抽象原则 | 执行细节写在对应领域或本页，大脑里只链接过去 |
| 项目和一单的事实 | 项目 README 或案例 | 方法里写“例：见[某案例]” |

写之前先搜这条规则有没有正文。有，就改那一处；本处最多补一句链接。收到建委纠正时，改规则的家，不要为了保险在入口、README、大脑各补一遍。提交前检查会拦下跨文件高度相似的段落。

### 新的工作怎么沉淀

不管是新项目、新设计单、新视频、新开发还是新一场培训，都按同一个办法拆成三样，分开放：

1. **事实**（这次的客户、要求、价格、进度、结果）→ 长期项目写进项目 README；一次性的事写成案例。
2. **案例**（这次怎么做的、出了什么问题、怎么改的）→ 按[案例模板](./templates/case.md)，文件名 `case-*.md`，放在它证明的方法所在目录。
3. **方法**（下次同类任务还能用的做法）→ 改对应领域里已有的方法文件；没有才按[方法模板](./templates/method.md)新建一个。

案例里要链接到方法，方法里写"来源：某案例"。**方法是给下次用的，最重要；案例是证据；事实只写一处。**

| 这次做的是 | 事实写哪 | 案例放哪 | 方法改哪 |
|---|---|---|---|
| 平面设计单（PPT、海报、折页、书） | 案例里 | `design/graphic/<门类>/` | 同目录的方法；多个门类都成立的放 `design/common/` |
| 视频单（宣传片、微课、故事片、漫剧） | 案例里 | `design/video/<片型>/` | 片型方法；提示词经验改 `design/video/common/seedance/` |
| 用秒哒开发 | 长期的建项目；一次性的写进案例 | 项目目录，或 `development/tools/miaoda/topics/` | 秒哒特有的改 `tools/miaoda/`；所有 AI 编程都成立的改 `development/experience/` |
| 用其他工具开发 | 同上 | 项目目录 | `development/experience/`，工具特有的改 `tools/<工具>/`（新工具要先问建委） |
| 一场培训 | `projects/ai-training/<场次>/README.md`，并在 [sessions-index.md](../../work/projects/ai-training/sessions-index.md) 登记 | 同一个 README 里写讲后反馈 | 接洽、方案、大纲、课件与授课SOP均改 `training/experience/`；跨领域文书、报价、表达标准引用 `other/commercial/`；新课题补 `training/topics.md` |
| 一篇文章、一条宣传 | 不单独记，除非建委要求 | 不建 | 写法改 `self-media/` 对应类别；建委认可的口语原文补 `voice-samples.md` |
| 一份商业方案、比赛申报 | 案例里 | `other/commercial/` 下对应方法旁边 | `other/commercial/experience/` |
| 长期项目的一次推进 | 项目 README 的"当前事实" | 不建案例 | 能用到别处的做法照上面各行写进领域 |

**不值得写的**：这次一切顺利、没有新做法；只是重复了已有方法；只跟这一次有关、下次不会再遇到的细节。

### 放哪里拿不准，或者想新建目录时

**先找已有位置。** 能放进已有文件就放进已有文件，能放进已有目录就放进已有目录。AI 找得越少，越容易找对。

**不要建"汇总型"文件夹。** 比如"新项目合集""其他经验""杂项"，这种目录换个模型就不知道该往哪放，最后又乱成一堆。

**建委已经点名了位置和名字的，直接建。** 其余情况，**真觉得需要新建文件夹或新分类，必须先问建委**，并同时给出两个方案：

> 这条经验我建议放在：
> A. 已有位置 `work/domains/xxx/yyy.md` 的"某某"小节。理由：……
> B. 新建 `work/domains/xxx/zzz/`。理由：……（为什么现有位置放不下）
> 我倾向于 A/B，你看呢？

建委同意后再建。新建单个文件（放在已有目录里）不用问，但要先确认没有已有文件讲同一件事。

## 第三步：改原文，不要追加

1. **先搜索。** 用关键词和同义词搜整个仓库，找到讲同一件事的地方。
2. **找到了就改那一处。** 补充、修正或替换。旧说法错了就直接改掉，不要保留"旧口径""新口径"两段并列，Git 历史能找回旧版本。
3. **没找到才新增**，放在最相关的文件里、最相关的小节下。
4. **不要在文件末尾追加"补充说明""最新经验（日期）"** 这种段落。
5. **同一个错误又犯了**，说明规则没被读到，或者写得不够具体。去改规则的写法和检查动作，不要再加一条"必须……"。

## 第四步：写清楚

每条经验写出这几样：

- **什么场景**：什么任务、给谁、什么条件下用。不适用的场景也写一句。
- **怎么做**：具体动作，能照着做。
- **一个例子**：最好是正例、反例各一个；有建委原话就用原话。
- **为什么**：一句话讲原因，AI 遇到没写到的情况才能自己判断。
- **级别**：`红线`（不能违反）、`默认`（没有理由就照做）、`可灵活`（按场景判断）。不标就算默认。

**不要压缩成口号。** "注意口语化""保持专业"这种话 AI 没法执行。要写"像这样说……，不要像那样说……"。宁可多写两句具体的，也不要写一句抽象的。

**会过时的事实**（平台功能、价格、限额、界面位置）写上核验日期，并且只写在一处。别的文件需要时链接过去，不要各抄一份。

### 方法正文只写做法，来源和状态放在末尾（默认）

方法文件是给下一次照着做的。正文只写场景、做法、例子、原因；“这条还没在别的项目验证过”“截图不代表客户验收”这类证据说明，集中写在文件末尾的“来源与状态”一节，几行就够，不要在正文里逐句加“不代表、不冒充、不能证明”。

为什么：AI 用方法做成品时会照着正文写。免责句一旦被带进教程、方案、宣传稿，读者只会觉得心虚、混乱。反例：一篇公开教程的图注写“这是原始反馈标注，不是后来伪造的验收记录”，读者根本不需要知道这个。

项目里的具体数字、本机路径、版本号、客户名写在案例或项目里，方法里写“例：见[某案例]”。提交前检查会拦下领域方法文件里的本机路径。

### 大脑和入口要短（默认）

- `brain/` 每条一两句原则，加“执行见[链接]”。超过两三句，说明混进了操作细节，把细节挪到对应领域或项目。
- `AGENTS.md` 任务表每格只放链接和一句限定，细则放到链接指向的入口里。

提交前检查会拦下过长的大脑条目和任务表单元格。

## 第五步：同步

- 新增、删除、移动文件后，更新最近一层 README 的目录。
- 移动文件：先 `git mv`，再运行 `python system/repository/maintenance/relink.py 旧路径=新路径`，自动修正所有链接。
- 新文件在 `system/repository/maintenance/structure-descriptions.json` 的 `descriptions` 里加一行中文用途说明（桌面结构页要显示）。
- 新增一类常见任务：在根目录 `AGENTS.md` 的任务表里加一行。
- 新增或移动项目：更新 `system/repository/navigation/projects.json`。
- 个人事实变了：更新 `personal/` 对应文件。能力有新证据时，按[能力证据规则](./capability-evidence.md)判断要不要更新个人概要。
- 收录 Skill：按 [Skill 库](../../work/domains/other/skills/README.md)的规则登记来源、许可和版本。

## 第六步：校验和发布

```text
python -B system/repository/maintenance/sync-navigation.py
python -B system/repository/maintenance/sync-structure.py
python -B system/repository/maintenance/validate-context.py
```

没有错误再提交。只提交这次改动的文件，不夹带无关文件。按 `AGENTS.md` 的发布规则直接推送 main，推送后确认远端已包含本次提交，并把链接发给建委。

## 修订记录

普通改动不写修订记录文件，Git 提交信息就是记录，提交信息要写清改了什么、为什么改。只有整个仓库结构或规则发生重大变化时，才在 `system/repository/revisions/` 写一份说明。
