# 仓库怎么越用越好用

适用于：用仓库做完一件实际的活之后、建委纠正或认可成品时、仓库该升级时。任何 AI 都按本页执行，不用等建委开口。

目标：让仓库像模型训练一样，从每一次真实使用里拿到“这样做对、那样做不对”的信号，好的强化，差的改正。仓库不是备忘录，规则写得再多，下一次没做好就等于没写；要的是下一次真的做得更好。

## 先分清错在哪：三类失败

返工时先判断属于哪一类，再决定改什么。不同的失败，治法完全不同：

| 类型 | 怎么认 | 改什么 |
|---|---|---|
| **A 没读到** | 仓库里有这条经验，这次没读那个文件 | 改 [AGENTS](../../AGENTS.md) 任务表、领域 README 的入口或路由，让同类任务一定读到 |
| **B 读了没做到** | 读过了，交出来还是违反 | 不再补一句“必须”；把这条变成交付前要做的检查动作（检查单里要填实测值的一行、脚本、独立审查的必查项） |
| **C 照做了仍不好** | 写下来的规则都满足了，建委还是说不好看、不对 | 规则没写到的判断。补一对真实的正反例，找出差在哪，见[建委的审美标尺](../../work/domains/design/common/design-principles/taste-benchmarks.md) |
| **仓库里本来没有** | 搜不到相关经验 | 先记观察（第二节），出现第二次再提成规则 |

为什么要分：以前几轮整改主要治的是 A；B 和 C 也用“再加一条规则”去治，结果规则越来越多、互相稀释，长任务里读过的规则照样被忘。B 要靠检查动作管住，C 要靠例子补足，都不是靠多写一句话。

## 一、每次用完记一行使用日志（默认）

**什么时候记**：用仓库经验做了实际成品并交给建委，或者建委纠正了用仓库经验做出来的东西。只查事实、只回答问题的不记。

**一单一行**：同一单返修时不另起一行，改原来那一行的结果（返工 N 轮）、失败类型、涉及规则和说明；几轮里违反了不同的规则，都写进“涉及规则”。

**记在哪、记什么**：在[使用日志](./usage-log.md)的表里加一行：

| 列 | 写什么 |
|---|---|
| 日期 | 交付当天 |
| 任务 | 一句话：做了什么、给谁 |
| 读了 | 实际读过正文的文件，写文件名即可 |
| 结果 | 一次过 / 返工 N 轮 / 没完成 / 待反馈 |
| 失败类型 | A、B、C，可以多选；没问题写“无”；建委还没看写“待反馈” |
| 涉及规则 | 被违反或缺失的那条规则，链接到具体小节（带 `#` 锚点，同一条规则每次用同一个链接）；没有写“—” |
| 说明 | 建委原话或一句话原因 |

- 格式示意（不是真实记录）：`| 2026-12-01 | 某创赛片第 3 幕返修 | ae-template-layout、ai-code-ae-pipeline | 返工 2 轮 | B | [画面里不能有任何闪](../../work/domains/design/video/promo/competition/ae-template-layout.md#改模板时的设计判断默认) | 建委：“这里还在闪” |`。判断 B 的前提是：交付时仓库里已经有这条规则，而且这次读过那个文件；规则是这次反馈之后才补的，算“仓库里本来没有”。
- 失败类型按建委的反馈判断，不按自评。交付时建委还没看，先写“待反馈”；之后哪次对话收到了反馈，就改这一行。
- 用不了仓库写入（工具不支持、没有权限）时，在交付说明里写出这一行，下次能写时补上。

为什么：日志是以后升级仓库的依据。哪条规则总被违反、哪类任务总读不到经验、哪里返工最多，看日志就知道往哪改，不靠印象。

## 二、建委纠正或认可时：先记观察，不当场写成通用规则（默认）

**这一单照改。** 建委说的，这一单马上按他说的改。这里管的只是“要不要把它写成以后都适用的规则”。

**先记观察。** 在[观察记录](./observations.md)加一行：日期、项目、类别（一两个词，用来把同一类判断归到一起，例如“画面饱满”“字的取舍”）、好还是不好、建委原话、对应的成品（文件名、版本、第几页或第几秒）、改了什么以及改后建委怎么说、状态（先写“待定”）。**认可也记**：建委说“这版好”“这个对了”，和否定一样有用。

**为什么不当场写成规则**：单次反馈里常混着只对这一单成立的东西。反例：“图要等大”被当场写成“同一排一样大”，同一单的下一轮就被建委纠正：“是以美观好看为判定的标准，而不是同一排一样大”；字幕区写成“最低内容 y 880—950”，几天里改了两次。一条错的通用规则，会把以后每一单都带偏。

**可以直接写进方法的情况**：

- 建委明确说“记住这条”“以后都这样”“沉淀到××”：照[写入规范](./ingestion-workflow.md)写进方法，同时在观察里记一行、状态写“已按建委要求写入 → 链接”，以后被推翻时好查。
- 事实变了：平台功能、价格、路径、版本。按写入规范直接改事实所在的文件。
- 只属于这个比赛、这个项目的规定：直接写进比赛文件夹（像天津 AI 教育大赛这样一个比赛一个文件夹的）或项目记录。创赛片这类片型方法是多个项目共用的，按通用方法走第三节的晋升。

## 三、什么时候把观察升成通用规则（AI 自己判断，默认）

不用等建委提。每次记观察时、每次升级仓库时，AI 都按下面五条核对一遍，**全部满足才提**：

1. **出现过两次。** 两个独立的项目里都出现了同一类判断（同一单的几轮返修算一次，独立的意思见[能力证据 · 哪些不能重复计数](./capability-evidence.md#哪些不能重复计数)）；或者建委自己把它说成了一条普遍原则。
2. **换个项目还成立。** 去掉项目名、版本号、像素值、颜色以后，这句话仍然对（换位测试见[写入规范 · 从一个项目里提炼](./ingestion-workflow.md#从一个项目里提炼写给下一个不同的项目默认)）。
3. **不和已有规则打架。** 有相近的规则就改那一条，让它覆盖新情况；新旧说法矛盾时，以建委更近的说法为准，改掉旧的，不并列。
4. **拿来源检验一遍。** 用这条规则去看那两次的成品：能说清被否的那版为什么不好，也不会把建委认可的那版判成不好。会误伤正例的，说明写宽了，收窄再提。
5. **级别只能是默认或可灵活。** 红线只有建委能定。

**怎么写**：写进这条规则的家（各类规则写在哪见[写入规范 · 一条规则只有一个家](./ingestion-workflow.md#一条规则只有一个家默认)），配一个正例、一个反例，来源写在文件末尾；能在成品上核对的，同时在那个领域的检查表里加一行检查动作。观察表里对应的几行，状态改成“已晋升 → 链接”。

**告诉建委**：在本次交付说明里加一句：“把‘××’升成了通用规则，写在××，因为在甲、乙两个项目都出现过。”建委不同意，就撤回，并在观察里记下他的原话。

## 四、规则什么时候改写、降级或撤掉（默认）

- **读了仍被违反两次**（日志里有两条 B 指向它）：写法管不住，不再加“必须”。改成检查动作：在检查单里写成要填实测值的一行；能用脚本判断的进 [check-deliverable.py](./maintenance/check-deliverable.py) 并配测试；放进独立审查的必查项（见[成品自查](./execution-checks.md#正式交付前请一个全新的审查者默认)）。
- **被建委推翻**：直接改掉或删掉，把推翻它的那次写成正确规则旁边的反例；观察里记一行。
- **长期没人用**：升级时看日志，连续三个月没被任何一次任务引用、也不在必读入口里的规则，考虑并进相近的规则或移到来源说明。**经验原文不因为没被用到就删**，只合并；合并后逐条核对旧内容都还在。
- **合并、缩写时不丢细节**：把几段合成一段时，原来的场景、例子、数值、原因都要留下，用改前的清单逐条对。为了简短把经验压成口号，比不改更糟。

## 五、样例：少而典型的正反例对（默认）

仓库里的“题”不是单独攒一个题库，而是建委真实评价过的成品对照：同一单前后两版，一版被否、一版被认可，加上他的原话。它们写在各方法的例子里，设计类集中在[建委的审美标尺](../../work/domains/design/common/design-principles/taste-benchmarks.md)。

**怎么用**：

- 制作的人开工前，挑和这次成品相关的两三对看，写进设计简报：这次要达到的是哪一边、要避开的是哪一边。
- 独立审查时交给审查者，让他判断新成品更像哪一边。
- 晋升规则时拿来检验（第三节第 4 条）。

**怎么维护**：每类判断留一两对最典型的就够；来了更典型的，替换旧的，不往上堆数量。被建委推翻的样例撤掉或改成反例。样例学的是判断，不是外观，下一单的配色、版式仍按内容重定。

## 六、仓库什么时候该升级（看内容量，不看日期）

满足任意一条就该升级，阈值是起步值，升级时按日志的实际情况调整：

1. 同一条规则在日志里被记了两次 B（一单一行，所以是两单）。
2. 观察里同一类别出现在两个不同的项目，状态还是“待定”。
3. 日志里累计有两次 A（该读的没读到）。
4. 上次升级当天及以后记的日志满 20 条。

第 1—3 条数的是日志、观察表里还留着的所有行：升级时处理完的行会删掉，没处理完的留着，下次继续计数。第 4 条只数上次升级以来新记的行。项目名用项目 README 里的名字、类别用观察表里已有的词，写法不一致会让脚本数不到一起。

**谁来看**：运行 `python -B system/repository/maintenance/evolution-status.py`，它按上面四条读日志和观察，给出“该升级”和原因。Claude Code 在本机每次开新对话时自动运行（会话开始钩子，见[本机环境](../environment/computers/desktop-1/README.md#仓库升级提醒)）；其他工具开工读完 AGENTS 后自己运行一次，不能运行脚本就按上面四条自己数。

**怎么提醒**：状态是“该升级”时，每次回复末尾加一句：“仓库该升级了：（原因）。说一句‘升级仓库’我就开始。”一直提醒到升级完成为止。第三节的单条晋升不用等升级，满足条件随时做。

## 七、升级怎么做

1. **拉最新，留基线。** `git pull --ff-only`；导出改前的文件清单、每个文件的字数、红线清单，放在仓库外的临时目录。
2. **读日志和观察，先归因。** 每条返工按三类失败归到具体文件、具体小节，列出这次要改的规则。
3. **逐条处理。** 晋升按第三节，改写降级按第四节，入口按 A 类的治法改 AGENTS 或 README。
4. **长文件只在日志显示需要时才拆。** 一个文件反复出 B 类、而规则埋在长段落里时，按使用时刻拆：开工前要读的判断、交付时用的验收表、判断不清时才翻的事故经过。内容一字不删，用基线逐项对比。
5. **校验和测试。** 跑写入规范第六步的三个脚本和全部测试。
6. **收尾。** 把[使用日志](./usage-log.md)顶部的 `last-upgrade` 日期改成今天，在“历次升级”表里记一行；已经处理过的日志行和观察行删掉（Git 历史能找回），没处理完的留着，它们下次仍按第六节第 1—3 条计数。
7. **告诉建委**：这次根据哪几条日志改了哪些规则，哪些没改、为什么；新增或降级的红线单独列出来请他确认。

## 来源与状态

- 建委 2026-11-12 至 11-13 的整改对话：三类失败的判断，写入分两步（先记原始反馈，提炼由 AI 按准则自动做），样例和规则都不能是死的、不追求数量，按日志内容量提醒升级，审美是重点。
- 借鉴的做法（都是不改模型参数、只靠上下文让 AI 越用越好的研究）：
  - [ACE](https://arxiv.org/abs/2510.04618)：把上下文当成不断演化的工作手册，用小步增量更新，避免为求简短丢掉领域细节、反复重写把细节磨掉。对应第四节“合并不丢细节”和第七节第 4 步。
  - [ExpeL](https://arxiv.org/abs/2308.10144)：从成功和失败的经验里用自然语言提炼洞见，用时再召回。对应“先记观察、再晋升”。
  - [Dynamic Cheatsheet](https://arxiv.org/abs/2504.07952)：只留简洁、能迁移的片段，不存完整记录。对应观察处理完就清掉、方法里只留能迁移的判断。
  - [GEPA](https://arxiv.org/abs/2507.19457)：对执行过程做自然语言反思来诊断问题，再测试改法。对应日志归因和第三节第 4 条的检验。
  - [Anthropic：Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)：上下文要少而有用；与其列一堆边界规则，不如给少量多样、典型的例子；子代理用干净的上下文做专门的事。对应第五节和独立审查。
- 2026-11-13 建立。阈值、日志列和观察列是起步设计，按真实使用调整；没有做过对照实验，效果靠日志检验。
