# 用仓库经验做成品时怎么自查

适用于：用仓库里的经验做出实际成品（课件、方案、文章、视频、应用），交付之前。只查事实或位置时不用。

读到规则不等于做到了。常见情况是 AI 明明读了"课件不写讲师安排"，交出来的稿子里还是有"本节讲 20 分钟"。所以交付前要拿成品逐条对照。

## 动手前（在心里或草稿里过一遍，不写进成品）

1. 这次交付什么、给谁看？给学员的课件、给主办方的方案、给讲师的备课稿，是三种东西。
2. 读了哪几个文件？里面有哪几条红线？
3. 这次有没有建委的特别要求，会不会跟默认规则冲突？冲突时按 [AGENTS](../../AGENTS.md) 第 3 步的优先顺序取舍。
4. **把这次要守的规则抄成本单检查单。** 从读过的文件里只挑和这一单有关的几条（红线全抄，默认挑相关的），每条写成能在成品上核对的样子：看哪一页、哪一帧、量什么、多少算过。设计类再从[建委的审美标尺](../../work/domains/design/common/design-principles/taste-benchmarks.md)挑两三对相关的正反例放进去。长任务每交一版之前，回到这张单子逐条过一遍。

   **观察表里的待定行一条不落地抄进来。** [观察记录](./observations.md)里同一个项目、同一类成品状态为“待定”的行，每一行都写成检查单上的一项（看哪里、怎么算做到），不只是“读过”。**换方案、换架构、换一版重做时，把旧检查单整张带过来逐条过**，新路线最容易把旧教训丢掉。反例：图片入表工具 11-19 已记“只比写入列”，换成逐格识别的新架构时没带过来，又把截图上所有数字都识别了一遍，被建委和客户指出；城建课件开工时，社群第 10 课的两条待定（“没有对话截图看不出过程”“每个点都有但摸不清头脑”）都在观察表里，只落实了第一条、补了过程截图。两次都是“读了没照做”，所以改成抄进检查单（[进化机制 · 反复出错怎么升格](./evolution.md#反复出错怎么升格)）。

为什么要抄：读过的规则在长任务里会被后面的工作冲淡，最常见的返工是“明明读过还是没做到”。抄成本单检查单，交付前对的是这张单子，而不是凭记忆。

## 交付前逐条检查

| 成品 | 重点查 | 什么不算查过 |
|---|---|---|
| 学员课件 / 分享资料 | 标题、表头、提示框、正文里有没有讲师视角的话（时长、"讲师演示"、"课堂要看什么"）；读出来像不像建委在说话（对照[口语样稿](../expression/voice-samples.md)）；每个知识点有没有画面或例子；截图上的编号和框逐张按原尺寸看，有没有压住要看的字 | “写入成功”；只看了自己的源稿、没回读飞书；课件里写的数字、“全对”没回到原始结果核对；截图只看了缩略图 |
| 写了事实、引用、结论的任何文字成品（课件、文章、方案、分析、整理别人的答复） | 逐句找出“全部、一定、安全、不能、一句没加”这类说满的话，和引用、转述的原话，回到出处（原话、官方文档、实跑截图、原始数据）对一遍：程度不比出处更绝对；演示用的是示例数据、模拟、某个版本，就写明 | 数字核对过了但程度词没核对；凭记忆转述；把“能做到”写成“做到了” |
| 讲师备课稿 | 开头写明"仅内部使用"；时间和备用方案符合本场安排 | 只看了大纲，没按本场时长过一遍 |
| 对外方案 | 有没有内部内容（谈判策略、提示词原文、操作路径、"待核实"）；价值写得具体，没有假大空 | 脚本没报错就算干净 |
| 宣传 / 招生 | 身份、荣誉、价格、权益和[背书表](../../personal/credentials.md)、项目记录一致；每个问题都是潜在学员真关心的 | 凭印象写的数字和头衔 |
| 书稿 | 功能、菜单名是否查证过；小白能不能照着做 | “应该叫这个名字”；看的是旧版本界面 |
| 设计 / 视频 / 界面 | 看实际导出的画面：有没有裁字、漏镜头、声音错位；对照[设计原则检查表](../../work/domains/design/common/design-principles/README.md#交付前检查表) | 只看了缩略图、源文件或渲染进度到 100% |
| 应用开发 | 真实走一遍用户流程和出错的情况，不能只看构建通过；交付说明附[证据表](../../work/domains/development/experience/delivery-and-testing.md#说法不能比证据大交付附证据表默认)；交付前再填下面“开发交付前八项”的实测值 | 构建通过、代码检查通过、AI 说“已修复”；写入后回读一致（只证明写进去的等于读到的，不证明读对了）；抽查没抽到最容易错的那类；模拟手机当实体手机；测试只说“全部通过”不写跑了几项；在最后一次改动之前跑的测试 |
| 比赛评审材料（申报书、技术报告、逐字稿） | 每句是不是写给评委的：没有填写提示、代做、多余澄清；团队表只空姓名；标题黑体、图注居中（[天津大赛文档规范](../../work/domains/development/industry-cases/education/tianjin-agent-contest/document-format.md)） | 只看了正文，没看实际导出的 Word 或 PDF |
| 仓库写入 | 按[写入规范](./ingestion-workflow.md)跑校验 | 本地提交成功，但没推送或没确认远端已有 |

**“什么不算查过”这一列为什么要有**：AI 最常见的偷懒，是拿“生成成功”“没报错”“它说好了”当作做完了。证据要对得上这一次的成品：数字换一种办法重算、文件打开看、画面按原尺寸看、流程真走一遍。别的成品照这个思路判断，表里没列的也一样。

**开发交付前八项（检查动作，每项填实测值，不打勾；某项不适用就写“不适用：原因”，例如网页项目没有打包版）**：

| 查什么 | 填什么 | 规则 |
|---|---|---|
| 测试本身 | 实际执行了几项；用的测试数据、模拟接口、缓存、环境开关是哪个版本；从哪个目录跑的 | [测试结果先查测试本身](../../work/domains/development/experience/delivery-and-testing.md#测试结果先查测试本身默认) |
| 最后一版 | 最后一次改代码的时间，和最后一次完整测试的时间；源码版、打包版各跑了几项、几项过 | 同上，“交付的那一版最后再完整跑一遍” |
| 用户能从头试 | 清了哪些旧结果、保留了哪些设置；按用户方式启动后看到的第一屏是什么 | [交给人实测之前](../../work/domains/development/experience/delivery-and-testing.md#交给人实测之前清掉旧状态自己先打开一次默认) |
| 加功能、改功能的影响面 | 同级参照是哪一个（页面、组件、弹窗、类型），新旧并排截图看到哪里不一致；影响面清单每一行（后台发布、列表、“全部”、详情、搜索、标签、导航、权限、分享导出、缓存）是“改了”还是“不受影响”，用同一条新记录实际走过的结果；换一个新名字复验的结果。往已有网站发新内容时填：同栏目参照的是哪一条、走的哪个发布入口和数据类型、新旧两条详情页并排截图看到的差异 | [加功能、改功能](../../work/domains/development/experience/delivery-and-testing.md#加功能改功能先列影响面新界面沿用同级的旧样式默认)；建委个人作品网站、十一创网站、仓流三个项目都出现过“只改点名那一处”或“新界面另起一套”，2026-11-27 建委要求写成通用经验 |
| 跨层用同一套数据 | 这次改动经过哪几层（界面、服务端、数据库、外部接口）；每层测试用的是哪套数据；至少一条关键操作从界面点到数据库真实走通：填用户原新建/编辑入口、请求地址、状态码、库里同一条记录，以及重开和前台结果；公开环境变量和构建脚本逐项对过几个 | [跨层契约](../../work/domains/development/experience/delivery-and-testing.md#跨层契约前端后端数据库要用同一套数据测默认)；仓流 11-16 和十一创直播系统 11-14 两个项目读了仍各层分开测，2026-11-24 升级改成填值 |
| 有界面时：宽度、长内容、同类对象、状态 | 按[前端移动端检查的填值表](../../work/domains/development/experience/frontend-ui-quality-standards.md#移动端从真实失误提炼的检查方法)逐行填：侧栏展开后的实际宽度、用的最长内容、旧项和新增项的同视口截图、空/加载/失败状态各看到什么 | [前端 UI 质量标准 · 交付前填值表](../../work/domains/development/experience/frontend-ui-quality-standards.md#移动端从真实失误提炼的检查方法)；个人作品网站 R77、R80 两单读了仍漏，2026-11-27 升级改成填值。没有界面写不适用 |
| 出错的情况 | 这次改动会碰到哪些失败组合（部分成功部分失败、中断后重开、接口返回异常或缺字段），每种各用什么数据测了、结果是什么 | 上表“应用开发”行的“真实走一遍出错的情况”；[中断以后再测一遍](../../work/domains/development/experience/delivery-and-testing.md#跨层契约前端后端数据库要用同一套数据测默认) |
| 收尾 | 自己启动过的进程编号或配置目录、现在是否都已退出、端口是否释放；用户原来开着的程序是否都还在 | [只停自己启动的进程](../../work/domains/development/experience/delivery-and-testing.md#只停自己启动的进程默认) |

为什么写成填值：图片入表工具 11-21 到 11-23 的日志里，同几类问题在不同阶段反复出现：测试夹具、回放缓存、模拟协议、环境开关用错版本或从错的目录跑；最后一次改动后没重跑、打包版才测出；交付前没留干净的初始状态；测试进程遗留。前四项对应的规则这次才写进[交付与测试](../../work/domains/development/experience/delivery-and-testing.md)，按[晋升的写法](./evolution.md#三什么时候把观察升成通用规则ai-自己判断默认)，能在成品上核对的同时写成检查动作。“出错的情况”一行不同：上表“应用开发”早就要求走一遍出错的情况，阶段 26（失败批次缺坐标，状态接口报错）、阶段 28（单段失败没单测）两次仍漏，属读了没做到第二次，按[反复出错怎么升格](./evolution.md#反复出错怎么升格)改成填值。打勾太容易，填不出实测值就说明没做。

发现问题先改，改完回看受影响的上下文，再交付。

## 正式交付前，请一个全新的审查者（默认）

做的人和查的人是同一个 AI、同一段上下文时，容易看不出自己的问题。所以正式交付前，另开一个**全新的子代理或新对话**，只给它审查需要的东西，让它挑毛病。

**什么时候做**：交给建委看的正式版本（成片、整套 PPT、对外文档、学员课件、给评委的材料、上线前的应用）。中途预览、只改一个字、只回答问题的不做。工具开不了子代理时，做的人自己按下面清单换位复看一遍，并在交付说明里写“这次没有独立审查”。

**交给审查者的**：

1. 成品本身：文件路径，或者按原尺寸导出的关键页、关键帧（视频含转场和镜头运动中的帧）。
2. 这一单的要求：建委的原话、交付对象和用途。
3. 本单检查单（动手前第 4 条抄的那张，含抄进来的观察待定行）。**检查单要包括这个领域验收表里的通用项（视频的全片切点和配音对照、结尾留白、闪帧，PPT 的字号和出界……），不能只把建委这一轮提的几条交过去**：审查者只会查你给它的范围。反例：驰热固芯创赛片 v3 的审查说明只列了建委提的 8 条，审查者没查全片切点，“答案”没说完就切进建模动画、几处切点比句尾早 0.1—0.2 秒都没查出来，建委看片时指出。
4. 设计类：[建委的审美标尺](../../work/domains/design/common/design-principles/taste-benchmarks.md)里相关的两三对正反例，以及同类的认可成品。
5. 写了事实和引用的文字成品：出处（原话、原文链接、实跑截图），让审查者逐句核对转述有没有说过头。开发和数据类：交付说明里的[证据表](../../work/domains/development/experience/delivery-and-testing.md#说法不能比证据大交付附证据表默认)。让审查者逐行核对每句“通过”“全对”的范围有没有比实际做的大，“没覆盖什么”是否如实；再核对“开发交付前八项”填的实测值，填不出或对不上的列为问题；其中“加功能、改功能的影响面”一行是**必查项**：审查者自己打开同级参照和新做的那一个并排看，样式、状态、发布路径有一处不同就列为问题（2026-11-28 升级：这条读了仍两单被违反）。

**不交给审查者的**：做的人的自评、改了哪些、为什么这样做。审查者先拿到结论，就容易顺着结论看。

**让审查者做什么**：逐条对照检查单找出没做到的；对照正反例判断这版更像哪一边；按严重程度列问题，每条写清在哪一页、哪一帧、哪一句。只列问题，不改成品。**设计类还要单独回答“这一页好不好看、像不像专业设计师做的”，并说出最丑的一处和改法**；只核对检查单逐条“过了”，不算审查过（默认）。反例：驰热固芯 v5 交付前审查了两轮，查的都是切点、出画、字号这类条目，吉利页、宝钛页、温度页版面像随手摆放也全部放行，建委说“两轮独立审查做的没有任何意义”。**判美丑时先看整页、再看细节**：先把每页落定帧缩小看块面，回答“几块内容的外沿落在哪几条共同的线上、哪里空出一块”，再放大看字和框。反例：驰热固芯 v6 的审查回答了“好不好看”，但只放大看了出界和字号，政策页零散、良品率页左侧空都放行，建委问“这些问题为什么你都检查不到”。

**拿到结果后**：做的人逐条改，改完重新出图核对；认为某条不用改的，在交付说明里写理由。审查者指出、而仓库里本来就有对应规则的，就是一次 B 类失败的苗头，记进[使用日志](./usage-log.md)的说明里。

## 交付时告诉建委

一两句话即可："这次用了仓库里的 ××、×× 经验；××那条因为……没有照做。"不要附一大张自评表。有独立审查的，再加一句它查出了几条、改了几条。

交付之后在[使用日志](./usage-log.md)记一行（怎么记见[仓库怎么越用越好用](./evolution.md#一每次用完记一行使用日志默认)）。建委这次纠正或认可了什么，记进[观察记录](./observations.md)。

## 自动检查工具（可选）

能运行 Python 时，可以用脚本扫一遍常见问题：

```text
python system/repository/maintenance/check-deliverable.py <草稿路径> --profile learner            # 学员课件
python system/repository/maintenance/check-deliverable.py <草稿路径> --profile external-proposal  # 对外方案，支持 DOCX
python system/repository/maintenance/check-deliverable.py <docx或txt> --profile competition --layout tianjin-contest-word  # 天津大赛评审材料（txt 不加 --layout）
python system/repository/maintenance/check-deliverable.py <成品> --profile general --links <链接清单.txt>  # 成品里的链接是否与清单逐字一致
```

[脚本](./maintenance/check-deliverable.py)只能发现已知的几类问题（讲师视角词、方案里的内部内容、DOCX 隐藏链接等）。没报错不代表没问题，仍然要自己读一遍。

## 同样的错又犯了

说明规则写得不够具体，或者没被读到。先在[使用日志](./usage-log.md)里把这次记成 A（没读到）或 B（读了没做到），再按[规则什么时候改写](./evolution.md#四规则什么时候改写降级或撤掉默认)处理：改规则的写法和检查动作，不要再加一条"必须"。能用脚本判断的错（禁用词、字体、版式参数），加进检查脚本并写一条测试：脚本对任何模型都一样执行，不靠这一次的 AI 记不记得。
