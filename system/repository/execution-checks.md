# 用仓库经验做成品时怎么自查

适用于：用仓库里的经验做出实际成品（课件、方案、文章、视频、应用），交付之前。只查事实或位置时不用。

读到规则不等于做到了。常见情况是 AI 明明读了"课件不写讲师安排"，交出来的稿子里还是有"本节讲 20 分钟"。所以交付前要拿成品逐条对照。

## 动手前（在心里或草稿里过一遍，不写进成品）

1. 这次交付什么、给谁看？给学员的课件、给主办方的方案、给讲师的备课稿，是三种东西。
2. 读了哪几个文件？里面有哪几条红线？
3. 这次有没有建委的特别要求，会不会跟默认规则冲突？冲突时按 [AGENTS](../../AGENTS.md) 第 3 步的优先顺序取舍。
4. **把这次要守的规则抄成本单检查单。** 从读过的文件里只挑和这一单有关的几条（红线全抄，默认挑相关的），每条写成能在成品上核对的样子：看哪一页、哪一帧、量什么、多少算过。设计类再从[建委的审美标尺](../../work/domains/design/common/design-principles/taste-benchmarks.md)挑两三对相关的正反例放进去。长任务每交一版之前，回到这张单子逐条过一遍。

为什么要抄：读过的规则在长任务里会被后面的工作冲淡，最常见的返工是“明明读过还是没做到”。抄成本单检查单，交付前对的是这张单子，而不是凭记忆。

## 交付前逐条检查

| 成品 | 重点查 | 什么不算查过 |
|---|---|---|
| 学员课件 / 分享资料 | 标题、表头、提示框、正文里有没有讲师视角的话（时长、"讲师演示"、"课堂要看什么"）；读出来像不像建委在说话（对照[口语样稿](../expression/voice-samples.md)）；每个知识点有没有画面或例子 | “写入成功”；只看了自己的源稿、没回读飞书；课件里写的数字、“全对”没回到原始结果核对 |
| 讲师备课稿 | 开头写明"仅内部使用"；时间和备用方案符合本场安排 | 只看了大纲，没按本场时长过一遍 |
| 对外方案 | 有没有内部内容（谈判策略、提示词原文、操作路径、"待核实"）；价值写得具体，没有假大空 | 脚本没报错就算干净 |
| 宣传 / 招生 | 身份、荣誉、价格、权益和[背书表](../../personal/credentials.md)、项目记录一致；每个问题都是潜在学员真关心的 | 凭印象写的数字和头衔 |
| 书稿 | 功能、菜单名是否查证过；小白能不能照着做 | “应该叫这个名字”；看的是旧版本界面 |
| 设计 / 视频 / 界面 | 看实际导出的画面：有没有裁字、漏镜头、声音错位；对照[设计原则检查表](../../work/domains/design/common/design-principles/README.md#交付前检查表) | 只看了缩略图、源文件或渲染进度到 100% |
| 应用开发 | 真实走一遍用户流程和出错的情况，不能只看构建通过 | 构建通过、代码检查通过、AI 说“已修复” |
| 比赛评审材料（申报书、技术报告、逐字稿） | 每句是不是写给评委的：没有填写提示、代做、多余澄清；团队表只空姓名；标题黑体、图注居中（[天津大赛文档规范](../../work/domains/development/industry-cases/education/tianjin-agent-contest/document-format.md)） | 只看了正文，没看实际导出的 Word 或 PDF |
| 仓库写入 | 按[写入规范](./ingestion-workflow.md)跑校验 | 本地提交成功，但没推送或没确认远端已有 |

**“什么不算查过”这一列为什么要有**：AI 最常见的偷懒，是拿“生成成功”“没报错”“它说好了”当作做完了。证据要对得上这一次的成品：数字换一种办法重算、文件打开看、画面按原尺寸看、流程真走一遍。别的成品照这个思路判断，表里没列的也一样。

发现问题先改，改完回看受影响的上下文，再交付。

## 正式交付前，请一个全新的审查者（默认）

做的人和查的人是同一个 AI、同一段上下文时，容易看不出自己的问题。所以正式交付前，另开一个**全新的子代理或新对话**，只给它审查需要的东西，让它挑毛病。

**什么时候做**：交给建委看的正式版本（成片、整套 PPT、对外文档、学员课件、给评委的材料、上线前的应用）。中途预览、只改一个字、只回答问题的不做。工具开不了子代理时，做的人自己按下面清单换位复看一遍，并在交付说明里写“这次没有独立审查”。

**交给审查者的**：

1. 成品本身：文件路径，或者按原尺寸导出的关键页、关键帧（视频含转场和镜头运动中的帧）。
2. 这一单的要求：建委的原话、交付对象和用途。
3. 本单检查单（动手前第 4 条抄的那张）。
4. 设计类：[建委的审美标尺](../../work/domains/design/common/design-principles/taste-benchmarks.md)里相关的两三对正反例，以及同类的认可成品。

**不交给审查者的**：做的人的自评、改了哪些、为什么这样做。审查者先拿到结论，就容易顺着结论看。

**让审查者做什么**：逐条对照检查单找出没做到的；对照正反例判断这版更像哪一边；按严重程度列问题，每条写清在哪一页、哪一帧、哪一句。只列问题，不改成品。

**拿到结果后**：做的人逐条改，改完重新出图核对；认为某条不用改的，在交付说明里写理由。审查者指出、而仓库里本来就有对应规则的，就是一次 B 类失败的苗头，记进[使用日志](./usage-log.md)的说明里。

## 交付时告诉建委

一两句话即可："这次用了仓库里的 ××、×× 经验；××那条因为……没有照做。"不要附一大张自评表。有独立审查的，再加一句它查出了几条、改了几条。

交付之后在[使用日志](./usage-log.md)记一行（怎么记见[仓库怎么越用越好用](./evolution.md#一每次用完记一行使用日志默认)）。建委这次纠正或认可了什么，记进[观察记录](./observations.md)。

## 自动检查工具（可选）

能运行 Python 时，可以用脚本扫一遍常见问题：

```text
python system/repository/maintenance/check-deliverable.py <草稿路径> --profile learner            # 学员课件
python system/repository/maintenance/check-deliverable.py <草稿路径> --profile external-proposal  # 对外方案，支持 DOCX
python system/repository/maintenance/check-deliverable.py <docx或txt> --profile competition --layout tianjin-contest-word  # 天津大赛评审材料（txt 不加 --layout）
python system/repository/maintenance/check-deliverable.py <成品> --profile general --links <链接清单.txt>  # 成品里的链接是否与清单逐字一致
```

[脚本](./maintenance/check-deliverable.py)只能发现已知的几类问题（讲师视角词、方案里的内部内容、DOCX 隐藏链接等）。没报错不代表没问题，仍然要自己读一遍。

## 同样的错又犯了

说明规则写得不够具体，或者没被读到。先在[使用日志](./usage-log.md)里把这次记成 A（没读到）或 B（读了没做到），再按[规则什么时候改写](./evolution.md#四规则什么时候改写降级或撤掉默认)处理：改规则的写法和检查动作，不要再加一条"必须"。能用脚本判断的错（禁用词、字体、版式参数），加进检查脚本并写一条测试：脚本对任何模型都一样执行，不靠这一次的 AI 记不记得。
