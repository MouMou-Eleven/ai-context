# 表达与成品标准

目标是准确、自然、符合用途的中文成品：课件像有实践经验的讲师在解释，书稿符合编辑与读者要求，方案体现真实判断。专业感来自内容与细节，不能虚构经历、从业年限或资质；自然也不等于一律口语化。

## 默认短卡

生成、改写或审核中文成品时先用本卡，再按[体裁入口](./genres.md)读取本次需要的专项要求。简单回复遵守已载入短卡即可；写入仓库同时执行[沉淀流程](../repository/ingestion-workflow.md)。

1. 先明确读者、用途、成品形式与事实来源，直接回应实际问题。
2. 说清谁做什么、对什么起作用、得到什么结果。删掉没有新增信息的客套、抽象套话、重复总结与机械排比。
3. 检查主谓搭配、指代、因果和承接。句长随内容与读者调整，不把长句全部切碎，也不靠口头重复模拟真人。
4. 保留原意、条件、责任和不确定性，不用润色扩大能力、抹去未定项或编造第一人称经验。
5. 按接收者需要安排标题、步骤、表格、图文与结尾。说明标题讲清主题，创意标题可以有悬念但不能误导；纯讲解、叙事和动态不强加营销行动。
6. 交付前先核事实与专业完整性，再读实际句段，修正歧义、空泛、重复和语气不合。口播朗读，书面检查上下文；文字通顺不能替代项目验收。

## 冲突与沉淀

通用层负责中文清楚准确，专项层决定组织与专业要求，项目提供事实。课堂口播不覆盖出版书面语，营销结构不覆盖纯教学，正式成品也不能隐藏未约定的责任。用户本次要求与已接受稿的保护范围先核对；不可消解的事实冲突必须说明。

建委2026-09-12确认希望专业、自然、减少模板感。领域偏好、认可样稿和真实改稿留在原领域／项目，注明用途与确认依据，不在个人信息另建文风档案。没有认可样稿时按体裁写，不宣称“完全像建委”。

发现问题先在原项目保留改前／改后及原因；跨任务反复发生，或建委明确要求普遍执行的，才提炼进纠错表。新同义反馈补证据，不增加文件；只对某客户或体裁有效的规则留专项。具体更新动作见[来源文件](./sources.md#后续反馈怎样进入规则)。

资料存在GitHub不会训练模型，也不保证其他AI宿主已经读取。这套标准的价值是被实际调用后约束写作与改稿；能否改善质量需要真实成品反馈验证，不用AI检测器分数证明“像人”。
