# 表达与成品标准

本页是所有中文输出的通用短卡。生成、改写、润色、翻译或组织中文成品时先读；简单回答遵守本轮已载入的短卡即可，不重复读取长规则。代码或文件操作本身不加载写作流程，其中文说明仍应清楚、准确。

这里负责表达质量与成品检查；专业方法来自工作领域，事实来自项目，建委个人口吻来自[个人表达偏好](../../personal/expression-preferences.md)。专业感要由准确内容、判断和细节体现，不能靠虚构从业年限或堆术语。

## 如何使用

确认读者、用途和主要成品 → 本页短卡 → [对应体裁](./genres.md)的权威规则 → 必要领域方法与项目事实 → 按成品检查并修订。需要署名或以建委身份表达时，再补个人风格和真实经历。

“生成中文”和“写入仓库”分别判断。修改课件并沉淀经验时，表达、培训与[写入流程](../repository/ingestion-workflow.md)都适用，不能因为选择写库而漏掉表达标准。多个能力可按制作步骤组合，不同时套用多个互斥体裁。

## 每次执行与交付前检查

1. 确认给谁、解决什么问题、交付形式和事实来源；项目身份不能从模板示例推断。
2. 主语、动作、对象、指代明确；一个句子承担一个主要判断，复杂因果拆开。
3. 事实、推测、示例和待确认分开；数字、产品功能与效果承诺必须有依据。
4. 先说具体内容，删掉空泛客套、机械排比、同义重复和翻译腔；不能因润色改变原意或增加经历。
5. 标题自解释，图文/旁白一致；表格用于横向比较，流程关系用图，顺序用步骤，不设固定视觉数量。
6. 按成品选择结构和语气；正文面向接收者，内部过程和制作提醒另放。纯观点、记录或讲解可以自然收束，不强加销售行动或固定例子数量。
7. 交付前对照原始事实与该体裁标准，检查是否缺必要信息、是否有歧义和重复、是否像接收者实际会使用的成品；发现问题先改再交付。复杂改稿按[验收流程](./evaluation.md)展开。

## 写入

通用口语/书面规则分别只维护一处，体裁索引只指向权威正文，领域文件只补场景差异。原始材料就近登记来源，不能直接当规则。已有同义方法补证据或修订，不复制。新规则应有适用/排除条件和可观察验收；本页只保留高频通用质量要求。用户认可样稿与合成示范分别标记，不能把演示结果写成实战验证。
