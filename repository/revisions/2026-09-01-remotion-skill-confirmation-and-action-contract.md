# 2026-09-01 Remotion Skill 确认门与动作契约修订

## 触发原因

`jianwei-ai-community-remotion-video` 首次图片开场动画实测暴露了两项问题：原 Skill 规定“内部形成 Motion Blueprint 后直接实现”，用户无法在生成前核对方向；动作规范只要求主动作和镜头，没有强制逐元素定义触发、路径、速度与因果，模型因此使用通用缩放、淡入和镜头推拉替代用户期望的动作编排。

## 错误案例结论

- 参考图展示的是最终构图，不能把整图低透明度铺底后再叠一套重建元素，否则会产生重影和错误视觉。
- “有明显镜头运动”不能替代元素动作。开场动画应先建立指针、路径、框体、控制柄、标签、标题和装饰之间的触发链。
- 用户说“随机弹出”时，Remotion 中必须转换成预先确定但视觉上有差异的方向、顺序和幅度，不能使用未播种随机数。

## 新口径

- 代码、预览和渲染任务默认分为“制作规划确认单 → 用户明确批准 → 实施”两阶段。
- 即使用户已经写出详细动作，也先结构化复述供核对；详细需求不是实施授权。
- 只有用户当前请求明确说“无需确认、直接制作”等同义表达，才允许免确认，并记录原话作为证据。
- 用户提出修改后必须更新规划并再次等待确认，不能把修改意见直接当作批准。
- 每个关键元素必须说明触发、起始状态、动作路径或形变、持续时间、缓动、因果、结束状态、微动和实现类别。
- 相机必须服从动作链，不能用持续变焦掩盖内部状态没有变化。

## 同步范围

- 更新 Skill 主入口、图片分析、动效导演、输出契约、质量门槛、JSON Schema、验证脚本和 UI 默认提示词。
- 更新 ai-context 固定快照、本机安装目录和本地交付包。
- `workflowRevision` 提升为 2，默认确认模式固定为 `plan-first-explicit-confirmation`。
