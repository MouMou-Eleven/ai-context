# Teaching and Course Design — 备课、课程开发与课件设计

> 状态：当前有效的知识入口
> 口径确认：2026-08-18
> 适用范围：建委作为 AI 讲师进行备课、培训课程开发、培训课件设计、教学活动和讲师交付。

## 当前已经确认的边界

这里负责跨课程可复用的“怎样教”，例如课程开发方法、课件设计、讲师课件与学员资料边界、教学活动和课程复盘。它不负责某个课程产品的价格、招生话术或季度大纲。

这里也不负责教师微课、精品课、参赛课或 VR 交互课件制作。此类任务进入 [`../microcourse/README.md`](../microcourse/README.md)。

当前仓库尚未形成一套完整、经过建委确认的课程开发和课件视觉规则。AI 不能把通用教学法自行写成“建委的规则”；每次先遵循用户当次要求，确认有效后再沉淀。

## 当前调用顺序

1. 先确认培训对象、已有基础、授课场景和最终要做出的结果。
2. 判断交付物是讲师备课、讲师课件、学员课件、课程正文还是招生内容。
3. 读取所属项目的当前事实，避免课程内容和产品承诺冲突。
4. 学员正文再调用教程写作方法；技术难点再按需调用表达与讲解方法。
5. 课程规则只服务教学，不能自动套进普通文章、短视频、销售页或飞书书稿。

## 学员正文与讲师备课的边界

2026-08-16 建委确认：面向学员的课程正文默认不写“这一部分多少分钟”“每个环节多少时间”等讲师内部授课时长。时长、讲课顺序、现场提示和互动安排属于讲师备课资料；只有建委明确要求时，才在学员资料中出现时间信息。学员正文应把篇幅用于解释为什么学、怎样操作、怎样验证和遇到问题如何判断。

2026-08-18 建委进一步确认：学员正文中的标题、段落和列表也不能伪装成讲师提示。“把三种方式放在一起演示”“讲师这里打开页面”“接下来向学员展示”等措辞属于备课动作，不属于课程内容。学员正文应直接写学员要理解的对象，例如“更加直观的案例演示”“普通网页和 API 地址有什么不同”。课程资料即使由讲师用于授课，默认观看对象仍然是学员。

## 现场授课复盘确认的课程标准

2026-08-16 晚，建委实际讲授会员社群第3课后确认：一份资料看起来信息丰富、阅读顺畅，不代表它能够被自然地讲出来。技术概念课应优先设计现场动作、前后对比和可观察结果，再补充解释；不能先写成长文章，再把文章标题当成课程目录。

当前通用规则：

- 一节课开头先建立学习理由：学员当前怎样使用、为什么会卡住、学完后会多出什么判断和能力、这些内容会在后续哪些任务中继续出现。没有这张地图，概念越多，学员越容易把课程理解成术语记忆。
- 每个核心概念至少对应一个学员能看见的操作、变化或结果。抽象概念可以用受控测试、产品对比或同一任务的前后差异呈现。
- 推荐顺序是“熟悉任务 → 旧做法 → 新做法 → 结果对比 → 概念名称 → 收益与边界”，不要从英文全称和内部组成开始。
- 正文和表格必须分工。正文解释原因和变化，表格只做横向比较、选择或映射；表格只是把正文重写一遍时应删除。
- 学员正文只呈现知识、案例、操作和判断；演示准备、切屏动作、讲师提醒、提问方式和节奏安排另放讲师备课资料。
- 现场被讲师直接跳过的段落不是无关反馈，而是高价值证据。复盘时要判断它属于重复、书面化、无演示、顺序错误、专业细节过早还是只适合作为延伸阅读。
- 技术简化不能制造错误机制。类比和演示必须保留真实边界，例如图形界面操作不等于暗中执行 CLI 命令，上下文压缩也不等于窗口无限或模型能力按固定比例下降。

完整方法、案例和检查表见 [`demo-driven-course-design.md`](./demo-driven-course-design.md)。
